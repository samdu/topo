# Timing a launch and a turn

Where the time goes is read off marks the app writes itself. `Perf.mark(_:)` (`Packages/TopoCore/Sources/TopoCore/Perf.swift`) logs one `notice` line per named moment under subsystem `zone.hexagon.topo`, category `perf`: `mark t=<epoch ms> <name> [detail]`. A mark carries a name and nothing of the person's: no words, no tokens, a request's method, route and byte count at most. The route is the path with every segment that is not one of `Forwarder.routeSegments` replaced by `*`, and no query (`Forwarder.routeForMark`). `turn.reply.shown` is the reply handed to the view, a frame before it is drawn; `resident.spawned` is a launch that succeeded (its `cpu`, and `resident.ready`'s, is the CPU the app's process has used so far, in milliseconds, so the difference between the two is what the whole app spent while Claude Code started, the guest included), and one that failed is `resident.launch.failed`.

## The marks

| Path | Marks, in order |
| ---- | ---- |
| Launch | `app.init.begin sinceProcessStart=<ms>`, `app.housekeeping.begin`/`.end`, `app.init.end`, `chat.appear`, `scene.active`, `chat.log.read`, `ear.load.begin`/`.end`, `voice.load.begin`/`.end` |
| Guest start | `guest.boot.begin`, `guest.downloads.present`, `guest.kernel.booted`, `guest.dns.up`, `guest.tmp.zone.done`, `guest.claude.verified`, `guest.tools.ready`, `guest.proxy.up`, `resident.launch.begin fresh\|resume`, `resident.spawned cpu=<ms>`, `resident.ready fresh\|resume cpu=<ms>` (Claude Code's answer to the `initialize` each launch writes first, which it gives once it is reading its input: the process is ready for a turn) |
| Turn | `turn.send`, `turn.runner.made`, `turn.begin`, `turn.lease.acquired` and `turn.log.read` (the long way only: the read runs while the lease is taken, so the second is whichever ended later), `log.append.checked`, `lease.batch.lapsed` (a batch found the lease lapsed and reads the record to claim afresh: before a reply's save, or before `turn.lease.fresh` when the lease lapsed while the person's batch waited), `lease.batch.refused <notHeld\|taken>` (why a batch was refused: a reply's as displaced, the person's before the turn goes the long way), `turn.lease.fresh` (the fresh path only, after its save: the person's turn saved in one batch with the lease's renewal or that fresh claim, or on a retry found in the log and the lease heartbeated; ## A run with nobody at the phone

`scripts/perf-run.sh --device <id> [--build | --app <Topo.app>] "question" ["question" …]` installs a build, launches it cold with `TOPO_PERF_SEND` in its environment, and copies the marks off when the run is done. `PerfRun` (`Apps/Topo/PerfRun.swift`) is what reads the variable: it starts `tmp/topo-perf.log` in the app's container empty, has every mark written there as well as to the log, sends the first question as soon as the scene is up and each next `TOPO_PERF_GAP` seconds (5) after the reply to the last, through the harness's own line (`willSend`, `retry`) as the composer does, and marks `perf.run.done answered=<n>/<m>`. Each `perf.question <i>/<m>` carries `thermal=<0–3>` (`ProcessInfo.thermalState`: nominal, fair, serious, critical), since a phone warmed by earlier runs interprets the guest slower and a run is only comparable with one at the same state. A question counts as answered when its reply is in the transcript, which is waited for up to a minute after its turn ends (a turn saved as a limb's is answered by another device); the run ends at the first question that gets none, and, after the log has been read and any words the launch before left on the line have been sent (`perf.line.waiting`), sends nothing if words are still waiting. A proxy mark names a request by the path segments in `Forwarder.routeSegments` and writes `*` for any other. `TOPO_PERF_SEND` is a JSON array of strings, which the script makes from its arguments. One launch is one run, however many windows it restores. The script polls the file with `devicectl device copy from` until that mark is in it, taking only a file whose first mark is no older than its own launch (a copy can reach the phone before the new process has emptied the last run's file), and exits 4 when fewer questions were answered than asked. A blank question is refused before anything is installed (exit 2).

In a timed run the proxy also marks what each `/v1/messages` request is made of and what the API counted of it: `proxy.shape` (`system=<bytes>:<digest>` a block each, `tools=<count>:<bytes>:<digest>`, `messages=<count>:<bytes>`, `head=<digest>` of the first message, `marks=` each `cache_control` by place, `s`, `t` or `m` and an index, with its `ttl`), `proxy.usage in=… cacheRead=… cacheWrite=…` from the answer's `message_start`, and `proxy.usage.out <tokens>` at its end. A digest that differs between two requests is a part that changed, which is what stops a cached prefix being read. They are made only while a run is being timed, since they parse the request.

With `--spoken` (`TOPO_PERF_SPOKEN=1`) the questions are sent as spoken turns once the voice is resident, their replies are read aloud from the phone, and the next question waits for the reading to end. The run waits up to two minutes for the voice, since a fresh install compiles its model on the first load (`voice.load.begin` to `voice.load.end`, 35–44 s on an iPhone 15 Pro), and marks `perf.voice.unready` if it sends without it.

With `--fresh` (`TOPO_PERF_SETUP=1`) the run is a first run: the script deletes the app from the phone, which takes its container and every download and compiled model with it, then installs (so `--app` or `--build` is required, exit 2 without), and the app waits for every setup line to be done before its first question, up to 50 minutes, marking `perf.setup.done`, `perf.setup.failed <part>` as soon as a line fails (nothing retries it without a foreground), or `perf.setup.unfinished`. A reinstalled phone is a new device to the lease, so it usually opens as a viewer, its kept login dropped: whoever is at the phone makes it the primary ("Make this device the primary…", which demotes the device that was) and signs in if asked. The phone stays unlocked with Topo in front throughout, or the suspended time is inside the timings. The script deletes nothing unless `--app` (or `--build`'s product) is a bundle whose identifier is Topo's, asks the phone whether Topo is installed rather than reading an error's words, takes only a well-formed answer, and stops when there is none or the delete fails, since a container left behind would make a warm run read as a first one. The script's timeout is an hour unless `--timeout` says. The first-run account is then read off the marks: from `app.init.begin` to each entry's `download.present`, `guest.import.end`, `ear.load.end` and `voice.load.end`.

So one run times a cold launch, a question asked into a cold app, and as many warm turns as there are further questions. The questions are sent as the person and land in their transcript.

`PerfRun` is in a release build because a release build is what is timed. The variable reaches the process only from a launch by `devicectl` or Xcode, from a Mac the phone trusts; an ordinary launch has none.

The phone has to be unlocked: `devicectl` refuses to launch an app on a locked one, and the script exits 3 saying so.

## Without the script

The same marks are in the phone's unified log: `sudo log collect --device-udid <hardware udid> --last 15m --output run.logarchive`, then `log show run.logarchive --predicate 'subsystem == "zone.hexagon.topo" AND category == "perf"' --style compact`. The collect needs the phone awake and unlocked and no `idevicesyslog` attached to it; from buddybox it works over the Wi-Fi pairing (`sudo` is needed, with the login password), and `--last 24h` reaches as far back as the phone keeps, a few hours of a busy day. The archive is the phone's whole log, which the predicate narrows at `log show`; the collect changes nothing on the phone, so it is the read to make while somebody is using it. A file the app writes into its own container, copied out with `xcrun devicectl device copy from --domain-type appDataContainer` as `perf-run.sh` does with the marks file, is the other read.

## What the process costs

`EnergyPulse` (`Apps/Topo/EnergyPulse.swift`) writes one `energy` mark a minute for as long as the process runs: this process's CPU as a share of one core and in seconds, its idle and interrupt wakeups a second, both from the kernel's `TASK_POWER_INFO` counters, the battery level and charger, the thermal state, Low Power Mode, whether the app is in front, and what it was doing — the guest resident or not, a turn in flight, the microphone open, a reply being spoken, a background hold standing. A second mark, `energy threads`, names the threads the minute's CPU went to, the busiest first, so a minute that cost something says where: each thread's seconds are summed under its name before a group under 0.05 s is left out, and what threads that ended inside the minute spent, which the kernel no longer names, is `unattributed`. Both marks read the same interval, timed by the continuous clock, so a change to the phone's clock does not move a rate. Both are marks like any other (unified log, `perf` category, and a timed run's file), and both are appended to `tmp/topo-energy.log` in the app's container, started afresh past 512 KB, which `devicectl device copy from --device <id> --domain-type appDataContainer --domain-identifier zone.hexagon.topo --source tmp/topo-energy.log --destination <file>` reads off a phone nobody is at. A guest process's thread is counted as `guest`, never by the command it was named after. The diagnostics screen shows the last pulse.

MetricKit's daily payload (`MXMetricPayload`: this process's CPU time, display luminance, bytes over cellular and Wi-Fi, time in the foreground, the background and background audio) lands through the same subscriber, up to a day after it was gathered, as a one-line `energy metrickit` mark and a JSON file under Application Support/metrickit (not backed up), the newest fourteen of each kind kept, metrics and diagnostics; the diagnostics screen counts them. A TestFlight build's payloads also reach Xcode's Organizer under Energy, which a dev-signed build's never do.

Two launch arguments are for a profiling run from a Mac and nothing else: `--stay-awake` holds auto-lock off for the run as a standing `AudioSession` screen claim, beside the microphone's and the speaker's (a locked phone takes no launch and no copy), and `--still-mascot` draws Topo once, as Reduce Motion does, so a state can be measured with and without him moving. A run is the phone unlocked on a charger, one state at a time for four or five minutes (the first pulse after a launch carries the launch itself), and the lines compared by their `cpu` and `wakeups` fields.
