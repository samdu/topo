# Running Topo in the simulator, signed in

The iOS Simulator is where a change is tried against a real Claude account before it goes to the reviewer: the app signs in, takes a turn, and the reply lands in a real CloudKit log — Buddy's own, not Sam's. `scripts/simulator-run.sh` on buddybox does the whole of it.

## The one rule

**A debug build only ever talks to Haiku.** `ClaudeModel.pinned` in `Packages/TopoTurn/Sources/TopoTurn/MessagesAPI.swift` is `.haiku45` under `#if DEBUG` and nil otherwise, and `MessagesAPI.complete` puts the request's model through `ClaudeModel.effective` — so the pin is at the wire, not at the picker, and every caller obeys it: the chat's own turn, `answerPending`, and anything added later. The settings sheet still offers Sonnet, Opus and Fable, and in a debug build all three go to Haiku; `MessagesAPITests.aDebugBuildAsksHaikuWhateverTheSettingSays` is what holds that. The guest's requests go through the API proxy, which in a debug build rewrites the `model` of every `/v1/messages` body to Haiku (`APIProxy.pinnedModel`) whatever the guest asked for; `DebugPinTests` holds that.

Three things would get past it, and all three are visible: building Release (`-configuration Release`, or an archive — `scripts/archive-upload.sh` is a release build and is meant to be), editing `pinned`, or a turn taken by something that is not this app on this build — the hub, or a `claude` CLI somebody runs by hand.

## The token

Sam's long-lived Claude Code setup token (`claude setup-token`, inference only) lives in the 1Password Homelab vault as `long-lived-claude-auth-token`, field `oauth token`, and reaches the Macs as `CLAUDE_SETUP_TOKEN`. The script reads it from that variable, or from the vault with `op-item` when it is not set, and hands it to the app as `SIMCTL_CHILD_TOPO_CLAUDE_SETUP_TOKEN`.

An environment variable is the whole delivery: it lives in the launching shell and the launched process and nowhere else. It is not in the scheme (which is generated from `project.yml` and committed), not in a build setting, not in a file the app reads, and not in the `.app` — so no build, artifact or commit carries it, and nothing survives that a screenshot or an `ipa` could leak.

`DebugRun.signIn` writes it into the store as a finished sign-in, which is why the simulator comes up past the sign-in screen with no browser and no paste. A setup token has no refresh token, so none is stored; it is written with a 30-day life (`TOPO_CLAUDE_SETUP_TOKEN_DAYS`) so no run tries to exchange it. It then sits in **that simulator device's keychain**, so the device stays signed in across runs, a reinstalled app included, until the device is erased.

## Whose account the simulator is on

The simulator device is signed into **`buddy.durose@icloud.com`**, Buddy's own Apple ID. The container is the one every bundle uses, `iCloud.zone.hexagon.topo`, but a private database belongs to whichever account is signed in, so the log a run writes is that account's: a turn sent from a simulator never reaches Sam's transcript, and nothing of his is readable from one. Send whatever a test needs.

Both sign-ins are per device and both persist: the iCloud account and the Claude setup token in the keychain stay until `scripts/simulator-run.sh --erase`, which returns that device to a factory one and takes both with it. So the sign-in is paid once per simulator device, and erasing one is what to do when it is finished with — after which the next run needs the iCloud sign-in by hand again.

## A run

From the cluster, through buddybox's GUI session, because `xcodebuild` needs the login keychain (see the wiki's `macs` page):

```bash
ssh buddybox 'sudo launchctl asuser $(id -u) sudo -u buddy bash -lc \
  "cd ~/github/topo && scripts/simulator-run.sh --send \"what did I forget this week\" --screenshot ~/Desktop/topo-sim.png"'
```

What it does, in order: builds the `Topo` scheme Debug for the named simulator (`DEVICE`, an iPhone 17 by default), boots it, installs the app, and launches it with the token in its environment. With `--send` the app takes exactly one turn through the ordinary harness — the primary lease, the append-only log, `MessagesAPI` — and prints each step prefixed `[topo-debug]`, ending in `done`. The script launches the app under a fresh run id (`TOPO_DEBUG_RUN`) and waits for `done`; it exits non-zero if the launcher exits before it (or non-zero after it), if no turn finishes within `TIMEOUT` seconds (180), if an `error:` line came back, or if there is no `reply to <turn> in run <id>:` line under this run's id. The app prints that line only for the reply to the turn it just sent — the person's turn found by the nonce `Harness.willSend` returned, the reply found as an assistant turn naming it among its parents (`DebugRun.answer`) — and prints `no reply to <turn>` otherwise, so an older reply in the log, a reply to another device's turn, or a line from an earlier launch never passes as this run's answer. Without `--send` it leaves a signed-in simulator on screen to drive by hand, and exits with the launcher's failure if the launch fails. `scripts/tests/simulator-run-test.sh` runs the script against a fake `xcrun` (no simulator, token or network) through each of those failures and a clean answer; the PR check runs it.

The turn is a real one: it spends Sam's subscription (a Haiku turn, so barely) and it appends to the simulator account's Topo transcript in the development container, which is the point — it is the path the phone takes.

## Pressing the microphone

The microphone press is covered by an XCUITest, `TopoUITests` (`Tests/ClientUI/MicrophonePressTests.swift`), which is what `simctl` alone cannot reach: it drives the running app, taps through the permission prompts on SpringBoard, and taps, holds and releases the button on the chat screen. After each gesture it holds that the app is still `runningForeground` and the button is back at rest, and that the press reached `VoiceInput` (the tap included). After the hold it holds which branch the press took, and what the microphone delivered. A crash on the press, an instant one included, is an app that is no longer running, whichever layer it came from: a trap or an Objective-C exception that `VoiceInput.begin`'s `do`/`catch` never sees, not only a Swift error. The test is in the `Topo` scheme's test action, and the PR check runs it in a job of its own, `topo_ui`, beside the jobs that run the rest of the scheme's tests and everything else; `scripts/simulator-run.sh --press-mic` runs it by hand on buddybox.

Everything it reads is the button's debug-only accessibility value, a JSON `VoiceInput.Report` decoded strictly (unsigned counts, so a malformed or negative one fails the test): `presses` and `sessions`, the last press's `refusal`, the ear's state, and its `capture`. The capture is counted by `TapMeter` inside the input tap block itself (buffers, frames, rate, RMS), so it is what the input delivered after the engine started rather than that a tap was installed, plus the samples that reached `SampleSink` at the ear's rate and what the release returned as heard. All of it is behind `#if DEBUG`. Every outcome is recorded as an XCTest activity named for its branch, with the report attached, so the result bundle and the log say what ran.

The app is launched signed in with a placeholder token, past the first-run question, and with `TOPO_DEBUG_KEEP_SPOKEN=1`, so whatever a press hears is printed and never sent and the token never reaches the API. Three tests, each selected through `TOPO_DEBUG_EAR` (`DebugRun.ear`) and asserted rather than assumed:

- **The ear over a stub**, `TOPO_DEBUG_EAR=stub`: an ear resident without a model, over an engine that returns no words. It holds that the stub is resident before the press, that buffers reached the tap for most of the hold, and that the sink holds what the tap delivered at 16 kHz.
- **A press the ear cannot hear**, `TOPO_DEBUG_EAR=loading`: an ear whose load never finishes, so it is never resident and every press is refused with the ear's own words ("preparing the models for this phone"). It holds that the refused hold opened no session and delivered nothing. The refusal comes before the audio session and before the input guard, so this one passes on every host, a Mac with no microphone included.
- **Parakeet hearing the fixture through the microphone**, `TOPO_DEBUG_EAR=<directory>`: the real ear, loaded from a directory holding the two model directories (`scripts/fetch-ear-models.sh <directory>` fills one from the manifest, verified). The lane loops `Tests/Fixtures/purple-elephants.wav` ("purple elephants juggle seven lanterns", from `say`, 16 kHz mono) into the host's input, and the hold is two loops and a second long, so it spans a whole phrase; the test holds that the fixture's energy reached the tap and the sink and that Parakeet's transcript has each of the phrase's words.

The lane comes from the test runner's environment, set on the `xcodebuild` command line with the `TEST_RUNNER_` prefix. `TEST_RUNNER_TOPO_UITEST_AUDIO_INPUT=1` declares a host with an audio input, where a hold refused for want of one fails. `TEST_RUNNER_TOPO_UITEST_EAR_MODELS=<directory>` enables the Parakeet test. `TEST_RUNNER_TOPO_UITEST_PRIVACY_RESET=1` declares that the app's privacy grants were cleared, which makes the prompt count exact. The PR check sets the input and the reset on every PR, and the models only on the full lane: `scripts/ci-audio-lane.sh start` installs BlackHole (a virtual loopback device, CI tooling only) as the runner Mac's default input and output, and starts the feeder (`scripts/ci-audio-feeder.swift`) under a loop that restarts it if it exits. The feeder is one long-lived engine: it loops the fixture into the output, listens to BlackHole's input in the same process, and restarts itself on three seconds of silence or on a device change, logging each restart. The runner's loopback goes silent now and then, with the devices still pinned and a player still running, so a feeder that only replays the file does not hold. `scripts/ci-audio-lane.sh check` runs before and after the suite. It fails the job with an `::error::` naming what died: a dead supervisor, a stale heartbeat, a default device that is no longer BlackHole, or BlackHole's input silent over three seconds to a separate meter (`scripts/ci-audio-meter.swift`). It prints every restart the feeder logged as a warning. The fixture has to come from the host: what an app in the simulator plays does not reach the host's loopback device.

**The real ear runs on the full lane, not on every PR.** The stub and loading tests hold the press path and need no model, so they run on every PR, behind the same audio lane, since the stub replaces recognition and not capture. The Parakeet test runs on the full lane: a PR whose diff touches the voice path (the `VOICE_PATHS` list on the select job in `pr-validate.yaml`, which `scripts/ci-select-lane.sh` reads and `scripts/tests/ci-select-lane-test.sh` holds against the file), and the same workflow's nightly run on main. The full lane restores the models from a cache keyed on the manifest and, past the target check, asserts by name that the Parakeet test ran and passed (`scripts/ci-require-tests.sh named`). Every other PR takes the fast lane, which deselects that one test with `-skip-testing`, so it neither runs nor skips; a skip anywhere still fails the job. The select job's log and summary say which lane the run took and why. A regression in recognition from a change outside the list shows up on the next nightly rather than on its PR. By hand, `workflow_dispatch` runs the workflow with `lane: full` (the nightly's body) or `lane: fast-benchmark` (the fast lane forced, to time it).

### What the press cannot reach here

**A host with no audio input has no microphone to press, and says so with a skip.** The simulator routes the Mac's default input, and a Mac mini with none leaves `AVAudioEngine`'s input node reporting a dead format, so the press is refused at `VoiceInput`'s own guard (`VoiceInput.noInput`) before any tap is installed. The test holds that the refused hold opened no session and delivered nothing, then ends in `XCTSkip("missing coverage: …")` naming what did not run; without the models directory the Parakeet test skips the same way. Any other refusal fails. The refusal test needs no input at all, since the ear's check comes first, so it passes there too. The tap, the sink, the caption loop and recognition from the microphone are the PR check's loopback lane, or a Mac with a microphone.

**The permission prompts are counted, and on a cleared lane the count is exact.** Both lanes that run the test clear the app's privacy grants before the suite (`xcrun simctl privacy <udid> reset all zone.hexagon.topo`, in `pr-validate.yaml` and in `scripts/simulator-run.sh --press-mic`) and declare it to the runner as `TEST_RUNNER_TOPO_UITEST_PRIVACY_RESET=1`. The first press in each test answers whatever SpringBoard puts up, and the class keeps a running total across its tests, which share one process. With the flag set, every test that pressed holds the total is exactly one — the microphone prompt, raised by the first press in the run and by nothing after it — so a permission the app should not ask for and a reset that silently did not happen both fail. Without it the total is held at no more than one. Every alert answered has to carry `NSMicrophoneUsageDescription`.

**The simulator runs Parakeet and Pocket on the CPU; a device runs them on the Neural Engine.** FluidAudio's CoreML models load and decode in the simulator (a few seconds to load, about a second and a half for the fixture), so recognition and synthesis are tested there, but not their speed, the ANE's numerics, or the vocabulary rescoring on a device. This lane speaks nothing at all: it launches with `TOPO_DEBUG_VOICE=loading`, so the voice asks for none of its 351 MB and no reply is read aloud. Reading one aloud is the talk lane's.

## Speaking a question, answered aloud

`scripts/simulator-run.sh --talk` is the one run that chains the whole voice path on a real account: a question spoken into the simulator's microphone, heard by Parakeet, sent as a spoken turn, answered by Claude, and read aloud. It runs on buddybox and nowhere else, because it needs a real setup token, the simulator's iCloud account and a loopback lane:

```bash
ssh buddybox 'sudo launchctl asuser $(id -u) sudo -u buddy bash -lc \
  "cd ~/github/topo && DEVICE=<udid> EAR_MODELS=~/models/topo-ear VOICE_MODELS=~/models/topo-voice scripts/simulator-run.sh --talk"'
```

The test is `SpokenTurnTests` (`Tests/ClientTalk`), the only test in the `TopoTalkTests` target and the `TopoTalk` scheme. It is not in the `Topo` scheme's test action: the PR check has no token and no iCloud account, and `scripts/ci-require-tests.sh` fails any skip there. `DEVICE` takes a UDID as well as a name, which matters on buddybox, where two simulators are called iPhone 17 and only one is signed into iCloud.

What the script does, in order: reads the token as `--send` does; fetches and verifies the ear's models into `EAR_MODELS` (`build/ear-models` by default) and the voice's pack into `VOICE_MODELS` (`build/voice-models` by default, under `Models/pocket-tts/` beneath it, where FluidAudio's Pocket loader reads it from); both scripts keep a file that already matches; starts the loopback lane with `Tests/Fixtures/capital-of-france.wav` ("What is the capital of France? Answer in one word.", from `say`, 16 kHz mono) as `scripts/ci-audio-lane.sh start <fixture>` does on CI, saving the Mac's default input and output first; runs the test with the token and both model directories in the test runner's environment (`TEST_RUNNER_TOPO_TALK_SETUP_TOKEN`, `TEST_RUNNER_TOPO_UITEST_EAR_MODELS`, `TEST_RUNNER_TOPO_UITEST_VOICE_MODELS`); holds the lane with `check after`; and passes only when `scripts/ci-require-tests.sh xcresult` finds `TopoTalkTests` ran and passed. Once the lane is up it shuts the simulator down and boots it again: a simulator's audio is served by a host process bound to the coreaudiod it booted against, and `start` restarts coreaudiod when it installs BlackHole, so a simulator booted before that finds no input and the hold is refused. The iCloud account and the keychain survive the reboot. On every exit it runs `scripts/ci-audio-lane.sh stop`, which kills the feeder's supervisor and then the feeder and puts back the defaults `start` saved. On buddybox that is output "Mac mini Speakers". buddybox has no microphone, so BlackHole is its only input and stays the default input.

The lane's own tools ask macOS for the microphone the first time they open BlackHole's input, and the prompt ("bash would like to access the Microphone") waits in buddy's GUI session, not the shell. Until someone clicks Allow there, the feeder writes no heartbeat and the meter cannot start the input, and `start` fails naming both. It is a virtual 1920×1200 display, reachable with `vncdo` against `127.0.0.1:0` as `buddy`, whose password is the Homelab vault's `Buddy Mac Login`. The token reaches the test runner's environment and the app's launch environment, and no file, scheme or build setting.

The test launches the app with the token, the real ear and the real voice from their model directories, `-firstRunAnswered YES`, `-readAloud YES`, and an empty outbox, so no line an earlier launch left waiting goes ahead of the question. `TOPO_DEBUG_KEEP_SPOKEN` is not set, so what the microphone hears is sent. Every missing prerequisite fails by name: no token or models directory in the environment, an ear or a voice that is not resident within ten minutes, a hold refused for want of an input, an error line on the chat screen in place of a reply. Pocket compiles its models on the first load, so the question waits for the voice to be resident — a reply that landed before it would be answered in silence. The hold is two loops of the fixture and a second, so a whole question is in it wherever the loop starts, and the transcript usually holds the question more than once. On a simulator that has not answered the microphone and speech prompts, the first hold is released while they are up and starts nothing. The test answers the prompts and holds again. It then holds:

- Parakeet was the recogniser and heard each of the question's words.
- The spoken turn is in the log, under the nonce the chat sent it with, and its text is what Parakeet heard.
- A reply naming that turn among its parents is in the log and contains "Paris".
- The speaker was given that reply's text, started it on Pocket and came to its end rather than being stopped. The activity records how long the reply's first frame took and its real-time factor.

What it reads is two debug-only accessibility values, decoded strictly: the microphone's `VoiceInput.Report`, and the badge's `DebugRun.ChatReport` (identifier `topo-debug-chat`, on the button; a toolbar item's container carries its child's identifier too, so the type is what names the one element), which carries the last spoken turn's nonce, that turn and its reply as `DebugRun.answer` finds them, the chat screen's error line, and `Speaker.Report`. The speaker's report says how many replies `speak` was given, the last one's engine (`pocket`, the only one there is) and text, whether audio for it started (the first frame queued), whether it finished, and the reply's own two measurements: seconds from `speak` to the reply's first frame being scheduled, and the time spent synthesising over the audio that made. Neither is ever a stand-in — the first is written once, when that frame is scheduled, and both are absent when no frame ever was. The app's `voice:` console line carries the same two numbers per sentence, which an XCUITest cannot read because the app's stdout goes to the test runner rather than the log. The chat report also carries the voice's own state, which the test waits on before it presses. Each step is an XCTest activity with the report attached, printed as `[talk]` lines in the log.

What it does not cover: Parakeet and Pocket run on the simulator's CPU, not the Neural Engine, so neither the speed nor the placement a phone gets is shown here; the question is `say`'s through a loopback device, not a person's through a microphone; and what the speaker plays goes to the host's output, which nothing listens to.

## Running a command in the guest

```
DEVICE=<udid> scripts/simulator-run.sh --userland "claude --version" --fresh --expect "2.1.278 (Claude Code)" --expect-rootfs fetched --expect-claude fetched
DEVICE=<udid> scripts/simulator-run.sh --no-build --userland "claude --version" --expect "2.1.278 (Claude Code)" --expect-rootfs reused --expect-claude reused
```

`--userland CMD` launches the app with `TOPO_DEBUG_USERLAND=CMD`: it fetches the rootfs and Claude Code through `ModelDownloads` (or finds the fakefs already made and the binary already on the phone), imports the rootfs, boots the guest, checks Claude Code against its pin and mounts it at `/usr/local/bin/claude`, starts the API proxy on loopback, and runs the command under `/bin/sh -c` with `ANTHROPIC_BASE_URL` set to the proxy and `CLAUDE_CODE_OAUTH_TOKEN` to the guest's token (the line `userland: proxy on …, guest token: long-lived` or `access token` says which; with no login it says so and the command runs with no token), printing the proxy's own lines as `proxy: …`, `[topo-debug] userland: claude code <version> verified in <n> ms, mounted at /usr/local/bin/claude`, `[topo-debug] guest: <line>` for each line the command wrote and `[topo-debug] guest exit: <status>`, ending in `userland done`. No token is read unless `--send` is given too — a simulator signed in by an earlier launch keeps the setup token in its keychain, and `DebugRun.signIn` writes it as the guest's token as well, since it is the long-lived kind — and the build runs `scripts/build-ish.sh` first. The script passes only with no `userland error:` line, the line saying Claude Code was verified and mounted, exactly `guest exit: 0`, and, when given, a `guest: <TEXT>` line equal to `--expect TEXT`, the rootfs line `--expect-rootfs` names — `fetched` (this launch downloaded the tarball and imported it) or `reused` (the fakefs was already whole and nothing was fetched or imported) — and the Claude Code line `--expect-claude` names: `fetched` (this launch downloaded it) or `reused` (it was already on the phone; nothing was fetched, and nothing is ever copied). `--fresh` uninstalls the app before installing it, so its container, the downloads and the fakefs go with it. The rootfs comes from `dl-cdn.alpinelinux.org` and Claude Code (227 MB) from `downloads.claude.ai`, so the simulator needs the network the first time, and a first run wants `TIMEOUT` above the default 180 s on a slow line. `claude -p` in the guest reaches the model through the proxy, on the guest's token.

## What a shell cannot reach

`simctl` has no tap. It boots a device, installs and launches an app, and captures the screen, and there is no command in it that touches what is on that screen; System Events cannot see the Simulator's window either, so an AppleScript UI script finds nothing to click. Anything behind a gesture is out of reach from a *shell* — which is why the microphone press is an XCUITest (above) rather than a `simctl` step; screenshots are the same, so `--screenshot` captures whatever the app came up on and nothing further in.

That is the shape of the whole shell path: what a run can exercise from a shell is what the launch environment can drive — the sign-in `DebugRun` writes, the one turn `TOPO_DEBUG_SEND` takes — and the gestures are the XCUITest's or a person's at the Simulator on buddybox.

## Behind the lock, on a phone

A simulator cannot lock, so the reply heard behind the lock screen is shown on a phone. Two things make that run readable:

- **No debugger.** Xcode's debugger keeps a backgrounded app alive, so anything it shows about the background is wrong ([Apple DTS](https://developer.apple.com/forums/thread/75468)). The build is installed and launched over `devicectl` (`xcrun devicectl device install app` and `device process launch`), and the evidence is unified logging: every hold and keeper transition, every rebuild of the play queue, and — in a debug build — a heartbeat every five seconds go to `os_log` under subsystem `zone.hexagon.topo`, category `audio` (`Apps/Client/AudioLog.swift`). Read them back after the run with `log collect --device` and `log show --predicate 'subsystem == "zone.hexagon.topo"'`. The heartbeat stopping is the process being suspended.
- **What an interruption was.** Every `AVAudioSession.interruptionNotification` is logged with its type, `AVAudioSessionInterruptionReasonKey`, `AVAudioSessionInterruptionWasSuspendedKey` and its options, because iOS posts a `.began` at the lock screen with no call and no Siri in it and the numbers are what name it.
- **A reply that lands late.** `TOPO_DEBUG_REPLY_DELAY=<seconds>` (`DebugRun.delayReply`, a debug build only) makes the harness wait that long before the model call, so the reply arrives well past iOS's ordinary background grace of about thirty seconds and only a working hold carries it.

## What needs a person

- **The iCloud sign-in on the simulator device**, once per device: Settings › Sign in to your iPhone, `buddy.durose@icloud.com` and its two-factor code. It is a gesture, so it is done at the Simulator rather than from a shell. Without an account CloudKit answers `noAccount`, the log cannot be written, and a `--send` run fails at "Reaching iCloud…" rather than at the model.
- Nothing else. The build signs itself from the certificate already in `buddy`'s login keychain, there is no Xcode dialog on this path, and no keychain unlock: `launchctl asuser` puts the build in the GUI session, where the certificate's keychain is already open.
