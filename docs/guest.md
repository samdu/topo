# The guest

Claude Code on the phone: the Alpine userland iSH runs inside the app, the loopback proxy its API calls go through, the internet it reaches directly, the tool service its `topo` command calls, the one resident process, and the bridge that makes it the chat's brain. What the guest may reach is decided at its holes (`docs/design.md`); the invariants are in CLAUDE.md's *Where the risk lives* (the resident process, the bridge, the holes, the token and the proxy, the tool service).

## The userland

The guest is an arm64 Alpine userland run inside the app's own process by iSH's kernel: `Packages/TopoUserland`, linked into the iOS target alone. Its C side is `TopoIsh.xcframework` (iOS device and arm64 simulator slices, gitignored under `Packages/TopoUserland/Frameworks/`), which `scripts/build-ish.sh` builds from `OpenMinis/ish-arm64` at its pin with meson `guest_arch=arm64`, `kernel=ish`, `engine=asbestos` and exactly the patches in `patches/ish/` — the memory brake's refresh hook (`ish_mem_refresh_hook`, `kernel/mmap.c`: on a sample older than two seconds the kernel asks the app for a fresh one before it fails closed), `pidfd_open` on a child that has exited and not been reaped (`kernel/pidfd.c`: it opens and reads as exited, as on Linux, rather than failing `ESRCH`; Claude Code's runtime opens a pidfd on every child it spawns, and its `ESRCH` path registers fd 0 with its own epoll, so its stdin reader's registration fails and it exits 0 having read nothing), the guest's own `mount(2)` refused `EPERM` for `real` (`fs/mount.c`: the guest runs as root, and a realfs mount made from inside is a bind mount of any path the app's sandbox can open, so what the guest reaches is what the app mounts — `topo_ish_mount` calls `do_mount` and is not this path — while `proc`, `devpts` and `tmpfs` stay mountable), the guest's DNS stub (`fs/sock.c`: `127.0.0.53` port 53 carried to the app's forwarder on `127.0.0.1` and reported back as the stub, while the app has set a port; below), SQABS and SQNEG on every vector arrangement (`asbestos/guest-arm64/gen.c` and `asbestos/guest-arm64/gadgets-aarch64/math.S`, run on the host's NEON as ABS and NEG are: the ugrep Claude Code's Bash tool runs as `grep` counts newlines with SQABS, so without it `grep -n` over a real file dies of SIGILL, which through a pipe reads as no match), a guest tmpfs unmounted rather than the app ended (`fs/tmp.c`: the fork's `tmpfs_umount` is `TODO()`, which is `die()`, so a guest process's `umount` of a tmpfs it mounted ends the whole process; it frees the tree, outright, since `mount_remove` reaches it only at a mount refcount of 0, which no open fd allows, and the filesystem has no unlink, rmdir, rename or link to put a pointer into the tree from outside), the block chaining's test of a free jump slot (`asbestos/asbestos.c`: a block's exit is chained to the block it jumped to only while the slot still holds its own fake ip, since a patched slot holds a host pointer, and the resident's text lies where the low 32 bits of the heap's pointers fall, so judged by its low 32 bits alone a patched slot reads as a guest address now and then, which chained it again and linked the block into a second block's predecessor list; the invalidation that disconnected the first block then found the link already cleared and crashed on it, #290), SMOV to a general register (the same decoder and `math.S`'s UMOV gadget, sign-extending: Claude Code's Bun reads a vectorised count back with SMOV, so without it a turn dies of an illegal instruction a few seconds in, though `claude --version` runs), the rest of the NEON Claude Code's binary holds and the fork did not decode (SQSHLU and UQSHL by immediate, SCVTF and UCVTF with fractional bits on vectors, UDOT, and FNEG on half-precision vectors, in the same two files: the first four are ordinary NEON, in its pixel packing, its Adler-32 and its number scaling, and the last two sit behind features the guest does not report), and the `offsets` source meson leaves out of the fork's own executable — linking the fork's libraries, its fakefs importer and `deps/libarchive` (built with no crypto library and no XML reader); `deps/linux` is never fetched and `deps/libapps` never linked. The script refuses a checkout that is not the pin, a patch that does not apply cleanly (`git apply --check`), a populated `deps/linux`, and a meson configuration read back that is not those three options, and skips when the framework's inputs stamp matches the pin, the options, the patches, the glue and the script itself; `scripts/tests/build-ish-test.sh` holds each refusal red, and the PR check builds the framework before any `xcodebuild` and asserts both slices export `ish_mem_refresh_hook`, `ish_dns_sentinel_port` and the glue's `topo_ish_set_dns_port`.

The glue is `Packages/TopoUserland/Guest/topo_ish.c` behind `topo_ish.h`: import, combining the rootfs and Alpine packages into one archive for it, boot, spawn (stdin from `/dev/null`, or a pipe whose write end the app keeps, `F_SETNOSIGPIPE`, so a write to a program that has gone is `EPIPE` and never a signal; a program that cannot be started has its task exit and reaped, since a task that never ran takes no signal and would leave every later termination unconfirmed), wait, signalling every guest task but init under the pid table's lock, counting what of a list of pids still runs (reaping, as init, those orphaned to it, which init never reaps), a line about one task for a log (its name, thread and parent, whether it is running, exiting or a zombie, the last syscall it entered, a pending `SIGKILL`), a realfs bind mount of a host directory, a mount of the memory's folder through the vault's own filesystem, the unmount of either, a link in the fakefs, and the brake's feed, compiled into the framework. The vault's filesystem is `Guest/topo_vaultfs.m`, the fork's realfs with the file coordination the fork's `app/iOSFS.m` puts around it (that file is the fork's app, which its meson build does not make): an open of a regular file for reading is a coordinated read, released once the file is open, so it waits for any writer and has iCloud Drive bring an evicted file down first — judged on the descriptor the open returns as well as the stat before it, so a file made between the two is let go and opened again under the coordination; every open for writing is a coordinated write held until the file closes, so the mirror never reads half a note the guest is writing; a rename, removal or creation is a coordinated write; stat, readdir, readlink and utime are realfs's own, since a coordinated stat of an evicted file is a download of every file a listing touches. Each wait is on a queue of its own, holds no lock of the kernel's, is bounded at `TOPO_ISH_VAULT_WAIT_SECONDS` (20 s, the mirror's own bound on a download; then `EIO`) and is looked at every 100 ms for a SIGKILL to the waiting task (then `EINTR`), since a host semaphore is nothing the kernel's signal wakes. `.topo` at the mount's root, the mirror's baseline, is refused `EACCES` to every operation, judged by the path's text, which is the host's path because the host follows no link: every call is made from the path's folder, opened from the vault's root with `O_NOFOLLOW_ANY`, on a last name it does not follow either. The guest resolves its own links first, but keeps what it resolved per thread for 100 ms, so a folder on the way can be a link — to `.topo`, or out of the vault — by the time the host walks it, and that walk fails `ELOOP`. Unlike realfs, its unmount closes the folder's descriptor.

A task is started with `SIGUSR1` unblocked on the starting thread: every task thread, and every thread it forks, inherits that thread's mask, a GCD worker blocks `SIGUSR1`, and `SIGUSR1` is how iSH interrupts a task parked in a host call, so with it blocked no signal, `SIGKILL` included, reaches a `sleep` or a blocked read. A second `SIGKILL` to a task that already has one pending wakes its thread again, since iSH queues a pending signal without waking and its one wake is lost if it lands between the syscall's check and a host `nanosleep`.

`Guest` boots one kernel per process on a fakefs — init never runs a program, since init exiting halts the process — refuses every boot after the first whatever it answered, names the guest `topo` rather than letting the kernel copy the host's name into its 65-byte field, and runs a program as init's child over host pipes, returning its output and its exit status (128 plus the signal for a signal), in `Guest.environment` unless it is handed another: root's home, the usual path, `SHELL=/bin/bash` (what Claude Code's Bash tool runs in, inherited by the resident and everything it starts), `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, which keeps Claude Code's telemetry, error reports and start-up fetches off: none serves a turn, and its start is about a fifth shorter without them. `Userland.bootGuest` then starts the guest's DNS forwarder and keeps the guest's `/etc/resolv.conf` to it (`GuestResolver`, `Apps/Topo/GuestResolver.swift`). The forwarder (`DNSForwarder`, `Packages/TopoProxy`) listens on `127.0.0.1` at one port picked at start, over TCP through an `NWListener` required to that address and over UDP on a socket of its own bound there, each reply sent to the address its question came from (an `NWListener` over UDP hands datagrams from different clients to one connection, and a reply to only one of them). It asks each question of the phone's own resolver — `DNSServiceQueryRecord` with `kDNSServiceFlagsReturnIntermediates`, on every interface, class IN, driven by `DNSServiceSetDispatchQueue` on the forwarder's own queue and deallocated there (`SystemRecordResolver`) — and writes the answer back as a DNS reply of its own making, so the guest's names are resolved as the phone's own lookups are: through Private Relay, a VPN's resolver and its split DNS, a DNS profile. musl's `resolv.conf` names an address and never a port, and an unprivileged process cannot bind `127.0.0.1:53`, so the file names `127.0.0.53`, the guest's stub, on which nothing listens, and the guest's socket layer carries it (`patches/ish/0006-dns-sentinel.patch`, given the port by `Guest.setDNSPort`): a `connect`, `sendto` or `sendmsg` to `127.0.0.53` port 53, or `::ffff:127.0.0.53`, goes to `127.0.0.1` at the forwarder's port, and `127.0.0.1` at the forwarder's port comes back from `recvfrom`, `recvmsg` and `getpeername` as the stub, since musl drops a reply from an address it did not send to — for any socket, so a guest process that addresses the forwarder's port directly sees its replies come from the stub; no other address, port or family is touched, and with no port set nothing is. A question is complete when a record of the type asked for has arrived (for a CNAME question, the CNAME) and its batch has ended — the next callback without `kDNSServiceFlagsMoreComing` — or when a negative or an error arrives — save a negative dnssd answered from its cache (`kDNSServiceFlagAnsweredFromCache`), which waits up to 250 ms for an answer from the network and is the reply only if none comes, since when a VPN comes up dnssd answers from the old configuration's cache first and the network after (a phone with Tailscale just on gets a cached `NoSuchRecord` for a tailnet name and the address 10 ms later): dnssd's `NoSuchName` is answered `NXDOMAIN`, `NoSuchRecord` `NOERROR` with no answers, each with the CNAMEs gathered, and any other error `SERVFAIL`; a batch of CNAMEs alone is not complete, since the target's records can come in a later one. TTLs are dnssd's, and nothing is kept past its reply. It is bounded: a message over 512 bytes is dropped, or its TCP connection closed, unread; at most 64 questions are in flight, and the next is answered `SERVFAIL` without being asked; every question is answered within 4 s of its arrival, `SERVFAIL` at the bound with its query deallocated; at most 16 TCP connections, each closed 10 s from its accept; a reply that does not fit 512 bytes over UDP, or the query's EDNS size up to 1232, goes back with `TC` set and no records, so the client asks again over TCP, where a reply is at most 65,535; only a query of one question, opcode `QUERY`, class IN is asked, and anything else is `FORMERR` or `NOTIMP`. It logs counts, one line at most every 60 s while there is traffic, and a line when it cannot start or loses its listener or socket, since the guest then resolves through the phone's servers; never a name, a type, an address, an answer or a client's port. Every question's bound is kept by one timer, set for the earliest deadline in flight and answering only questions past their own, and questions are keyed by a number never used twice, so no late timer or callback reaches a later question and a flood leaves nothing waiting per question. The resolver writes the stub alone while the forwarder is up and the rewrite carries its port, and the phone's own name servers while it is down: `Guest.systemNameservers` reads them through libresolv's `res_ninit` (`TopoResolv`), as upstream iSH does, and only numeric addresses with no scope are written — a link-local one names an interface the guest does not have — IPv4 first and at most three (musl reads no more); when the phone lists none the guest can use, the file is `1.1.1.1` and `8.8.8.8`. Those the guest asks itself in plain DNS on port 53, round Private Relay, a VPN's split DNS and an encrypted DNS setting. `Guest.writeResolver(servers:)` writes the file through the guest so the fakefs records it, replacing whatever it held — a stale one from another network, or the mind's own — beside and moved over: once at boot, again on every change `NWPathMonitor` reports while the process lives, and on every change of the forwarder — up, the rewrite is given its port and then the stub written; down (stopped, or its listener failed or taken by iOS from a suspended app), the rewrite is cleared and then the phone's servers written — one write after another, each reading the state as it starts, so the last one written is the newest. A forwarder that went down starts again at the next foreground (`Userland.prepare`). Only a listener or socket that reports its failure is seen as down: a UDP socket iOS closes under a suspended app without an error on the next read is not, and the guest's datagram lookups go unanswered until one does (musl then asks again, and a truncated reply's TCP retry still works). With it the guest's own clients — `apk`, git, `gh`, anything the mind installs — resolve names and reach the network directly through the app's sockets, doing their own TLS, which completes on the simulator for `apk`, git's libcurl and `gh`'s Go client. A write that fails is logged and tried again, each try reading the state afresh and waiting twice as long as the last, up to 30 s, until it is made or a newer write takes its place, which does not wait out the older one's backoff; the boot waits for the first try only, so while a write fails the guest runs and may have no name resolving, which is not the boot's failure. The boot then empties `/tmp` (`Guest.clearTemporary`): the fakefs is persistent, so without it whatever a killed process left there would outlive the process. A file is read out of the booted guest by its guest path with `Guest.contents(ofFile:from:limit:)`, which the chat draws a reply's images from (`GuestImages`, `docs/chat.md`): `sh` runs `[ -f ]` and then `timeout -s KILL 25 head -c` on the path, so it is the guest that resolves it — mounts, links, the vault's coordinated open — and only a regular file is read, a pipe or a directory being refused before any read, to at most the limit and one byte, a file past it being nil. Its output is taken as bytes. It is one more guest process beside the resident, and each call holds a thread of the shared queue until its program ends, so the chat makes them one at a time: a teardown's kill of every guest process ends it (a nil), and one still dying when the teardown counts is counted among what stayed. It then mounts the phone's own time zone database into the guest at `/opt/topo/zoneinfo` (`Guest.mountZoneinfo`: the directory Apple's libc reads, `/var/db/timezone/zoneinfo` on a device and `/usr/share/zoneinfo` in the simulator, resolved to the versioned directory it links to, which the mount holds for the life of the process, so a time zone update iOS installs meanwhile reaches the guest at the next launch; a path no Alpine package owns, so an `apk` that installs or upgrades tzdata keeps its own `/usr/share/zoneinfo` untouched; read-only in effect and not by construction: the mount is read-write and the host refuses the app a write there) and starts `GuestClock` (`Apps/Topo/GuestClock.swift`), which keeps the guest's `/etc/localtime` a link to `/opt/topo/zoneinfo/<zone>` for the phone's zone (`Guest.writeTimeZone`: the name read from `TimeZone.current` after `NSTimeZone.resetSystemTimeZone()`, refused unless it is a plain zone name naming a TZif file there, the link made beside and moved over): written once the guest is booted, again on `NSSystemTimeZoneDidChange` and every foreground, and before every launch of the resident (`Userland.bringZoneUpToDate`, awaited by the launcher's environment, since a runtime keeps the zone it first reads for its life), one write after another, each reading the zone as it starts; every cue writes, whatever was written before, since a command in the guest may have relinked it, and the clock listens before its first write, so a change that lands while it runs is a cue after it. Every program started after a write — BusyBox `date`, musl's `localtime`, the Bash tool's commands, a resident Claude Code launched since, whose runtime takes the zone's name from where the link points — tells the time in that zone. A resident already running when the zone changes keeps, in its own runtime, the zone it started with until it is next launched (the process is not replaced on a zone change: #256); the commands its Bash tool runs read the new link at once. No `TZ` is set anywhere, since one fixed in the resident's environment would outrank the link for everything it starts. A refused mount or a failed write is swallowed as the resolver's is and logged nowhere: with the mount refused, a link a fakefs kept from an earlier launch points at nothing and the guest is on UTC, as it is with no link at all; with only a write failed, the link that stood stays. The app's side of the brake is `MemorySampler`, started by the boot: `os_proc_available_memory` every 250 ms and on memory pressure, and the refresh hook.

The root is Alpine's `alpine-minirootfs-3.22.6-aarch64.tar.gz`, one more entry of the model manifest with its own source URL (`url` beside the path, where the Hugging Face entries carry `repo` and `revision`), fetched by `ModelDownloads` on every foreground until it is imported (`Apps/Topo/Userland.swift`, through `DownloadSource`, which settles once with the entry's files and their pins or the fetch's failure: a failure is `Userland`'s `failed` and what `ready()` throws, and the next `prepare` fetches afresh) and never in the bundle. bash is laid in beside it from Alpine's own packages for v3.22 aarch64, pinned the same way as the entry `alpine-bash` (`url` is the branch's `main` repository, and the files are `bash`, `readline`, `libncursesw` and `ncurses-terminfo-base`, which is what `apk add bash` pulls on top of the minirootfs; `scripts/model-manifest.sh` checks each against the repository's APKINDEX, its version and size, and the set closed over its dependencies at the versions they require, which `scripts/tests/model-manifest-test.sh` holds; the PR check runs `--check`, so a manifest that is not the script's output fails), fetched on the same cue, and no `apk` runs in the guest.

`RootfsInstaller` checks the tarball and every package against the manifest's size and sha256 before the importer is called, and imports them together into `Userland/alpine.importing` under Application Support with the fork's own importer (`fakefs_import`, which keeps modes, owners and device nodes in `meta.db`): since it makes a fakefs from one archive, `topo_ish_combine` first writes one uncompressed tarball beside the staging directory — every entry of the rootfs, then each package's entries in the manifest's order, headers as the archives carry them, less each package's control entries (the dot-names at its root: `.PKGINFO`, `.SIGN.*`, the install scripts, `.trigger`), so no package script runs — and that archive is what is imported, and removed. Once the import has finished a completion marker, `topo-userland`, listing each layer's digest and name, is written inside the staging directory (beside `meta.db`, outside the guest's `data/`), and the directory is renamed to `Userland/alpine` with it — beside `Models/`, never in it, since `ModelStore.sweep` removes what under `Models/` is not a manifest home, while the tarball's and the packages' own homes, `Models/alpine-minirootfs` and `Models/alpine-bash`, are — so the marker being in `Userland/alpine` is the fakefs being whole. A staging directory or combined archive found at the start is an import a killed process left, and is discarded; a `Userland/alpine` without the marker is imported afresh and replaced once the new one is whole, never patched in place. A fakefs with the marker is kept, so a bump of the rootfs or a package reaches a phone that already has one only when that fakefs is taken away.

Claude Code is a third kind of entry, pinned by `version` beside its `url`: Anthropic's `linux-arm64-musl` build from the release distribution the official installer reads (`downloads.claude.ai/claude-code-releases/<version>/`, its size and checksum from that release's `manifest.json`, which `scripts/model-manifest.sh` checks), fetched into `Models/claude-code` on the same foreground cue and never in the bundle. It is never copied: `ClaudeCodeInstaller` (`Packages/TopoUserland`) checks the binary against the pin's size and sha256 on every install — the digest of 232 MB is what a launch pays in place of a copy, and the debug launch prints how long it took — and only then makes it executable (the guest sees the host's mode bits, and its kernel refuses to exec a file nobody may execute), bind-mounts its home at `/opt/claude-code` and links `/usr/local/bin/claude` to the file there; a binary that fails the check is mounted by nothing and made not executable, so no mount already standing can run it. A bump is a new pin: the downloader replaces the file in its home, and the next install checks, mounts and runs the new one. Its own updater stays off (`DISABLE_AUTOUPDATER=1`), since the updater speaks TLS through a library whose handshake never completes under the emulator; nothing in a user build starts it. The diagnostics `userland` row has a clause for each download — the rootfs's and bash's downloader states, then the two importing together, then ready; Claude Code's downloader state, then downloaded at its version — so it says which of the three a guest is waiting on.

The fork is GPL-3.0 under its holders' App Store waiver, which stands while the app meets the GPL otherwise, so the iOS bundle carries the licence's text (the repository's `LICENSE`) and the About screen shows it beside where the corresponding source is (`Licence` in `Apps/Client/AboutView.swift`): this repository at the commit `scripts/archive-upload.sh` writes into the Info.plist as `TopoSourceCommit` — refusing a tree with uncommitted changes or a commit on no remote branch — and the fork at its pin; `scripts/check-built-plist.sh` fails a product with no `LICENSE`.

The guest is booted once per process (`Userland.bootGuest`) by the chat's brain, once both downloads are resident (`ResidentConversation`, below), or by a debug launch with `TOPO_DEBUG_USERLAND=<command>` or `TOPO_DEBUG_GUEST_TURN`. The first (`DebugRun.userland`) waits for both downloads, mounts Claude Code, starts the API proxy and runs the command under `/bin/sh -c` with `ANTHROPIC_BASE_URL` and `CLAUDE_CODE_OAUTH_TOKEN` in its environment (`DebugRun.handOver`), and printing `[topo-debug] guest: <line>` and `[topo-debug] guest exit: <status>`, which `scripts/simulator-run.sh --userland` asserts on (`docs/simulator.md`).

the guest's own mount of a host directory refused; the memory's folder (`GuestVaultMountTests`: a read and a write through it, an open waiting for a coordinated writer, a note made between the open's stat and its open never read half written, a guest write holding its coordination until it closes, an open failing at the bound and printing nothing, a task parked in a coordination ended and confirmed inside the teardown's bound, a parked open stalling no other guest task, `.topo` refused and left byte-identical by an emptying of the vault, a mount made again reaching the new folder, an unmount refused while a guest file holds it, and a write through the home's link landing in the vault); a spawned `cat` echoing each line while it runs, a write to a program that has gone refused, and a tree of four ended and confirmed; `pidfd_open` on a zombie, a reaped and a live child, from a static program built from `Tests/Programs/pidfd.c`; ## The API proxy

The guest reaches the API through `Packages/TopoProxy`, linked into the iOS target alone, since TLS under the emulator does not work: `APIProxy`, an `NWListener` bound to `127.0.0.1` at a port picked at start (`requiredLocalEndpoint`, so no other interface and no LAN peer reaches it), plain HTTP/1.1 in and every path and query forwarded to the one upstream, `URLSessionUpstream` — `https://api.anthropic.com` over TLS, redirects refused by the session delegate so the 3xx itself goes back, no cookies, no cache, and a target that would name any other scheme, host or port refused. The guest holds its own credential (`CLAUDE_CODE_OAUTH_TOKEN`, handed over only in the environment of the process the app starts) and the proxy passes `Authorization` through unchanged, adds none, and logs method, path, status and time and never a header value.

Inbound it keeps the connection alive across requests, reads bodies framed by `Content-Length` or chunked (both at once, or any other transfer coding, is refused), answers `Expect: 100-continue`, and parses each head with CFNetwork's `CFHTTPMessage` (the target taken from the request line as written, since `CFHTTPMessage` resolves its URL against `Host`); the chunked decoder and the reader over `NWConnection` are its own. The request body is read whole; the response is streamed back chunked as the data delegate hands each piece over, hop-by-hop headers and the `Content-Encoding` URLSession has already undone taken out. An upstream failure before the response head is an Anthropic-shaped 502; one after it cannot change the status, so the response ends incomplete: no terminating chunk, and the connection closed. A target carrying a fragment is not origin-form and is refused. The connection is read continuously, so a client that goes away mid-response cancels its task, and that ends the upstream request through the body stream's termination.

In a debug build the `model` of every `POST /v1/messages` body is rewritten to `APIProxy.pinnedModel` (Haiku 4.5) before it is forwarded, the path judged in its canonical form (`APIProxy.canonical`: up to three layers of percent-encoding decoded, backslashes read as slashes, empty and dot segments dropped, lowercased, no trailing slash) so no other spelling of that path goes through unpinned; a path still percent-encoded after three decodes, on any method, is refused with a 400 before its body is read, and a body it cannot read as a JSON object is refused rather than sent unpinned. `swift test` in the package runs its suite offline: a scripted `Upstream` for the proxy, and local stub origins over loopback for `URLSessionUpstream`. `GuestResident` starts it with the guest.

## The tool service

The phone's own tools reach the guest through `TopoTools` (a library of `Packages/TopoProxy`, sharing the proxy's HTTP reader; linked into the iOS target alone): `ToolService`, an `NWListener` bound to `127.0.0.1` at a port picked at start (`requiredLocalEndpoint`, as the proxy's), with one route, `POST /run`. The body is the service's token on its first line, then a call's arguments, each one's UTF-8 in base64 on a line of its own (`ToolRequest`; BusyBox `wget --post-file` sends a file only up to its first NUL, so the bytes themselves cannot go), so a space, a quote, a newline or an empty argument arrives as given; the answer is `200 text/plain`, a first line `exit: <status>` and then what the tool said. One request per connection.

Loopback is not private, so every request carries the token: 32 random bytes as hex, made when the service is (once per process), handed to the guest only in the environment of the process the app starts, as `TOPO_TOOLS_TOKEN` beside `TOPO_TOOLS_URL`, and compared in constant time. It rides in the body and not a header because `topo` would have to give `wget` a header as an argument, and every process in the guest can read every other's arguments; `topo` writes it with bash's own `printf`, so it is in no process's argv, into a FIFO `wget` posts from (`mktemp -d`, mode 600): `wget` opens its body by name and iSH cannot open a pipe by path (no `/dev/stdin`; `/proc/self/fd` does not reopen), and a FIFO holds nothing on the disk. The FIFO's writer is bounded at 110 s, so one whose reader never came is gone within the call's bound, and writes nothing unless it opened the FIFO — a `topo` ended before then has removed it, and the writer's standard output is the caller's — and the answer comes back on `wget`'s standard output, so neither the token nor what a tool answered is ever in a file. Before any tool runs a request is refused when it lacks that token, carries an `Origin` or a `Sec-Fetch-*` header, names a `Host` other than `127.0.0.1` or `127.0.0.1:<port>`, or is not `POST /run`, or when its body is not newline-ended lines of base64 UTF-8 or is over 64 KB. Every connection is bounded at 90 s from its accept, under the 120 s Claude Code's Bash tool gives a command: a request not whole by then is answered 408 and closed, and a call not answered by then is answered with status 4 whether or not the tool has stopped; the call is cancelled then, and when whoever awaits `ToolService.bounded` is cancelled (a widget's run at a sign-out). The service logs each call's tool, status and time and each refusal's reason, never an argument, a header value or a tool's output.

The tools are a table (`ToolTable`): `topo help` lists it and `topo help <tool>` prints a tool's usage, from the same table the calls dispatch through. The statuses are 0 done, 1 failed, 2 not a call the tool takes, 3 the app did not answer (the script's own), 4 past the bound, 5 not allowed on this phone, 6 part of the call refused. The app's tools are set by `TopoApp` on `GuestResident.toolTable`:

- `topo look` (`Apps/Topo/Tools/LookTool.swift`) is the mind's hand on this phone's look, through `Tuning` (`docs/chat.md`). With nothing after it, it prints the fields most worth tuning — the transcript's margin, insets, spacing and line width, Topo's placement, scale, clearance and speed, and what the three models are called (`mind.sonnet`, `mind.opus`, `mind.fable`, each a name of 1 to 24 characters on one line, drawn on the model slider and in the notice while a turn is asked) — each with the value worn, its range and whether this phone, the vault's `look.json` or the compiled look gave it (`look.json` when its reading took that field, `LookDocument.Reading.fields`, whatever the value); every other field this phone sets; and the `look.json` reading's summary, the diagnostics row. `topo look set <part.field> <value> …` sets fields: a value is JSON where it parses as JSON and a plain word otherwise, and each is read alone onto the worn look by `LookDocument` and kept only when the reader took it with no note; a refused one changes nothing and its note is the answer, and the others in the call stand. What is kept is worn at once. `topo look reset [<part.field> …]` takes fields back, all of them with none named. It takes a field or a part as the reader knows them (`LookDocument.place(of:)`, which asks the reader itself), and refuses a path inside a compound field (`mascot.pin.x`), which is set and taken back whole.
- `topo reminders`, `topo calendar`, `topo notify`, `topo contacts` and `topo location` (`Apps/Topo/Tools/`) reach the person's own data through EventKit (one `EKEventStore` for both, `EventKitStore`), `UNUserNotificationCenter`, `CNContactStore` and Core Location, each behind a protocol a suite fakes. Reminders are listed, added and marked done: `topo reminders` with nothing after it lists the ones with a due date, soonest first, whole lines up to 24 KB (`RemindersTool.budget`), then a line counting the later ones that left out and a line counting the ones with no due date, each only when it has something to count, so the call an agent reaches for first is bounded, while `--all`, `--list`, `--due-before` and `--done` are each answered whole, whatever their size; events listed in a span (a week from now unless named, a calendar year at most) and added, an all-day one running from `--start`'s day through `--end`'s; notifications scheduled now, at a time or after a span, and Topo's own (ids `topo-…`) listed and cancelled; contacts searched by name, number or address and shown, read only and with no note (its key needs an entitlement); the location is one fix from `CLLocationUpdate.liveUpdates()` with its accuracy, whether it is approximate, and a place line: the place the vault's `places.json` names when a precise fix is within its radius (the nearest centre when within several; `docs/memory.md`), as `place home (3147 Geary Blvd) — nearest address …`, and otherwise `place (nearest address) …`, the address being `CLGeocoder`'s if one comes within five seconds, marked because its house number is the geocoder's nearest guess. An approximate fix is inside no named place. What `places.json` named and did not get follows as up to three `note places.json:` lines and a count of the rest. Nothing deletes or edits a record; marking a reminder done is the one change to one that exists. Output is one record a line, id first (the bare `topo reminders`' counting lines aside), fields apart by ` | `, a field's own line breaks said as spaces; a list or calendar is listed as its id and `Title (account)`, and `--list`/`--calendar` take the id, `Work (iCloud)` or `Work`, read every way at once — a name that fits more than one (two share a title, or one's title is another's `Title (account)`) is status 2 listing each with its id, never the first EventKit returns; `list` and `cancel` are `topo notify`'s forms, never a notification's title; dates are ISO 8601 in the phone's time zone (`ToolDates`), options `--name value` (`Arguments`), where a value never starts with `--` (`--notes=--x` says one that does), and an option one form of a tool takes is refused by its other forms rather than ignored. `EKEventStore` and `CNContactStore` are reachable only through `Confined`, whose closures run on a serial queue of its own, so their synchronous fetches and saves never run on the cooperative pool. An all-day event is saved as EventKit holds one, ending on its last day's last second, and read back as midnight to the midnight after. `PhoneToolsTests` runs the calendar and contacts tools against the simulator's own stores too, with access granted by `simctl privacy` before the suite (a step of the PR check's unit job).
- `topo log` (`Apps/Topo/Tools/LogTool.swift`) answers the app's own lines from the unified log, so what the app did around a stall or a banner can be read from inside: `OSLogStore` scoped to this process (`UnifiedLogReader`), held to the subsystem `zone.hexagon.topo`, behind `LogReading`, which `LogToolTests` fakes. `topo log [--since MINUTES] [--category NAME] [--grep TEXT]` answers the last 10 minutes unless `--since` names 1 to 1440, oldest first, one line each: the time to the millisecond with the phone's offset, the level (`debug`, `info`, `notice`, `error`, `fault`), the category and the message, a message's line breaks said as spaces. `--category` keeps one category (`resident`, `audio`, `perf`, `dns`, `models`) and `--grep` the lines whose message holds the text, both whatever the case. `resident` is where `GuestResident.log` writes in every build: the session's starts and exits, each trip to the background and its outcome, and the API proxy's and the tool service's lines, which start `proxy:` and `tools:`; each goes through `GuestResident.redacted` first, since a line can end in Claude Code's own last words. It asks for no permission and changes nothing. The lines are this launch's, since the store is the process's own, and the widget and control extensions' lines are not among them, being other processes'. An answer is at most 24 KB: the newest lines whole, under a first line starting `…` that counts the ones left out; a line too long to fit alone is left out and counted, and the lines before it are still kept. The store's read blocks, so it runs on a queue of its own, and its predicate carries the date as well as the subsystem: a store of this scope takes no position, and without the date a read is of every line of the launch. What it answers is whatever the store composes, and nothing redacts it: a value logged `privacy: .private` reads back whole from the process's own store on the simulator (`testAPrivateValueIsNotPrivateFromTheProcessesOwnStore`), so a privacy marker is not what keeps a value from the guest. What keeps a secret out of an answer is that the app logs none: every line it writes is one the rules above already keep tokens, arguments and tool output out of.
- `topo maps` (`Apps/Topo/Tools/MapsTool.swift`) asks Apple Maps, through MapKit, for places, a route and a travel time, behind `MapsStore` (`MapKitMaps` on the phone, a fake in `MapsToolTests`). It changes nothing of the person's and reads only where the phone is, opens no other app and draws no map (`scripts/tests/maps-opens-nothing-test.sh` fails on a source of it holding `openInMaps`, `openMaps`, `UIApplication`, `openURL`, `maps://`, `maps.apple.com`, `MKMapView` or `MKLookAroundScene`, but for `MapsLink.swift`, which is let `maps.apple.com` and nothing else on the list), and logs nothing; what it sends goes to Apple's servers: the search text and its region, both ends of a route and, for `here`, where the phone is. `search QUERY` (one argument) answers a `region` line — `here`, `near` or `none`, the centre, the radius in metres, `exact` or `approximate`, the query — and then one place a line, numbered: name, category, address, `LAT,LON`, metres from the region's centre, phone, URL. The region is around the phone unless `--near LAT,LON` gives a point or `--anywhere` lifts it, `--radius` is 100 to 50 000 m (5 000 unless given), the region a square reaching that far each way round a centre between latitudes −85 and 85 and `--limit` 1 to 25 (10 unless given); a `--near` nearer a pole is status 2 and a phone there status 1, each pointing at `--anywhere`, since a span of longitude makes no square there; from iOS 18 MapKit is held to the region (`regionPriority`), and before it the region is a hint MapKit may ignore, which the distance shows. `route --to END [--from END] [--by walking|driving] [--depart DATE]` answers a `route` line (both ends, the mode, metres, seconds, departure, arrival, the route's name), up to 5 `notice` lines, and one step a line, numbered, with its metres: one route, never alternates, 40 steps at most. `eta` takes the same and `--by transit` too, and answers one `eta` line. Each answer's second line is `link | URL` (`MapsLink`): the same search (`?q=` and, with a region, `&sll=` its centre) or the same directions (`?saddr=&daddr=&dirflg=` `w`, `d` or `r`) at `https://maps.apple.com/`, which the chat draws as a link the person can tap, so leaving Topo for the map, turn-by-turn or a transit route is their tap and never the tool's. A `--from` that was `here` is left out of it, so Maps starts from wherever the phone is when it is tapped; a `--to` that was `here` is the fix. A link is written whole or not at all: one past 800 bytes (a very long query) is left out. `--from` is `here` and `--by` is `walking` unless given; a departure has a time of day. An end is `LAT,LON` — two plain decimals, latitude −90 to 90, longitude −180 to 180 — or `here`, never a name: a name is status 2 saying to search first, so no end is the first of several matches. `route --by transit` is status 2 pointing at `eta --by transit`, since MapKit gives apps a transit time and no transit route, and offering that route's link in Maps when `--to` is a point. Only a call that needs where the phone is — `here`, or a search with neither `--near` nor `--anywhere` — reads or asks for Location (`PhoneTool.run`'s per-call authorizer), under the same broker key as `topo location`, so the two share one prompt; refused, it is status 5 with a line saying how the call runs without it. The fix is `CoreLocationLocator`'s with no place asked of the geocoder (`MapsTool.standard`), waited on for 10 s; with none by then the call is status 1 naming what its verb takes instead: `--near LAT,LON` or `--anywhere` for a search, `--from LAT,LON` and a coordinate `--to` for a route or an ETA. Every field keeps its place on the line, an absent one empty; a field's line breaks are spaces and its bars slashes, and it is cut with `…` at 200 characters or 800 bytes, between characters (the link is not a field of this kind: it is whole, at most 800 bytes, or left out); coordinates are five decimal places, distances whole metres, times whole seconds, and a number that is not one is an empty field. An answer is at most 24 KB: records are written whole until the next would pass the budget less the last line's room, and a last line starting `…` counts what the caps and the budget left out. Each MapKit request is made by `MKMapRequests` behind `MapRequestRunner`, with MapKit's completion handlers and on the main actor, never a blocking wait; `MapKitMaps` waits on it for 20 s and cancels it at the bound and when its call is cancelled, without waiting for it after, since `MKDirections.cancel()` never calls its handler. A search that finds nothing (MapKit's placemark-not-found with no directions code) is the region line and its link with no place after them, status 0; no route between the ends (MapKit's directions code 16 on `calculate()` and 1 on `calculateETA()`, or a not-found with no directions code), a throttled request, a server failure, a request past its bound, and any other failure in MapKit's own words are each status 1 with their own sentence.
- `topo home` (`Apps/Topo/Tools/HomeTool.swift`) reaches the person's HomeKit home through one `HMHomeManager`, behind `HomeStore` (`HomeKitStore` on the phone, a fake in `HomeToolTests`). With nothing after it, it lists every home, primary first, and in each every accessory by room, one a line: id, room, name, category, whether it is reachable, and each service's writable characteristics, with the value of power, brightness, hue, saturation, target temperature and lock read from a reachable accessory (each read bounded at 4 s, and one that fails or is late is `?`). `get ID` is one accessory: every characteristic with its id, short name (`power`, `brightness`, `target-temperature`, or its own description hyphenated), value (every plain characteristic's value: a TLV8 or data one shows only its format), what it takes and whether it can be set. The listing names as settable only characteristics `set` writes. `set ID CHARACTERISTIC VALUE` writes one characteristic of one accessory, named by its short name or its id, where a name more than one of the accessory's services carry is status 2 naming each id; the value is judged against the characteristic's metadata first — read only, a name (`name`, `configured-name`: HomeKit may let one be written, and `topo home` renames nothing), a format other than bool, integer, float or string, a value of the wrong kind, outside its minimum and maximum, off its step, not among its valid values when it names some (on top of the range and step, not instead of them), or a `uint64` past `Int.max` (which also reads as `?`) is status 2 saying what it takes — the range, the step and those of the valid values they allow, never the refused value — with nothing written. A switch is judged as 0 and 1 against the same metadata, a string by its length, the only bound HomeKit gives one, and bounds, steps and valid values are compared as `Decimal`, exactly for every whole number — and the answer is the value read back. `scenes` lists the action sets and `scene ID` runs one. An id may be any start of it that fits one thing; one that fits more is status 2 naming each. Nothing adds, removes, renames, pairs or unpairs anything. The manager is made by the first call that needs it (`HomeAccess`), since making one is what raises HomeKit's prompt, and it knows the permission only after that: until then the permission reads as never asked, and the call that asks makes the manager and waits for its delegate to say the person answered (a status of determined or restricted; homes loaded while it is undetermined do not end that wait), then for HomeKit to load the homes, since a read before that is empty and would say there is no home; a status that leaves authorized (access revoked in Settings) forgets the homes it loaded, so after access is given back the next call waits for a fresh update. The wait for the homes ends when the call is cancelled, and the wait for the answer is the broker's one prompt, which the service's bound answers, and the write and the scene each check for cancellation just before they are made. An empty list once loaded is status 1, no home set up on this phone. HomeKit's reads, writes and scenes answer on blocks, awaited through continuations, and the delegate's callbacks hop to the main actor. Its switch is under Settings › Privacy & Security › HomeKit, which a refusal names. It needs the `com.apple.developer.homekit` entitlement (`Apps/TopoiOS.entitlements`) as well as its usage string.
- `topo photos` (`Apps/Topo/Tools/PhotosTool.swift`) reaches the person's photo library through PhotoKit, behind `PhotoLibrary` (`PhotoKitLibrary` on the phone, a fake in `PhotosToolTests`), with one permission for all of it, read and write access to Photos, which a library the person limited to chosen photos satisfies: a list from one opens with a line saying so and an id it does not find is answered as not among the chosen photos, and `PHPhotoLibraryPreventAutomaticLimitedAccessAlert` keeps the system's own sheet for choosing more from coming up at a read. `albums` lists the person's albums and the system's that hold anything (Screenshots, Favorites), 100 at most out of at most 300 collections of each sort read, each with a count of its photos that reads none of them; `search` answers photos newest first by album, a span of dates, `photo` or `video` and favourites, 20 unless `--limit` names up to 50, each fetch limited to one more than it shows, and takes no words, since PhotoKit searches by nothing a photo shows. `export ID` asks `PHImageManager` for one asset at 2048 px on its long side (a video's first frame), bounded at 30 s with the request cancelled at the bound or with the call, a photo kept only in iCloud brought down for it, and writes it as a JPEG to `/home/topo/photos/<the id's UUID>.jpg`, where the mind reads it as an image; `save PATH` reads a PNG, JPEG or HEIC of at most 20 MB as the guest reads it (`Guest.contents`, so a path in the memory goes through the vault's filesystem) and adds its bytes as they are as one new photo. That is the only write: no asset is changed, deleted, favourited or moved between albums. PhotoKit's change cannot be called back, so a save under way when the service's bound passes still adds its photo, as an EventKit save does. The fetches are synchronous and run on a queue of the library's own (`Confined`), as does the JPEG's encoding. The export is written by `HomeFile` (`Apps/Topo/Tools/HomeFile.swift`): a descriptor walked down from the home one name at a time with no link followed, and the file written under a hidden name and given its own with a hard link, which is made only where nothing is, so a link in the guest's home sends the app's write nowhere outside it, an export never writes over a file and a write cut short leaves nothing under the name; a second export of one photo answers the path already there.
- `topo files pick` (`Apps/Topo/Tools/FilesTool.swift`) puts the phone's file picker over the app (`DocumentPicker`: `UIDocumentPickerViewController` asked for a copy, so nothing of the person's is opened in place and no grant is kept) and copies the one file the person picks into the memory, at `inbox/` or the folder `--into` names, relative, with no `.`, `..` or hidden name. It asks for no permission, since the pick is the person's consent to that one file. A call made while the app is not on the screen or is between two screens, or while a picker is already up, fails at once saying so; a picker closed without a choice fails saying so; the person has 60 s, after which the picker is taken down, whether or not it ever reached the screen, and a call cancelled at the service's bound takes it down too. A choice that arrives after its call was answered has its copy removed. A file is 20 MB at most, and a file that is UTF-8 text 256 KB at most, the tool's own line, drawn because the mirror carries a text file to the store whole as one note (`docs/memory.md`). The app does not write the memory's folder itself: `GuestVaultDrop` writes the file into the guest's home (`.topo/picked/`, through `HomeFile`) and a short program in the guest (`VaultPlacement`, in `TopoUserland`) copies it into the memory's mount (`/memory`, `ClaudeLauncher.vault`) under a hidden `.topo-pick-<pid>.part` name, the copy bounded at 20 s, and gives it its own name with a hard link, so the folder's only writer is the vault's filesystem with its coordination, a copy cut short leaves nothing under the file's name, and a name already taken is refused with nothing written over: a link is made only where nothing is, so a file the mirror or another device puts at the name while the placement waits for it stays as it is, which a rename would have replaced. The name is given only within 65 s of the call's start, so that with one wait of the vault's (20 s) it is given or refused inside the service's 90 s bound, and a pick too late for that fails with nothing kept. The program does nothing unless a vault is mounted there (`/proc/mounts`), since after an unmount the path is a bare folder; the home's `memory` is a link to the mount and not the mount. The size that landed is read back before the call answers, and the copy in the home is removed; a copy a killed call left in the home is removed by a later pick once it is ten minutes old. In the memory's folder the program removes its own hidden copy as it ends and nothing else, since a name cannot say who made a file: a copy left by a program that was killed stays, hidden, where the mirror does not read it. A memory not mounted in the guest (`VaultMount.standing`) is a failure with nothing kept. `GuestVaultPlacementTests` runs the program in the booted guest against a vault mount.
- `topo widget` (`Apps/Topo/Tools/WidgetTool.swift`) writes the person's widgets: a slot's layout document, judged by `WidgetDocument`'s reader and each `run` action by the allowlist and its tool's own reader, an image copied from under the home, clearing slots, and the taps the person made. It is `docs/widgets.md`.
- `topo control` (`Apps/Topo/Tools/ControlTool.swift`) sets up the person's Control Center, lock-screen and Action-button controls: a slot's document, judged as a widget's with each `run` by the same judge, a toggle's state, the defaults written back, the secrets a request names (kept in the device keychain; the value is an argument on the wire, which logs none), and the controls' taps. A control's `request` is made by the app, not the guest. It is `docs/widgets.md`'s *Controls*.
- Each of those reads its arguments into a call first, so a call the tool does not take is status 2 and asks nothing; then it asks for its permission through one `PermissionBroker` on the first call that needs it and at no other moment, so a launch asks for nothing: granted goes ahead; never asked puts up the system's prompt, one prompt however many calls wait on it (a system alert makes the app inactive, not backgrounded, so the resident runs on under it, and the call's 90 s bound is how long it waits); refused, or write-only calendar access, is status 5 with where in Settings to allow it (Apps › Topo, or Privacy & Security › HomeKit for HomeKit), and restricted is status 5 with where in Settings the restriction is lifted, never an empty answer. At the bound the service cancels the call: one whose prompt is answered afterwards does nothing (the answer stands for the next call), and an EventKit save checks for cancellation just before it is made, so a call answered status 4 adds nothing unless its save was already under way. The usage strings are `INFOPLIST_KEY_*` settings on the iOS target, and `scripts/check-built-plist.sh` reads them off the product (`scripts/tests/check-built-plist-test.sh` holds each missing or empty one red), since a request with no string ends the process. The same script reads the HomeKit entitlement off a signed product's signature, and says so rather than passing when the product is unsigned, as the PR check's device build is. The app delegate is the notification centre's delegate so a notification that comes due with the app in front is shown.
- `topo github` (`Apps/Topo/Tools/GitHubTool.swift`) says whether GitHub is connected and as whom; `topo github token` answers the token and `topo github credential` git's `username=` and `password=` lines, or status 1 saying where to connect. It reads the keychain on every call, on a queue of its own, and keeps nothing (`docs/auth.md`, *Connections*).
- `topo secret` (`Apps/Topo/Tools/SecretTool.swift`) reads the vaults 1Password's service account reaches: `vaults`, `list [VAULT]` (id, title, category, vault), `show ITEM VAULT` (the vault is not optional, since a service account is refused an item without one; what one item holds: an `item` line, then a line for each field — label, type, purpose, section — and each file — name, size — ending in the reference `get` takes where `op` gave one, a file's by the ids of its vault, item and file, which reach it whatever its name holds) and `get`, which is one value by `op://VAULT/ITEM/FIELD`, or by `op://VAULT/ITEM` the text of the item's one file, exactly as `op` gave it; an item with several files is status 2 naming each, and one with none status 1. Each is a read — `op vault list`, `op item list`, `op item get`, `op read`, the one-file `get` being an `item get` and then a `read`, not made if the request was cancelled between them — and nothing else is ever asked of `op`; a reference has two to four non-empty parts and no line break, and an item's name follows `--`. `show` withholds every value by construction: what `op item get` prints is decoded into a type (`SecretTool.Item`) with no property a field's value, a one-time code, a URL or a password's history could land in. A file comes back as text, since a guest command's output is a string: one that is not UTF-8 is not whole. The token is never an answer: an answer of `op`'s holding it — a field whose value is the token, or an item `show` was asked for that holds it in any field — is refused whole. Every request runs through `SecretRequests` (`Connections.secrets`), which a clear of the token also runs through — a sign-out's, a takeover's, a demotion's, Disconnect's: under one lock a request is let in only while no clear runs and no refused clear stands, and a clear cancels every request in flight before it starts, which ends its `op`; a request cancelled answers that it was stopped, never what it read. So a request answers wholly before a clear or not at all, and a sign-out does not wait on one.

In the guest, `topo` is a bash script (`GuestTools.script`) carrying its arguments to the service with the rootfs' own BusyBox `wget` and printing the answer with its status; nothing is added to the rootfs for it. A refusal and a service that is not there are its own status 3, each with one line, never the token. It and its skill (`GuestTools.skill`, whose description names the look and the widgets and whose body points at `topo help`) are written under the home on every start (`.topo/bin/topo`, mode 0755, and `.claude/skills/topo/SKILL.md`, where Claude Code reads a user's skills), so they are always this build's, and `topo` is linked at `/usr/local/bin/topo`. `GuestResident.prepareTools` does all of it once per process, the home's mount included, for the resident and for a `TOPO_DEBUG_USERLAND` launch alike, so a debug command can call a tool (`userland: tools on …` says where).

Two shims beside it hand GitHub's token to one command at a time, so it is never in the resident's environment or a file the app writes: `git-credential-topo` (`GuestTools.credentialHelper`), which git asks for an `https://github.com` credential because the tools environment names it through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (no `.gitconfig` is written) after an empty helper entry, which clears every helper configured before it — git hands a credential it used to every helper on its list, and a `credential.helper store` in the home would write the token to `~/.git-credentials` — answers what `topo github credential` says and nothing for any other host, and says on stderr why when the app has none to give — not connected, the keychain unreadable, or the app not answering (`topo`'s status 3); and a `gh` wrapper (`GuestTools.gh`), which runs `/usr/bin/gh` with `GH_TOKEN` from `topo github token` in that process's environment, leaves a token the caller set alone, and says `apk add github-cli` when gh is not installed; when the app gives no token it says why and does not run gh at all, since gh would fall back on a login of the guest's own, which can be another account's and outlives a disconnect. Both are written under `.topo/bin` on every start and linked into `/usr/local/bin` (`GuestTools.links`), ahead of `/usr/bin` on the path, through `Guest.linkCommand`: those paths are the app's, so a regular file something in the guest left at one (a `gh` script the mind wrote before the app had its own) is removed and the link made in its place, while a directory there is never removed and the start fails naming it. Every guest process inherits `TOPO_TOOLS_TOKEN`, so anything in the guest can ask for the token while GitHub is connected (`docs/design.md`).

1Password's `op` runs in the guest, started by the app and never by the mind (`Apps/Topo/OnePassword.swift`). It is 1Password's static `linux_arm64` build, one more manifest entry (`op-cli`, 1Password's zip, with the `op` inside it pinned as the entry's `binary`), fetched only when a token is first checked. `OnePasswordInstaller` has the guest's own BusyBox `unzip` extract `op` into `Application Support/Userland/op-cli` (outside the downloader's homes, whose sweep would remove it), mounts that at `/opt/op-cli`, and makes the binary executable only at its pin; it is not linked onto the path. The pin is a check of the download, once per process, and bounds nothing in the guest. `GuestOnePassword` installs it — a check walked away from stops waiting for the install at once and runs nothing, while the install goes on for the next connect — then runs it through `OnePasswordRun`: `/opt/op-cli/op` under `/bin/sh`, with `OP_SERVICE_ACCOUNT_TOKEN` in the environment (never an argument, so no `/proc/<pid>/cmdline` holds it, and never the resident's), `OP_CACHE=false`, and `OP_CONFIG_DIR` and `TMPDIR` a directory made for the call and removed after it; `op`'s standard error comes back with the token replaced. The token is in the environment of every process of the call: the shell, `op`, the helpers the shell runs (`cat`, `cut`, `mkdir`, `sleep`, `kill`, `rm`), the watcher that bounds `op` at 60 s and leaves once the shell is gone, and what `op` starts. Under iSH `op` starts a daemon whether or not caching is off — `op daemon`, under a launcher in a session of its own, reparented to init, carrying the token — and writes its pid to `com.agilebits.op.<uid>/op-daemon.pid` under `TMPDIR`, sometimes only after `op` has returned. So when `op` returns the shell polls that file for up to 5 s — an empty file is one not yet written, and the directory may not be there yet — then ends the daemon, every process in its session and every child of it, and every other process in its own process group, sweeping each task's `/proc/<pid>/stat`. With no pid by then it finds the daemon by its arguments instead — every `op daemon` in the guest (or `<command> daemon`, as a test's stand-in runs itself) — which can only be this call's: one run of `op` is let in at a time (`OnePasswordRun.turn`), in the order they came, and a caller cancelled while it waits stops waiting. A cancel — Cancel, Disconnect, a sign-out, a takeover, a demotion — does the same from outside through a file holding the shell's group id, its 5 s of polling counted from the cancel rather than from `op`'s return; one that lands before that file exists leaves a mark the shell reads after writing it, so either the shell runs nothing or the cancel finds the group. After every call the app does the same for a shell that did not reach its own end — SIGKILLed by another guest process — and removes the call's files; after a wait that threw it runs the cancel instead, so a shell still running either stops at its group file or has its group ended. `Guest.run` throws only when the spawn failed or after the shell has exited, so there the cancel finds nothing running; the mark is a defence for any other `GuestRunning` whose wait could fail with the shell still starting. What that leaves: a daemon not yet started when that sweep runs, 5 s after `op` returned, outlives the call; a cancel's mark that lands after the call's files are removed — a cancel racing the call's end, or the cancel after a wait that threw once the shell had gone — stays in `/tmp` as an empty `<group>.cancelled` until the next launch empties it (`Guest.clearTemporary`); and while a killed shell's `op` holds the call's output the call waits for it, up to the watcher's second after the shell is gone. The token is not kept, and that is all the run promises: a guest process can take it while `op` runs. iSH's `/proc/<pid>/mem` reads and writes any task's memory with no permission check (`fs/proc/pid.c`), environment included, so the guest having no `/proc/<pid>/environ` protects nothing; the guest can `umount` `/opt/op-cli` (`patches/ish/0004-guest-mount-real-refused.patch` refuses a realfs `mount`, not `umount2`) and leave its own `op` beneath it, or replace the binary in the directory it is mounted from, which the guest can write; and the script finds `mkdir`, `sleep`, `cat`, `cut`, `kill` and `rm` on a path the guest can write to. A token so taken outlives a disconnect until the service account is revoked in 1Password (`docs/design.md`).

`swift test` in `Packages/TopoProxy` runs the service's suite (`TopoToolsTests`: the refusals, the loopback bind, the log, the bound, the arguments); the forwarder's is `DNSForwarderTests` in `TopoProxyTests` (every bound, the loopback bind, the completion and negative rules, the log of counts, no cache, over a scripted resolver); `GuestToolScriptTests` in `TopoUserlandTests` runs the script itself in the booted guest against a service in the test process; `LookToolTests` in `TopoTests` holds the look tool to the reader.

## The resident process

Claude Code runs in the guest as one resident process, and it is what answers the chat. `GuestProcess` (`Packages/TopoUserland/Sources/TopoUserland/GuestProcess.swift`, from `Guest.spawn`) is a guest program with stdin a pipe, stdout an `AsyncStream` of lines as they arrive, a 16 KB tail of stderr, and `terminate(within:)`, which `SIGKILL`s every guest task but init — the guest runs the one program and what it starts, and a descendant orphaned to init mid-teardown is reached by no parent link — kills again whatever of it is still running (and anything started since), and answers once the process is reaped, no descendant is running, both pipes are closed and every walk of the tree was made whole — or at the bound, saying which did not happen, how long it took and one line about each task still there; every blocking read, write and wait is on a queue of its own, never the cooperative pool.

`StreamJSON` is the parser, a pure function from one stdout line to typed events (the session and model from each `system/init`, a text block with the id of the message it is a block of, a tool call by name, with the file for a tool that writes one (Write, Edit, MultiEdit, NotebookEdit: `StreamJSON.fileTools`), a tool's result with its text and whether it was an error, a thinking block, usage with the context as input plus both cache counts, the result, anything else named `type/subtype`, and a line that is not an event kept as malformed), and the writer of a turn as one line. A sub-agent's line (`parent_tool_use_id` set) makes no text, no `writing` and no `writingBegan`, and a message Claude Code wrote in the model's place (`isApiErrorMessage`, the `<synthetic>` model) makes no text: neither is the reply's words, which is the same reading `GuestTranscript` makes of the transcript.

`GuestSession` is the actor that owns the resident `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` (`ClaudeLauncher`: `sh -c` moves into the home and `exec`s Claude Code, so the pid held is Claude Code's; permissions bypassed, `--dangerously-skip-permissions` with `IS_SANDBOX=1`, which Claude Code needs to bypass as root and the guest runs everything as root, because the guest is the sandbox and what the mind can reach is the holes poked in it — the mounts, the proxy — never a prompt inside it (`docs/design.md`); the environment is the guest's with `HOME` at `/home/topo`, a bind mount of `Documents/home`, and the proxy's base URL and the guest's token read at each launch, and the tool service's URL and token; the memory told to it with `--append-system-prompt` (`ClaudeLauncher.memoryPrompt`: where the vault is and how to write in it when it is mounted, that nothing written there is kept when it is not — an argument, so nothing the resident starts inherits it), which is the session's own and fixed at launch, so `use(memory:)` replaces a process told otherwise as a change of model does; and `--model` the session's current model, which `use(model:)` replaces by ending an idle process and starting one on the new model, resuming, and by doing that once the turn in flight ends when one is).

One turn at a time — a second send is refused, and so is a send with nothing resident; a send to a process started on a model or conversation the session no longer says replaces it first, and one to a process being replaced waits for the replacement, so no turn rides the old model — and its updates are the events then how it ended: answered, failed (an error result, which keeps the process; the process exiting, with its stderr; silence past the turn's bound, 180 s from the last line; a write that failed) or abandoned. Every failure but an error result ends the process and starts another, resuming, and nothing the old one says afterwards reaches anybody; a turn is never sent twice. A turn is sent with a uuid (`send(_:id:)`, the stream-json line's `uuid`), which Claude Code keeps as its transcript entry's.

The session to resume is the one the last `system/init` named, kept in `Documents/.guest-session`; a resume that exits before it begins anything clears it and starts a fresh session, and says so in the log; `forgetSession()` (sign-out) clears it, makes the next process fresh and ends the resident process at once — or the one still starting, as it lands — and returns once that end has answered, abandoning a turn in flight rather than waiting for it as a change of model does, since the process holds the login that went (its token in its environment) and a turn left running would run its tools and write that session's transcript for nobody; a process started before it never writes the session it names back (`keep` is gated on the conversation the process was started under).

`GuestLifecycle` carries the app's lifecycle to it, each foreground and background a generation the session admits only if it is the newest, so a start or a teardown still pending never acts on the wrong process: the foreground starts the process (or keeps it, when the app is back before the teardown began); `DidEnterBackground` begins a background task, reads `backgroundTimeRemaining` a second later (it is infinite inside the notification), and gives a turn in flight the grant less the 5 s the expiration handler fires with and the 8 s kept for the teardown (`GraceBudget`; 28 s is assumed when the reading is not a grant), then ends the process — at once when no turn is in flight, abandoning a turn still running at that point — with 7 s for the termination to be confirmed, and ends the task when the termination answers: confirmed, or at that bound unconfirmed, logged as `NOT confirmed` with each task still there. The task is not held past the bound, since holding it past the grace gets the app killed. The expiration handler does not end the task itself: it asks the session to expire — a teardown waiting on a turn stops waiting and ends the process, and a termination begun from then on has 4 s — and holds the task, which is ended when the teardown answers, or 4.5 s after the handler with the teardown still running and `background: background time ran out…` logged.

The memory's folder is mounted at `/memory` (`ClaudeLauncher.vault`) and linked from the home as `/home/topo/memory` (`ClaudeLauncher.memory`), so it is `memory/` from the resident's working directory. Beside the home rather than inside it, because the fork's mount lookup keeps the last mount it found per thread and answers a path under a mount nested in that one with the outer mount, which would put a note in the home's own folder under the link's name. `VaultMount` (`Apps/Client/VaultMount.swift`) keeps it in line with the home `Memory` names (`GuestResident.memory`, set by `TopoApp`): `reconcile` is asked when the session is made (its answer is what the first process is told) and for every turn, when it is readied (`ResidentConversation.ready`) and again when it is sent (`MemoryTurns.send`), each answer going to `GuestSession.use(memory:)` so a turn goes to a process told what the mount is now, never by a launch, and compares the folder by its device and inode, not its path, since a folder removed and made again at the same path is another folder and a mount's descriptor is on the old one. The local home's folder is made when it is not there yet; an iCloud Drive home is mounted from the vault folder, with access started on the URL the grant is on and held for as long as the mount stands; a lost home, or a vault folder that is not there, mounts nothing; and a home whose `memory` link cannot be made — the guest has put a folder of its own at that name — is a memory the resident is told it cannot reach, the mount left standing and the link tried again at the next reconcile. A mount that has to go and cannot, because something in the guest holds it, refuses the turn as not ready with that reason, before the guest receives anything. A move of the memory (`Memory`) and a turn are never in flight together: `MemoryTurns` is the memory's `VaultWriter`, so a move waits for a turn being sent and for the turn in flight to end before it reads the folder, and a turn sent meanwhile waits until the home has moved and is sent into a mount of the new one. A note a turn writes is therefore in the old folder before the move carries it, or in the new one. Sign-out waits for the resident's end (`VaultMount.forget(after:)` around `forgetSession`), then takes the mount away and then stops the access; a mount a teardown that did not confirm still holds is marked stale, its access stopped, and taken away at the next reconcile.

`GuestResident` (`Apps/Topo/GuestResident.swift`) puts these together over the app's notifications; a start of it that fails (the proxy not binding, a mount refused) is not kept (`StartOnce`), so the next turn's start tries again from the step that failed, while the kernel's own boot stays once per process.

A debug launch with `TOPO_DEBUG_GUEST_TURN=<turn> || <turn>` (`DebugRun.guestTurn`, refused beside `TOPO_DEBUG_USERLAND`, since the resident's end ends every guest task) sends the turns one after another to the one resident process and prints each turn's model, session, the resident process's guest pid, tool calls and each one's result (`tool result: <tool>: ok|error: <text>`, paired with the calls in the order they were made, on one line, cut at 300 characters, any `sk-ant-` key, `Bearer` value or token variable redacted), each pose Topo takes on the glass, reply and wall time as `[topo-debug] guest turn N …`, the session's log (the start, a resume, each teardown and its termination) as `[topo-debug] guest: …`, and `guest turn done`; `scripts/simulator-run.sh --guest-turn` asserts on those (`docs/simulator.md`).

## The bridge

The chat's brain is `GuestBridge` (`Apps/Client/GuestBridge.swift`), a `Brain` over a `GuestConversation`: in the app `ResidentConversation` (`Apps/Topo/GuestResident.swift`), the one `GuestSession` that `GuestResident` starts, and in the suites `ScriptedGuest` (`Tests/Client/ScriptedGuest.swift`), which writes Claude Code's own transcript format. Until the rootfs and Claude Code are both on the phone nothing starts, and a turn is refused as not ready with the userland's status line: the person's turn stands in the log, the chat shows the line, and the answering loop, which warms the guest on each pass, answers it once the guest is ready.

The reply the bridge hands the runner is the words of every assistant message of the turn, the ones said before a tool call included: it gathers each text block by its message through `ReplyWords` (`Packages/TopoUserland/Sources/TopoUserland/ReplyWords.swift`) — a message's blocks run on, a message with no words adds nothing, one message's words are parted from the next's by a blank line — and writes that, once, under the turn's nonce, when the turn ends. The result line's own text, which Claude Code fills from the last message alone, is written only for a turn whose stream carried no text. The row drawn while the guest writes (`Harness.writing`, `docs/harness.md`) and the reply read back from the transcript after a crash (`GuestTranscript`) are built by the same function, so the three hold the same bytes; tool calls, their results and thinking are in none of them. `GuestBridgeTests` holds it over a scripted turn of a message, a tool call, a tool call with nothing said and a message, whose result line carries the last message alone: both messages land with one blank line between, the row comes to the same bytes before the reply lands, a process that exits before its result line is answered from the transcript with those bytes, a reply whose append was refused is written by the next launch from the transcript under the original nonce, and a turn with a result line and no text event writes the result's text.

The guest keeps its own conversation, so it is told only what it has not seen: the person's words, after the turns of the log it was never given (a limb's turn, another primary's reply, a late branch whatever its timestamp) as a block of what happened meanwhile, or, for a session that has seen nothing (the first, or a fresh one after a resume failed), the last `contextLimit` (40) turns as the conversation so far (`GuestBridge.render`). The limit is a fresh session's alone, whose older turns are its history and are counted seen without being told; a session that has seen the log is told every turn it has not seen, however many, and an input covers exactly what it told, what an input the log moved past carried, and the turns it answers.

What it has seen is graph coverage — per-device runs of sequence numbers (`Coverage`), not a point in time — kept in the ledger, `Documents/.guest-bridge.json` (`GuestLedger`), beside the session it belongs to, and advanced only when the reply is in the log (`landed`), and then only over what the guest is known to have received — it answered the input, or read it and was cut off: a reply another device wrote under the nonce, for an input whose fate here is not known, settles the request and counts nothing seen, so those turns go with the next input rather than never; a different session id clears it. No ledger file is an empty ledger; one that cannot be read or decoded is not, since it may record an input the guest received: until it reads, every request is refused with that reason and nothing is sent, nothing is written over it, and each request reads it again, so a ledger unreadable at launch — before the first unlock, say — is read as soon as it can be. Sign-out removes it with the rest.

Before an input is sent the ledger records it (`Pending`: the uuid it carries, the reply's nonce and parents, the turns it answers and covers, the session, the time, and whether it is sent, answered by the guest, or unresolved); an input whose turn ended in an error result is unresolved without reading anything, since Claude Code said it received it and the process, still running, may still be writing its transcript; an answer that stops listening (its task cancelled) with the turn still the guest's concludes nothing and leaves the record as sent; after any other end but an answer, and before any later request, the bridge waits until nothing the guest is doing can still write about an input — no turn in flight, one nobody listens to any more included, and no process being ended (`GuestSession.settle`) — and, when the last process ended was confirmed gone, reads the guest's session transcript under the home for that uuid (`GuestTranscript`, `Packages/TopoUserland`: the input's entry, then the messages up to the next prompt; answered when the last message ended with `end_turn`, `stop_sequence` or `max_tokens` and holds words of its own, an error Claude Code wrote in the model's place being no reply; the reply is then the words of every main-chain message of the turn, the ones before a tool call included, built by `ReplyWords`), and one pure function decides (`Reconciliation.of`): never received, the record goes and the input is sent; answered, the reply is written under its nonce without asking again — before anything else when the log has moved on from its request (`owed`), and caught up with nothing sent when CloudKit already holds it under that nonce; received with no reply, the turn is unresolved, and a record already known received is never cleared by a later read that does not find the input (a transcript not written yet, or cleared away since); a process not confirmed gone, a transcript that could not be read, or a folder of them under `.claude/projects` that could not be listed (`unreadable`), is no answer at all, so the record stays, nothing is sent and the next request reads again; only no `.claude/projects` at all, or every folder listed and every file that could hold the input read, is not received.

An input can go ahead of its turn (`hear`, `docs/harness.md`, *A turn ahead of iCloud*). The reply's nonce and parents are the turn's ref's, which only the save assigns, so until then the ledger keeps the input under the person's nonce in `early` (`Early`: the uuid, what the input told, the session, the time, the state, and the answer's words once there are any), recorded before it is sent like any input. What it told is fixed when it is sent, from the log as the caller last read it, so nothing that reached the log afterwards is counted seen with it. The guest's turn on it is followed by a task of the bridge's own (`fly`), which holds the requests' one slot and concludes onto whichever record holds the input when it ends, by the rules above; the caller failing on iCloud, or going, does not stop it. `bind` turns the `Early` into `pending` once the turn is saved (the reply's nonce, the person's ref as parent and as the one turn more it covers); with another answered reply still owed the log it waits in `early`, bound, and takes `pending` when that lands. `answer` for a bound input waits for its turn's end and returns its words; anything but an answer is left to the reconciliation above. Nothing is given ahead over an input whose end is not known or that was cut off, nor to a session with nothing of the conversation in it and no read of the log to tell it; an input left `sent` by a launch that was killed is read off the transcript before anything else is sent. An answered record carries its words (`text`), so `owed` answers without the slot or the transcript, and a reply owed is written before the next turn even while the guest is on a later input. The ledger keeps the nonces of the turns last answered (`settled`), so words said under one are not given again by a launch with no read to show their turn in the log. When another device turns out to hold the lease, the harness stops words still on their way to the guest (`stopHearing`: a `hear` not yet sent sends nothing) and what the guest already has stays in `early`: should this device come to answer that turn after all, that input is its answer, and otherwise it goes as below, and an input from a session the guest has since left counts nothing seen when its reply lands. A request for one turn whose words are in `early`, unbound, binds them itself. A `hear` of words an outstanding input already carries, given ahead or asked, sends nothing. An `Early` whose turn a request shows already in the log — answered by another device, moved past, or one head of a fork — is counted received by the session that had it, with the input that request sends, and goes when that input's reply lands, its own reply unwritten. `withdrawn` removes one whose turn was never saved.

An unresolved turn is never sent again by itself, since it may have run tools: `answerPending` skips it, the chat shows it with an ask-again control under the transcript (`Harness.unfinished`, `Harness.askAgain`), and the person saying something new moves past it: the guest is not told the cut-off turn again, and what it carried counts as seen once the new turn's reply is in the log, with the rest of that input's coverage.

Requests go to the guest one at a time, and a request waiting behind the one that answered its nonce is handed the same words. The bridge reports each turn's start (with the resident's pid), updates and end to `Harness.onGuest` (`GuestActivity`), which is what moves Topo on the glass; a reply is read aloud through `Harness.onReply` as any reply is. The diagnostics screen's `Brain` row says where the guest stands (the userland, the process, its pid and model, how many turns it has seen of which session, a turn with it or cut off) and `Unfinished turn` names the one waiting to be asked again. A failure before the guest received the input is a failed turn the answering loop retries; one after is unresolved; the guest is the only brain, so neither is answered any other way.

Sign-out (`Harness.forget`), and the far end of a takeover (`Harness.demote`, since a viewer holds no login), cancels the turn in flight and the answering pass in flight — each pass is a task of its own for this — ends the answering loop, and forgets the ledger and the guest's session with the login. A demotion writes the line to the log as a limb's before it forgets, which waits on iCloud: it drops its runner and lease first, stops every word of the line still on its way to the guest, and holds the line as its own (`busy`) until it returns, so a pass or a send that runs meanwhile neither drains the line nor gives the guest any of it. An answer begun before it — waiting for the guest to be ready, or with its input already with the guest — records nothing, sends nothing and hands no reply to the runner once its wait ends: the bridge checks the login after every wait, before it records an input, before it sends it, once the guest's turn has ended however it ended, and after the transcript is read, and `owed` checks it after its read; and the runner checks its task immediately before the person's turn and each reply it appends, so words from before a sign-out are not written after it either.
