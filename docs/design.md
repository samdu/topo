# Buddy for Helen

A design page, not a build. The question: what would it take for someone like Helen to have what Sam has, without signing her data over to a company and without building it from scraps. Sam's constraints, stated 2026-09-04: not for profit, GPL, Helen is the spec, and the measure of done is whether she can set it up in an evening without him on the phone.

**Shape.** Limb and brain. The phone app is the whole thing on day one: sign into your own Claude account, harness on the phone, no always-on. The mind is an optional upgrade: a menu-bar Mac app bundling the Claude CLI and the channel servers, paired by QR code, and once paired the same app becomes a limb with inbox, schedules and messaging that work while the phone sleeps. No hosted tier.

**Pitch.** Indie Mac app (family) meets OpenClaw meets Plex, by way of HomeKit and EventKit: an open agent, packaged the way Plex packaged a home media server, with HomeKit's hub rule (works now, add a hub for the rest) and EventKit's manners (ask for access only when needed).

**Why the hub is a Mac and not a Pi.** It has Xcode: a mind with the keys to build its own limbs, as buddy-janitor does on buddybox. A hub owner can ask for a widget or a small app and have it written, built and installed on their own devices; a free developer account covers personal installs.

**Hard walls.** iOS has no read access to Messages and no silent send, so iMessage as a channel needs a Mac; on the phone the nearest things are the share sheet, Shortcuts automations on a message from a named contact, and notifications as the reply channel. A Mac sleeps with the lid shut, so the app must say when the mind is asleep and the phone's own harness covers the gap. Topo ships through the App Store so Helen can just download it, and that rules out other people's GPL code in any bundle (embedding it makes the whole app GPL, and any of its copyright holders can then object to store distribution, as VLC's did; code we own is ours to licence however we like) and makes downloaded code a review risk rather than a wall: Apple's rule is against downloaded *native* code, and code run inside an interpreter or emulator is tolerated (iSH ships with a package manager). The hub runs the real Claude Code on the Mac. The phone's first experiment is Claude Code installed into the emulated Alpine userland at launch, the same category as an apk install; it is the design only if a real turn is tolerably fast, since a big Node binary under emulation can be unusable. Either way the phone keeps a harness of its own as the fallback, because the downloaded binary is closed, updates on Anthropic's schedule, and can break under review. Memory, not CPU, bounds it: Node under Claude Code sits at several hundred MB and iOS kills background apps well before that, so the phone harness runs in the foreground or inside a background mode it legitimately holds. The only background handles that survive review are a scheduled background processing task (iOS runs it when it likes, typically overnight on charge), a silent push to wake for a specific event (rate limited), and a real audio session while a voice conversation is actually running. The design needs no more, because the hub is what stays awake.

**Reference.** OpenMinis (GPLv3) for the phone half. Its tools run in an embedded Alpine userland: on iOS an arm64 fork of iSH (GPL-3 with an App Store exception) under a shell executor, with some commands offloaded to native frameworks; on Android a PRoot chroot (GPL-2). Design reference only; if Topo's phone harness wants a shell, it links iSH under its exception or a permissive alternative, not OpenMinis' wrapper.

## Decisions

- **Two harnesses that feel like one Buddy.** The mind is the Claude CLI on the Mac; the phone carries its own small harness so the app works alone, OpenMinis-style, with nothing else installed. The phone harness is the spare, not a rival: same transcript format, same skills folder, same tools where the phone can do them, and anything it can't do says so rather than pretending. Because the phone harness is ours, other providers are cheap there; the mind stays Anthropic.
- **First screen: one button, "Sign in with Claude"**, through the OAuth client the Claude Code CLI uses (authorization code with PKCE, the CLI's client id and scopes), because a Claude subscription is only reachable as that client. The browser comes back to a loopback listener in the app, or to the hosted callback page whose code the user pastes when the listener cannot bind. An "advanced" link underneath takes an API key, another provider, or a custom endpoint.

- **One primary, never two brains.** Without a mind, the device that signed in first is primary and runs the phone harness; every other device is a viewer of the transcript (iCloud carries it as history, never as something two devices append to). One control hands primary to another device, the way the Home app picks a hub. Install the Mac app and it takes primary for good; everything else becomes a limb. The Home app is the model to borrow for the copy: works now, add a hub for automations, remote access and sharing.

- **Womble: the viewer-only app for old devices.** A separate, tiny bundle built on old APIs so it can target back to iOS 12 or 13, which the main client never could without dragging itself down. Same CloudKit records and pairing, no mic, no models, no sign-in; covers the viewer and house roles for the drawer iPads. Working title from Sam: Womble, because it is recycling. Off Apple (the XGIMI projector on Android TV, an LG on webOS) Womble is a web page served by the hub on the home network, as the kitchen pad is today, in a thin shell per platform; those screens need a hub on the LAN, which is fine because a TV is in the house, not in a drawer.
- **Three bundles: client, hub, Womble.** One client codebase for current iPhone, iPad, watch and TV; the Mac app is the separate hub bundle carrying the CLI (the Plex client / Plex Media Server split). A client's role is decided at first launch from the app's private CloudKit record: no primary or mind exists, so become primary and show sign-in; one exists, so become a viewer (or a limb if there is a mind) and show only a "connected to" line. The TV build never offers to be primary. Apple TV cannot be the hub: tvOS suspends third-party apps like iOS; only a Mac runs resident code.
- **Viewers never hold the Claude login.** Only the primary or the mind talks to Anthropic. Everything else holds a pairing token in the app's private CloudKit database, readable by every device on the Apple ID including Apple TV, so sign-in happens once. A lost viewer holds nothing that reaches the account.

- **The hub can be part-time.** On a laptop (Krista's setup; Helen has an iMac, a full-time hub with no lid) the hub is primary while the lid is up and hands primary back to the phone on sleep; on wake it reads the turns the phone took from the shared transcript and carries on. So the one-primary rule needs an automatic handover on sleep and wake, not only the manual switch. The hub has no chat window of its own: the Mac runs the ordinary client alongside it, paired like any viewer.

- **Inter-device transport, three layers.** CloudKit private database for state: transcript log, pairing record, primary lease; subscriptions push changes, Apple hosts it. Direct sockets for live turns on the home network, found by Bonjour. Away from home, the devices punch their own tunnel: CloudKit is the signalling layer (each device publishes its public key and address candidates as records, pushes deliver them), both ends hole-punch over UDP, and a WireGuard or QUIC session rides the hole, so the hub is reachable live with no account to make and nothing of ours hosted. When the punch fails (symmetric or carrier-grade NAT, hotel Wi-Fi, roughly a fifth of networks) there is no relay: the phone runs the turn itself against the same account (the phone harness) and the hub catches up from the log. A hub can also answer a turn through the log itself, seconds slow, for anything only it can do. Push notifications for wake-ups. Rule: CloudKit is truth, sockets are speed; with no socket the app still works off the records, just slower.

- **First ten minutes.** Sign in with Claude. The microphone is the only permission asked up front, at the first press; every other permission is asked the first time Buddy needs it, in the conversation, with a sentence saying why. No feature tour: the breadth is discovered, not read. The opening is one question, "What did you forget this week?" (concrete, actionable tonight, and everyone has an answer; "what's on your mind" invites a life story the app can't act on), with "or just start talking" visible; Buddy listens, asks at most one follow-up, and does something with the answer straight away. Everything else is learned over weeks from what she brings, the way Sam's was.

- **Conflicts: append, never overwrite.** The transcript is an append-only log with per-device sequence numbers, so two devices cannot clobber each other; offline branches are shown to the next turn as "meanwhile, on the phone" and carried on from. One record per turn, named by its device and sequence number and saved create-only, so a retry or a second writer on the same device fails rather than overwrites. Each turn lists the turns it continues from, so the log is a graph, a fork is more than one head, and the next turn carries a fork on by listing every head. A read that is missing turns (a record not yet visible to the query, or one that does not parse) says so, and nothing continues from it, since its heads could name a fork that never happened; because a newest turn the query has not caught up with leaves no gap behind it, a read also fetches by ID one past each device's last seen turn, and a writer checks by ID for turns of its own device beyond what it knows, and for its newest turn in the transcript, before choosing parents. Every read asks by a field of ours (a sequence above zero) rather than for everything, because CloudKit answers a match-all predicate out of the record name's index and the development schema never marks that queryable; the cost is that a record damaged badly enough to have lost its sequence reads as absent rather than as a hole, which is junk nothing here writes, and damage that matters is still caught by the fetch-by-ID probe. The only mutable record is the primary lease, one CloudKit record claimed atomically with an expiry: every write is a compare-and-set on the version the writer read, and each claim raises an epoch. Handover is probe-driven, not expiry-driven: at turn time a device probes the lease holder's socket, asking whether it still holds that lease, and claims if it gets no answer, so a dead hub costs one probe timeout, not a lease; the expiry (ten seconds, five-second heartbeat) only stops two claimants racing. Of two claimants one wins the compare-and-set and the other re-reads, probes the winner and defers. A holder heartbeats on its own from the moment it is granted the lease; a heartbeat or a turn that finds the record changed underneath means it was displaced, and it stops counting itself primary at once and yields to the lease that displaced it for as long as that lease stays fresh, so two devices that can both reach CloudKit but not each other settle on one primary rather than taking the lease from each other every turn. The one exception to the probe rule follows: a device that yielded waits for that lease to lapse before claiming, one duration, because the probe is exactly what it cannot trust; every other device takes over a dead holder on one probe. A holder that cannot reach CloudKit at all stops counting itself primary when its lease expires, judged on a monotonic clock as well as the wall clock so a clock correction on wake cannot revive a stale lease. So two brains last at most one heartbeat interval after a claim over a live holder, and one duration after a claim over a cut-off or suspended one. Every turn is saved in one atomic batch with a marker record named by the append's nonce; a retry after a lost acknowledgement carries the same nonce, the marker refuses to be created twice and names the turn, so the retry finds its turn on any writer, after a relaunch included, and never writes it twice. A turn written as primary rides in the same atomic batch as a heartbeat of the writer's lease, compare-and-set on the version it holds, so a device displaced during a long model call, or in the moment between the reply arriving and its write, writes nothing rather than a second brain's answer. Away from home the phone runs the turn itself and probes nothing. No graceful release: it isn't load-bearing. The household board is its own shared container, never the personal log's, because the board is shared across Apple IDs and the log never is. Memory is a git repo, as Sam's is, so it merges; a real conflict there is rare enough to ask.
- **Memory is held the way the transcript is: append, never overwrite.** One record per revision of a file, named by its device and its sequence number on that device and saved create-only, in the same private container as the log and so hers on her Apple ID with no account to make. A revision lists the revisions it replaces, so a path is a graph like the log is: two devices that edit one path without seeing each other leave two heads, the newer is the file and the older is a conflict copy beside it named the way Obsidian Sync names one, and an edit made after seeing the fork resolves it by continuing from every head. Identical text on two devices is not a conflict. A deletion is a revision like any other, so a delete on one device cannot swallow an edit made on another: the edit stays, as the file or as a copy. A read missing revisions says so and nothing is written from it, the transcript's rule and for the same reason, tail probe included. Every revision is kept, dated and numbered per device, so "everything that changed today" is a query rather than a diff — which is what the nightly memory review reads, and the reason revisions are never collapsed into the last write. Advanced: point it at a git remote (GitHub, as Krista has) for history, review and the nightly dreamers — recorded as a setting today, with nothing pushing to it yet.
- **The memory is an Obsidian vault.** A mirror keeps a directory on disk holding those files and syncs it both ways, so on the hub she opens it as a vault and reads the assistant's memory live; her edits become revisions the assistant sees next turn, continuing from the revisions that folder last saw rather than from whatever the store holds at the moment of the push, so a change made on another device in between stays concurrent and becomes a copy rather than being swallowed; a conflict copy is a file in the folder like any other — editing one merges it into the file it is a copy of, deleting one settles the fork on what the file already says. On the phone the app exposes the folder through Files, which Obsidian mobile opens. Standard markdown links work in Obsidian and its graph as long as they are relative paths inside the vault, so the only rule is no absolute paths; hidden files are local to the machine they are on, which is what keeps Obsidian's own `.obsidian` folder out of the store, and symbolic links are never followed in either direction, since one inside the vault could otherwise carry a file from anywhere the app can read into the memory. Two devices can also write `notes` and `notes/today.md` without either being wrong; both revisions are kept, and the one standing where the folder has to go is shown beside it under a copy's name.
- **The lid opens after a week.** The hub reads the CloudKit log, sees what the phone and any other client did, and picks up from the end; nothing lived only in it, so nothing is lost. Its first act is one line saying it was away, and an offer to catch up the week's inbox, never a replay of seven briefs. Rule: anything the hub does unprompted is idempotent and dated, so a late wake never double-does.

- **The contract is a standard form the assistants offer and the people sign.** When two Buddies first meet, each shows its person the same boilerplate with a one-line summary, and nothing flows until both have said yes. The boilerplate is the agent contract generalised: relay messages, keep the sender's authority, never pass memory, refuse what the other person has not asked for; both copies are the same text and the stricter reading wins. Specific grants ("she may read the estate folder") are addenda: named, visible in the app, revocable by either side in one tap. It ships with the app, so nobody writes one, and every pair holds the same document with different addenda.

- **Shared surfaces belong to a house agent.** A kitchen pad or any room device is driven by a household mind (buddy-household today): a peer on the mesh with only the house's memory (shared calendar, shopping, recipes, lights) and nothing personal. Each person's agent talks to it through the same contract. Voice on a shared surface cannot know the speaker, so it acts with household authority only; anything personal needs a claim (tap your name, or say it), and the pad hands that turn to your own agent and marks the reply yours. In the product this is a third hub role: person, viewer, house. The house exposes a few verbs as an API (show a card, add to the list) that personal agents call over the mesh with no model run on the house side; anything needing judgement is a message to the house agent and runs on the house's compute. Without a house account the surface is a noticeboard: it shows what agents post (cards, lists, calendar), takes taps (tick, dismiss, tap your name to reach your own agent), and answers nothing; the same API verbs land on a screen instead of an agent. Whose account the house runs on, if any, is nominated at setup and stated plainly; Apple has family sharing and Anthropic does not, so this is an open product question.

- **A Womble is discoverable on the LAN, and the board needs no account.** A Womble advertises itself over Bonjour; any hub on the network can list the surfaces in the house and ask each one which agents are registered. First registration pairs with a tap on the screen (the HomePod model); after that the roster is open to anyone on the LAN. Off the LAN, a phone reaches a surface through a hub that is on it, the same rule as the TV shells. The board itself is a shared store, not an agent: one person creates it and shares it with the household's Apple IDs, every agent writes through its own person's device and login, and each card carries an owner, so the sharing contract is the mesh's (post, tick, dismiss, nothing needing judgement). The only nomination is who created the share. A Womble depends on an always-on hub for discovery, registration and anything that reaches an agent; an Apple-device Womble still reads the CloudKit board with the hub asleep, while the web-page Wombles depend on the hub for everything. Making a Womble hub-independent is possible and deliberately not pursued.
- **Old iPads are the hook, not the constraint.** Every household has one in a drawer; "put it on the wall and it becomes the house board" sells better than any feature. The viewer and house roles are the light ones and live in Womble, which targets as far back as it can bear; only the primary role (mic, on-device models) wants a current device. The kitchen pad, a 2017 Pro on iPadOS 17, is the first customer.

## Building it

**Doctrine: steal before building.** For every layer, find the open-source thing someone already made and embed or crib it; write new code only where nothing fits. Topo ships publicly, so every borrowed piece is attributed and licence-compliant: an acknowledgements screen and a THIRD-PARTY file name each project and licence, and a copyleft licence held by others (GPL, and BSL for Tailscale's DERP server) rules a piece out for embedding in the app; Tailscale's client is BSD, Nebula is MIT, NetBird is BSD. For the tunnel that is Tailscale's own client code (the disco and DERP packages are the reference for punching), Headscale for the control plane shape, NetBird and Nebula as lighter embeddable alternatives.

From scratch, not a fork: the current app is a Daphne client with a Buddy screen, and its skeleton assumes buddybox, the turn server and one speaker. Build clean around the roles and the CloudKit log, then lift the proven modules across: the audio pipeline, on-device speech models, the lock-screen hold, barge-in. The CloudKit log and the primary lease are `Packages/TopoCore`, with no UI: a protocol over the few CloudKit calls used, an adapter onto `CKDatabase`, and an in-memory database with CloudKit's conflict semantics that the tests run against. The current app is the first thing to port onto it, which is also the test of the design.

## Identity

- **Name: Topo.** Buddy is what Sam named his; each person names their own. The product is the octopus, the mind is the head and every device is an arm; Womble is the arm that picks up old kit. Topo is Aquaman's octopus sidekick from the Silver Age, first seen in Adventure Comics #229 (1956), credited to Jack Miller (writer) and Ramona Fradon (artist); credit them wherever the name is explained (about screen, README).
- **Visual identity.** Decided; the starting point for the build. Not Daphne's (hers, and cute). Calm, indie-Mac, the neighbour of Things and Fantastical. The mark is an octopus: a filled round head over eight curling stroke arms, always eight and countable at icon size; the abstract hub-and-limbs glyph (a circle with eight radiating strokes) is the in-app connected indicator, not the icon. Wordmark in SF Pro Rounded. Two shipped schemes, both derived with the visual-identity method: **Topo teal** (seed `#1E8C9E`, the default) and **madder rose** (the option). Themes are user-made: a theme is four colours (the seeds for primary, secondary, highlight, signal) and the method derives the rest, so the picker is four swatches and Topo can make a theme from a spoken description.
