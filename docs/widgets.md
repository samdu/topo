# Widgets

The mind designs the person's home-screen and lock-screen widgets, and the watch's complications, itself. It writes a small layout document per widget with `topo widget`, the app judges it field by field the way `LookDocument` judges `look.json`, and a WidgetKit extension draws it. A control on a widget carries an action the mind wired: a turn, opening Topo, or one `topo` call run with no turn. The app writes one widget of its own, the default, so no widget is blank before the mind has written one. The same app group holds the mind's controls — a Topo Button and a Topo Toggle the person places in Control Center, on the lock screen or on the Action button — each a slot whose document the mind writes with `topo control` (*Controls*).

## The app group

Everything a phone widget draws lives in the app group `group.zone.hexagon.topo` (on the iOS app and the extension only), under `Surfaces/`: one document per slot (`<slot>.json`), what `topo widget set` said of it (`<slot>.notes`), the slot's images (`<slot>/<name>.png`), the slot revisions (`_revisions.json`), the pending cues (`_pending.jsonl`), each control's last run (`_outcomes.json`, its revision and status, which the failure mark is drawn from, so no number of other taps evicts it; a stale tap, or one from an older revision than the outcome's, is logged and leaves it) and the last 50 taps (`_taps.jsonl`, the widgets' and the controls' both). A control slot is `_control-<slot>.json`, with its notes beside it. The store's own files start `_`, which no slot the mind names can, so a slot is never one of them; a slot name is checked before it becomes a path. A revision counter file that cannot be read fails the write rather than starting the counters again, since a counter begun again issues a revision an old timeline already carries. For the same reason a sign-out keeps the counters as `_floor`, the highest given, which every slot's next revision is above: no revision is given twice across logins, and no slot name outlives one. `SurfaceStore` is the only way in: every write is one atomic replace under an `NSFileCoordinator`, every read a coordinated read, and the files are protected until first unlock, so a widget reads them on a locked phone. The vault is not used, because the extension cannot reach its folder and a widget's read has to work behind the lock. The watch keeps its copy in its own group, `group.zone.hexagon.topo.watch`, in the same layout through the same type (*The watch*), since app groups do not cross devices.

## The document

A slot is a name the mind picks (`[a-z0-9-]`, at most 32 characters, at most 12 slots); `_default` is the app's. A document's top level is `version` (1), `families` (a node tree per family: `systemSmall`, `systemMedium`, `systemLarge`, `accessoryCircular`, `accessoryRectangular`, `accessoryInline`, and `default`, which a missing family falls back to, its texts cut to 60 on a lock-screen family with a note at `set`, and drawn on `accessoryInline`, when that family is missing, as that family's one line, which is not kept, so the document holds only what its budget counted), and optional `tint`, `until` (ISO 8601; past it the slot draws the default), `tap` (a turn or open for the whole widget, since a widget's own URL carries no intent), `relevance` and `relevant` (*Relevance*). `accessoryCorner` is a family too, the watch's alone. `revision` is the app's: assigned at `set`, one more than the slot's last (the count outlives `topo widget clear` and a sign-out), and refused from the mind.

The node kinds are `vstack`, `hstack`, `zstack`, `text` (words, or a date drawn `relative`, `timer`, `time` or `date` so it ticks with no reload), `glyph` (an SF Symbol the system has), `image` (one `topo widget image` put in the slot), `gauge`, `progress`, `topo` (Topo in one pose, drawn as a still frame of `TopoMascot`), `spacer`, `divider`, and the controls `button`, `toggle` and `link`. A colour is a `Theme` token or a light/dark hex pair. `topo help widget` lists the fields and `topo widget example` prints a document with every kind.

`WidgetDocument.read` judges every field where it is read. An unknown kind drops that node alone; a bad field falls back to its default with a note and its node, words and children stand; a text past its length (200, 60 on a lock-screen family) is cut and a gauge value past its bounds is drawn at the bound, each with a note; a tree past its budget (16 KB, 64 nodes, depth 6, 4 images, 6 controls a family) is cut there with a note; a control's label's words and nodes count against the 64, the control before its label and needing room for one word of it (the id, when the label draws nothing), and the 64 nodes and 4 images are the document's across its families. The 16 KB is the mind's document's: the kept copy, written compact with every default field, may be larger, and a read of it holds to the other budgets alone. `accessoryInline` keeps one glyph and one text. A control's id is `[a-z0-9-]`, unique in its family, and the same id in two families is the same control. Nothing the reader keeps can trap in a view: every number is finite and in range, every name a case, every symbol one the system has.

## `topo widget`

`Apps/Topo/Tools/WidgetTool.swift`, a row in the guest's `ToolTable` beside `topo look`:

- `topo widget`: every slot, its revision, families, `until` and images, the reader's notes and the controls judged only at the tap, which placed widgets show it (`WidgetCenter`), and whether its record is behind (*The record*).
- `topo widget set SLOT JSON`: 0 when the reader took everything, 6 with the notes when it refused part (the rest is written), 2 when nothing could be read. It writes and asks for a reload.
- `topo widget image SLOT NAME PATH`: a PNG, JPEG or HEIC from under `/home/topo` (the app's `Documents/home`), read through a descriptor opened beneath the home's resolved path with `O_NOFOLLOW_ANY`, so no link anywhere along the path is followed; a `..` or `.`, a path outside the home, a file over 512 KB or 1024 px on its long side, one that is not one of those types, or a fifth image in the slot is status 6 with nothing copied. What is kept is the decoded image, turned upright by its EXIF orientation, re-encoded as PNG.
- `topo widget clear [SLOT]`, `topo widget taps [SLOT]` (time, slot, control, revision, kind and status — never an argument or a tool's words), `topo widget example`.

A `run` action is judged at `set` by `WidgetRunJudge`: the allowlist (`WidgetAction.allowed`: `home scene`, `home set`, `notify`, `reminders done`, `reminders add`, `look set`, `look reset`), then the call's own tool's argument reader, and for `home` the homes HomeKit has already loaded with access granted (`HomeAccess.loadedHomes`), never making the manager and so never asking. With none loaded the action is kept and listed as unchecked, and the tap judges it in full. A `home set` on a lock's or a garage door's target (`lock`, the short name `topo home` gives a lock's target, `lock-target-state` and `target-door-state`) is refused however the call names it, and so is a `home scene` whose action set writes one or holds an action that is not a characteristic write, since what that does cannot be read: an id is resolved to its characteristic first, and the check keys on HomeKit's characteristic type (`HomeTool.widgetRefused`) as well as the short name, so a change to `HomeNames` cannot let one through. A toggle's call is judged with `on` and with `off` appended. A refused action opens Topo instead, with a note.

## The extension

`TopoWidgets` (`Apps/Widgets`, bundle `zone.hexagon.topo.widgets`), embedded in `Topo`: one kind, `TopoSurface`, an `AppIntentConfiguration` whose one parameter is the slot, its options the slots in the app group. A widget with no slot picked, a slot that is gone or past its `until`, draws the default; with no default either, the phone is signed out and it draws the octopus mark and "Sign in on your phone". The timeline is one entry now and one at `until`, `.never` without one, each carrying the drawn document's `relevance` for the Smart Stack: the app reloads on every write, through `SurfaceReloader`, which coalesces requests, at most one reload of a kind per 2 s window, the first request starting the window, so a mind still writing delays a widget by no more than the window (and reloads everything at once on sign-out). The extension reads the app group and nothing else. `WidgetNodeView` is one switch over the node kinds; every text and control carries an accessibility identifier from its place (`widget-text-0.1`, `widget-control-<id>`), and a control whose last run at this revision failed is drawn with a mark until it runs again or the slot is written anew.

## Taps

- `open` is a link to `topo://open`.
- `turn` is `WidgetCueIntent` (`openAppWhenRun`), or for a `link` a `topo://cue?slot=…&control=…&revision=…` URL; the whole widget's `tap` is cued under the id `_tap`, which no control can have. A URL is kept as a cue only if the slot's document is at its revision now and holds a turn by its control, so one opened signed out, when there is none, is not left for the next login. A cue names the slot, the control and the revision, and carries no words, since any page or app can open a `topo://` URL. The intent mints a nonce and records the cue in `_pending.jsonl` under it, only when the slot's document is at the cue's revision (`SurfaceStore.recordCue`), so a widget still drawn after a sign-out keeps no cue, and the app drains the cues (`WidgetCues`) on becoming active, on the URL, on a control's tap, and on the harness's first read of the log; a drain on a harness that has not read the log — the app launched in the background for a tap, with no screen — reads it first, and a read that fails leaves the cues for the next drain, when Topo is next opened. The words are the slot's document's at that revision (`WidgetDocument.turn`): a cue outlives no layout, so one whose slot holds no document at its revision is dropped with no record, and one naming no turn control of the document is refused, the default included. Each goes on the line as `widget <slot>: <say>` (or `tapped <id>`, a toggle's new state after it) through `Harness.willSend(_:nonce:)`, which does nothing for a nonce already on the line or in the log, and its record goes only after. So a drain run twice is one turn, and a cue queues behind a turn in flight rather than joining its words.
- `run` is `WidgetRunIntent`, a `LiveActivityIntent`: it runs in the app's process, launching the app into the background if it is not running (measured on the simulator, backgrounded and killed; a plain `AppIntent` from a widget runs in the extension). `WidgetActions` refuses a tap whose revision is not the slot's current one (`stale`, and a reload; a revision given before the last sign-out is an earlier login's, and is recorded nowhere), judges the call against the allowlist again, and runs it through `ToolService.bounded` over the guest's tools with `home` refusing the targets above and the scenes that set them (`WidgetActions.table`), so the 90 s bound, cancellation at it and the permission broker apply as to a guest call. The status goes to `taps.jsonl`, never the words.

A toggle turns to the opposite of its stored state, not of the state the tapped entry drew: the tap's handling flips it in the slot's document under one coordinated write (`SurfaceStore.flip`), at the same revision, so two taps before a reload are on and then off, and another tap drawn from the document still lands. A control's runs wait each on the one before, so their effects land in the order the taps were flipped, and a run that fails holds up none after it and puts the toggle back to its confirmed state: the last state a run of it succeeded at, or its stored state before its taps began, so two failed taps leave it as it was. A turn toggle's new state is resolved once and written into its pending cue before the toggle is set to it, so a drain after a crash anywhere between sets and says the same state; a cue whose nonce is already on the line or in the log sets nothing.

`WidgetTaps` is the handler for both, set on `WidgetIntents.handler` in `TopoApp.init`, which the system finishes before an intent it launched the app for runs.

## Controls

Two kinds in the controls gallery (iOS 18): **Topo Button** ("A button Topo sets up") and **Topo Toggle** ("A switch Topo sets up"), `TopoButtonControl` and `TopoToggleControl` in `Apps/Widgets/TopoControls.swift`, of the control kinds `zone.hexagon.topo.control.button` and `.toggle`, a contract since a placed control is lost if its kind changes. Each is configured with one of its kind's six slots, listed "Button 1"…"Button 6" and "Toggle 1"…"Toggle 6" (`button-1`…, `toggle-1`…), a fixed list so a slot can be placed before or after the mind fills it; one with no slot picked is slot 1. The person places, removes and orders them; Topo cannot put one anywhere or learn where one is.

### The document

`ControlDocument` (`Apps/Shared/ControlDocument.swift`), kept as `_control-<slot>.json`: `title` (32), `symbol` (an SF Symbol the system has), `tint` (a colour as a widget's), `hint` (32, what the Action button says), a button's `subtitle` (32), a toggle's `on`, `onText` and `offText` (16), `onSymbol` and `offSymbol`, and an `action`; 16 KB a document. It is read field by field as a widget's is: a bad field falls back to its default with a note and the rest stands, a refused action becomes the default's (a turn naming the slot) with the title and symbol standing, and a document of the other kind than its slot — naming the other `kind`, or holding a field only the other kind has — is refused whole. `revision` and the `default` marker are the app's. `ControlValue` is what the value provider hands the template: every field already judged, the slot, and the revision it was read at.

The actions are A's `turn` (`control <slot>: <say>`, `control <slot>: tapped` without one, a toggle's state after it), `open`, and `run` (the widgets' allowlist, a toggle's call with `on` or `off` appended, judged at `set` by `WidgetRunJudge` in both forms), and one of the controls' own, `request`: `{"kind": "request", "method": …, "url": …, "headers": {…}, "body": …}`, or a toggle's `{"kind": "request", "on": {…}, "off": {…}}`. Its reader refuses a URL that does not parse, has no host, is not `http` or `https`, carries a user or password (which `ControlRequest.perform` refuses too, sending nothing) or is over 2048 characters; a method other than `GET`, `POST`, `PUT`, `PATCH` and `DELETE` (a request defaults to `GET` without a body and `POST` with one); more than 16 headers, a name that is not an HTTP token, a name or value holding a line break or over 1024 bytes; a body over 8 KB; and an `Authorization`, `Cookie`, `Proxy-Authorization`, `X-Api-Key`, `X-Auth-Token` or `Api-Key` header whose whole value is anything but one secret's reference, so nothing literal sits beside a credential and the secret holds all of it (`Bearer <token>` included). A secret is named `${secret:<name>}`; any other header's value or the body may name one among other text, and the document never holds its value.

### `topo control`

`Apps/Topo/Tools/ControlTool.swift`, a row in the tool table beside `topo widget`: `topo control` lists the twelve slots (default or written, revision, title, a toggle's state, the action — a request as its method, scheme, host and path and its headers' names, never a value, the query or the body — and what the reader said), the secrets' names and local network access. `set SLOT JSON` answers as `topo widget set` (0, 6 with the notes, 2); `state TOGGLE on|off` sets a toggle's drawn state and nothing else, taking no revision, and tells `WidgetActions` it is the state a failing run goes back to, and a run in flight that then succeeds shows its own state over it, since the device took that last; `clear [SLOT]` writes a slot's default back; `secret set NAME VALUE` and `secret clear NAME` keep a credential in the device keychain (`ControlSecrets`: service `zone.hexagon.topo.control-secret`, one item per name, `AfterFirstUnlockThisDeviceOnly`); `taps [SLOT]` is the controls' lines of the tap log with each request's HTTP code, and `topo widget taps` lists the widgets' alone; `example [button|toggle]`. Every write reloads its kind through `SurfaceReloader`, coalesced per kind as the widgets' are.

### The tap

The value provider reads the slot when the system asks (`ControlSlotProvider`), and the template takes one intent per kind, since `ControlWidgetTemplateBuilder` has no branch: `ControlButtonIntent`, a `LiveActivityIntent`, and `ControlToggleIntent`, a `SetValueIntent` and `LiveActivityIntent` whose `value` is the state the person asked for. Both carry the slot and the revision the value was read at and run in the app's process, launching it into the background (measured, backgrounded and killed). `WidgetTaps.controlTapped` reads the slot's action at that revision:

- `run` and `request` go through `WidgetActions` in the background: A's stale check, chain per control, confirmed state and restore, tap and outcome records and cancellation at sign-out, read through `ControlDocument` by the slot's `_control-` name. A toggle is set to the state its intent carried, not flipped (`SurfaceStore.setControl`), and a failed run puts it back to the state of the last run that took, and only when no later tap stands, since the effects land in the taps' order and a later tap's run settles the toggle itself. The last tap's run settles the toggle either way, at what the device took last — kept per target (the toggle's calls for on and off), since a rewrite can point it at another device: the last run that succeeded on the target the slot names now, whatever revision drew it, or the mind's `state` about that target since — written at the revision the slot holds now (a rewrite that points the control at another target draws nothing of the old one's run or the mind's word about it); with nothing taken, a slot written anew keeps the state the rewrite gave it. A rewrite's `on` during a live chain does not override a success, since a rewrite moves no device: the mind reports a change in the world with `topo control state`. A `run` is `ToolService.bounded`; a `request` is `ControlRequest.perform` (`Apps/Topo/ControlRequest.swift`): its secrets resolved from the keychain immediately before, a missing one sending nothing (`1`), then one task on an ephemeral session with no cookies or cache, under an absolute 10 s deadline from start to answer (`4`), no redirect followed (a 3xx is the answer), the response read no further than its status (URLSession itself holds a `text/plain` or untyped response back to sniff its type until 512 bytes or the body's end, so one whose body stalls is answered at the deadline), and `0` for a 2xx and `1` otherwise, recorded with the HTTP code as kind `request`. Nothing it carried is logged or recorded. Topo never retries one; the transport resends a `GET` on a connection dropped before an answer — measured at two resends, three received — and sends a `PUT`, `DELETE`, `POST` or `PATCH` once, so an effect that must not happen twice is a `POST`.
- `turn` records A's cue under a nonce minted here and drains it, and the intent continues in the foreground (iOS 26's `supportedModes` `[.background, .foreground(.dynamic)]` and `continueInForeground(alwaysConfirm: false)`); the cue is recorded before and its drain reads the log itself when nothing has, so a foreground that never comes — iOS 18 to 25, where the intent does not bring Topo forward — still sends the turn. Its record goes once the turn is on the harness's line, which the defaults keep (`Harness.pending`), so an intent ended before the turn reached the log leaves it for the next launch to send under the same nonce. Before iOS 26 the tap holds its intent open until that drain has sent the turn, bounded at 20 s (`WidgetTaps.holdsForTheDrain`; the intent returns at the bound and the drain runs on), since a process launched in the background for an intent is kept alive only while the intent runs.
- `open`, and a tap while signed out, continue in the foreground and record nothing.

The app declares `NSAllowsArbitraryLoads`, since a request may be plain `http` on the home network, and `NSLocalNetworkUsageDescription`. Local network access is asked for in the foreground only, since a background request while it is undetermined is denied unasked: `topo control set` on a request whose host is a name or a private or link-local address — anything but a public address, since a name like `homeassistant.lan` resolves to the home network and what it resolves to is known only where it is resolved (`LocalNetworkAccess.mayBeLocal`) — asks at once if Topo is in front and at the next foreground if not, by opening a connection to the host and cancelling it with nothing sent. The system raises its prompt only when that connection lands on a local address, so a name is asked for where the phone is at the set: one set away from home is not asked again, and its first press on the home network in the background may be denied until Topo is next opened there. The ask is recorded as allowed only when its connection landed on a local address.

### The default and sign-out

`ControlDefaults` writes each slot's default — `circle.hexagongrid`, "Topo", the slot's name as the subtitle or state text, a turn saying `control <slot>: tapped, not set` — into every slot holding no document when the phone becomes signed in, never over a written slot on a launch already signed in — a new login, the phase coming to signed in from anything else, writes it over every slot, so no document an earlier login wrote is drawn or run under it — and `topo control clear` writes it back; so every slot holds a document, under a revision, while signed in. A sign-out takes the control documents with the surfaces and reloads every control; signed out, a control draws "Sign in" and its tap opens Topo. The control secrets go with the connections' tokens (`Connections.forget`, at a sign-out, a takeover or a demotion), and a clear the keychain refuses is kept as the connections' is (`ConnectionsLeftBehind.controlSecrets`): said on the sign-in screen, tried again alone at each launch and at an install's first launch, and while it stands a request naming a secret sends nothing (`1`), `topo control secret set` is refused and the listing says why rather than naming what the keychain holds.

### Limits

A control draws a symbol, a title, a second line and a tint and nothing else; at the small size, the symbol alone, and the tint is the system's to honour. It shows what the system last read of it, and the system decides when it reads again. No control intent asks for Face ID, so a press on the lock screen or the Action button runs as pressed. On iOS 18 to 25 there is no dynamic foreground: a turn's cue is recorded and drained in the background and nothing comes forward, and an `open` control does nothing visible. HomeKit is not available to the extension, so a toggle's state is what the mind and the runs set, never a live read.

## The default

`DefaultSurface` writes `_default` after each reply the log brings (`Harness.onLanded`) and whenever the phone is signed in, at launch or after signing in again. It keeps the revision it was first given in the login, so a tap on the default drawn a reply ago still lands, and each login's first takes the next. The home-screen families carry Topo, the reply's first sentence, its time and an "Ask Topo" link, the words marked `.privacySensitive()`. The lock-screen families carry Topo, the time and "Ask Topo", and no word of the reply, since a locked phone shows them to whoever holds it whatever the person's settings. A slot the mind writes for a lock-screen family is drawn as written; `topo help widget` says those families show on a locked phone.

## The record

The phone's slots reach the watch through CloudKit, the only path between them: `SurfaceSync` (`Apps/Topo/SurfaceSync.swift`) keeps one `Surface` record per slot (`surface-<slot>`, `SurfaceRecords` in TopoCore) holding the kept document as the phone wrote it, its revision, `updated`, `runner` (the saving phone's device id) and the slot's images as assets. `topo widget set`, `image` and `clear` owe the slot's record a save before they write, so a process ended between the write and the record still owes it, and after the write `set` and `image` owe the save again and `clear` owes a clear, which starts the pass; the phone's widgets never wait on iCloud. A toggle's tap owes its slot a save before the state is written, since the state is part of the document (`WidgetActions`, `WidgetCues`). A save sends the whole slot or nothing: a document or an image the store cannot read just now (unreadable, or halfway through being written) leaves the record as it is and the save owed, and a save owed for a slot whose document is gone clears the record, which mirrors the file. A `set` whose document is written owes the save even when its notes are not; a `clear` of every slot that fails part-way owes a clear for each slot whose document went. Each pass makes the zone first (`TopoCloudKit.ensureZone`), since a fresh account has none until something writes one. The passes run one at a time. A write owed while a pass runs is seen by it in the same job, so the pass settles nothing it read before that write and goes round again; the last pass lets go in the same turn as its last look for a later write, so a write that lands as a pass ends always gets a pass of its own. A record belongs to its `runner`, and while a takeover lands two phones can be writing at once, so no write trusts a check made before the read it acts on. Every write is one compare-and-set on the change tag of a read made for it (`SurfaceRecords.read`, `all`, then `save(_:over:)` or `clear(slot:runner:at:over:)`), and the phone's role record is read after that read (`SurfaceSync.roleAllows`): a takeover saves the old primary's role record as viewer with the lease's first heartbeat, before the new primary is primary and writes any slot, so a read that saw the new primary's record is followed by a role read that says viewer, and a phone whose role record says viewer drops what it owed, save for a record of its own still on the slot (a save whose undo below never ran, read whole or not), which it clears under that record's tag. A write refused for its tag is read and judged again, up to three times a pass. A save keeps a later revision of the same runner's on the server and never overwrites it, while another runner's record is replaced whatever its revision, since each phone's counters are its own. A save that lands after a takeover it did not see (the role read before it, the takeover between) is undone: the role read after the save says viewer, and the phone clears its own write under that write's tag, a clear refused because the new primary has written since being dropped. Nothing is deleted: CloudKit's deletes take record ids and no tag (a save policy governs saves alone), so a clear is a tombstone saved under the tag, which the watch reads as the slot's removal and a save replaces. The primary sweeps the rest: at launch, at each sign-in and at a takeover (`SurfaceSync.sweep`, on the role being primary while signed in) it reads every record, then its role record, and clears each record another runner saved under the tag it read, the leftovers of an earlier primary or an earlier install; a clear refused because the record moved reads it again, with the role after it, and clears another runner's save there in turn only when that runner's own role record says viewer, while one this phone saved, or one by a phone not demoted, is left. A slot whose save or clear failed stays pending (in the app's defaults, outside `Surfaces/`) and is tried again at the next write, launch or sign-in; `topo widget` says its record is behind, a cleared slot's included, and does so when no slot is left. `_default` is not saved: the watch writes its own.

## The watch

`TopoWatch` keeps the watch's copy (`Apps/TopoWatch/WatchSurfaces.swift`). `WatchSurfaceCache` reads the zone's change feed for `Surface` from the token its last read left, reads each record's document with the watch's own `WidgetDocument.read` (the phone's judgement is not trusted), and keeps it at the phone's revision with its images through `SurfaceStore.keep` and `keepImages`, then reloads the timelines. A slot leaves the cache only when its removal is confirmed: a deletion or a tombstone in the feed, or, when the feed is read from the start (no token, or one CloudKit expired), a cached slot the feed does not list that a fetch by name finds gone. A change the feed reported that did not reach the group, a write or a removal that failed, keeps the feed's token where it was, so the next read reports it again. A deletion is judged by the slot's files on disk, not by whether its document reads. A record the feed lists that a read cannot take whole (an asset that did not load) is asked for by name at each fetch until it reads or is gone, while the token moves on, since a record malformed for good would otherwise hold it for good. A record is kept images first: the images it names are written, then the document, then the images it no longer names removed, so a write failing part-way leaves the cached document with every image it names (one kept under the same name may be the newer until the retry). A feed or fetch that fails any other way keeps the cache, so a watch off the network keeps drawing; what is cached otherwise ends only at its `until`. `WatchSurfaceSync` fetches at three moments and no others, one at a time: while the app is open (its 20 s refresh), on the `Surface` push (`SurfacePush`, a `CKQuerySubscription` on `updated` after 1970, content-available, with the `WKBackgroundModes` `remote-notification` mode), and on a background refresh it asks for 30 minutes on. The time from `set` to the wrist is Apple's push and refresh budget, observed and never promised. The subscription's predicate needs `updated` marked queryable in the development schema, as `sequence` is for `Turn`; until it is, the subscription's save fails, is ignored, and the watch fetches on the other two.

`WatchDefaultSurface` writes the watch's `_default` from the log it already reads, once per newest reply: Topo, the reply's time and "Ask Topo", on the four accessory families, and no word of a reply, since a watch face is read by whoever sees the wrist. Before the app has ever run there is no default, and a widget draws the mark and "Open Topo".

`TopoWatchWidgets` (bundle `zone.hexagon.topo.watch.widgets`), embedded in `TopoWatch`, builds `Apps/Widgets` with the shared reader and view for watchOS and reads the watch's group and nothing else; it holds no CloudKit entitlement. `TopoSurface` is the placeable kind, in `accessoryCircular`, `accessoryRectangular`, `accessoryInline` and `accessoryCorner`, each slot the watch holds offered as a recommendation since a watch face has no configuration sheet. `topo` is drawn as the mark, the pixel engine being iOS only.

A watch widget's only interactivity is `Button(intent:)` and `Toggle(isOn:intent:)`, and a watch intent runs in the app only by opening it (`LiveActivityIntent` is unavailable on watchOS). A `turn` is `WatchCueIntent` (`openAppWhenRun`), which mints the nonce, records the cue in the watch's group (`recordCue`, against the cached document's revision) and opens `TopoWatch`. The whole widget's `tap` reaches the app as a `topo://cue?…` URL (the watch app declares the `topo` scheme), which `WatchCues.open` keeps as a cue under a nonce it mints only when the cached document is at the URL's revision and holds a turn by its control, then drains; `topo://open` only drains. `WatchCues` drains on launch, on becoming active and on the intent, after a read of the log, sending the cached document's words (`WidgetDocument.turn`, a toggle's asked-for state as the tapped entry drew it) through `TranscriptStore.send(_:nonce:)`, which queues nothing for a nonce already on the line or in the log, and removes the cue only after. A cue whose revision the cache no longer holds is dropped with no record. `open` and `run` open `TopoWatch`. The phone drains nothing: the turn reaches it as every watch turn does.

## Relevance

`relevant`, at most 4 contexts, any of which makes the slot relevant: `{"from": …, "to": …}` (ISO 8601, the end after the start), `{"place": "home" | "work" | "school" | "commute"}` (the system's inferred places, which need no location permission), `{"near": {"lat": …, "lon": …, "radius": metres}}` (50–50 000), `{"sleep": "bedtime" | "wakeup"}` and `{"headphones": true}`. Each is read on its own: a bad one is dropped with a note and the rest stand. The phone keeps it and ignores it. On the watch, a placed `TopoSurface` returns the contexts of a slot whose `until` has not passed from its provider's `relevance()` (watchOS 11), and the app donates them through `RelevantIntentManager` below that; `TopoMoment` (watchOS 26, a `RelevanceConfiguration`) offers every such slot to the Smart Stack in its `accessoryRectangular` form without the person having placed anything, so the mind decides both what the card is and when it appears. The Smart Stack decides whether it shows; it shows to whoever is looking at the watch.

## Sign-out

A sign-out cancels every widget run in flight, the ones queued behind another included (`WidgetActions.cancelAll`, through `SurfaceReloader.onForget`; `ToolService.bounded` hands the cancellation to the call, so a tool that checks before its effect takes none), and a run that answers after its slot's document is gone writes no tap and no outcome; a control's request in flight is cancelled the same way. It removes everything in `Surfaces/` but the revision counters' `_floor`, and reloads every timeline at once (`SignOut.forgetSurfaces`); a takeover and a viewer's arrival take the same step (`Takeover.forgetSurfaces`, `ViewerArrival.forgetSurfaces`), and so does any login ending by another path (`DefaultSurface.follow`, on the phase leaving signed in), so each placed widget draws the signed-out state. Each of them also clears every `Surface` record this phone saved and no other phone's, each under the tag of the read that found it this phone's, so one another phone saved since is left (`SurfaceSync.forget`, which `SurfaceReloader.forget` calls on each of these paths; a clear refused for want of the network is owed to the next sign-in and goes before anything that login saves, the pending slots and any sweep not yet run are dropped, and a pass running when it lands sends no write after it: each clear of a sweep and each owed write is made only while the login the pass began in stands, so one already sent lands before the sign-out and none follows it; a second sign-out landing while the first's clears run is cleared in its own pass). A launch that finds no token takes nothing away.
