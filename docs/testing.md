# Tests and the PR check

Every suite's own description sits with the code it holds (the guest's in `docs/guest.md`, the mascot's in `docs/mascot.md`, the packages' in `docs/cloudkit.md`). Running the app signed in, the microphone press, the audio lane and the talk lane are `docs/simulator.md`.

## The debug launch environment

A simulator is signed in from its launch environment, not by hand: `Apps/Client/DebugRun.swift` (all of it behind `#if DEBUG`) takes a Claude Code setup token from `TOPO_CLAUDE_SETUP_TOKEN`, marks the launch signed in and hands it to every `claude` in the guest (`docs/auth.md`, *Debug runs and CI*), puts a turn on the harness's line from `TOPO_DEBUG_OUTBOX` (empty clears it) so a launch can be the relaunch that finds one owed, and takes one turn from `TOPO_DEBUG_SEND` through the ordinary harness, waiting first for the guest to be ready (`guest: waiting: …`, then `guest: ready`), printing each step prefixed `[topo-debug]`, each pose Topo takes from the guest's turn (`mascot: turn began for <turn>, process P, …`, `mascot: …`, `mascot: turn gone for <turn>, …`, naming the turns the guest turn answers), and the reply as `reply to <nonce> in run <run> from session <id>, process <pid>: <text>`.

A `--userland` run (`docs/simulator.md`) prints `userland: dns forwarder on 127.0.0.1:<port>` once the guest is booted; launched with `TOPO_DEBUG_DNS=stopped` (`DebugRun.dnsVariable`), it stops the forwarder instead, as iOS taking its listeners would, waits for the phone's name servers to be written to the guest's `resolv.conf`, and prints `userland: dns forwarder stopped` before the command runs.

A debug build launched with `TOPO_DEBUG_STORE=memory` runs on one in-memory record store for the life of the process (`Apps/Topo/AppRecords.swift`, TopoCoreTesting's `InMemoryRecordDatabase`, as the hub's unsigned build does with `TOPO_STORE=memory`) instead of CloudKit, with no zone to make and no push subscription saved: the harness's log and lease, the role at first launch, the memory, the widgets' slots and the viewer's transcript and lease all read and write it. Every UI suite launches that way (`Tests/ClientUI/TopoLaunch.swift`), because an unsigned simulator's first CloudKit reads after a fresh boot can outlast a test's wait for the chat screen (#434). So `topo_ui` exercises no CloudKit store (the diagnostics screen still asks for the device's iCloud account when it is opened): what the UI suites show of the log and the lease holds against the in-memory store's semantics, and the real store is a signed-in run's (`docs/simulator.md`). `TOPO_DEBUG_STORE=stalled` is a store that never answers and a zone that is never made, which is CloudKit at its slowest: the first screen under it is what a first launch shows while iCloud keeps it waiting. The store is the process's, so a relaunch starts with no records, and what a suite carries across one is what is on disk.

## The PR check

The suites run on buddybox, not on a hosted runner: a macOS runner bills at ten times a Linux one, and the three suites that cover the product are about 77 runner-minutes a push against the account's 2,000 free minutes a month. An engineer pushes with `scripts/validate-and-push.sh`, which runs the suites at the commit being pushed, pushes it only when they pass, and posts each suite's result to that commit as a status; `pr-validate.yaml` runs on `vm-linux`, the Macs' pool of ephemeral Linux VMs (dotfiles `tools/vm-runner`), and its `test` job, the required check the merge waits on, reads those statuses. A commit pushed any other way has none, and its `test` is red until the script is run on it.

There are four suites (`scripts/mac-suite.sh`). Three cover the product: the Topo scheme's test action split by test selection into the UI tests (`topo_ui`) and everything else (`topo_unit`), and the scripts' tests, the packages, Womble, the watch's suite (`TopoWatchTests` on a watch simulator from the pinned watchOS runtime, booted and waited on with `simctl bootstatus -b` before the run, bounded at 15 minutes) and the watch, TV, Release and hub builds (`others`; the watch build is read for its widget extension, background mode and URL scheme by `scripts/check-built-plist.sh --watch`, and the Release build by `scripts/check-built-plist.sh`, which reads the watch app it embeds as its companion the same way, and by `scripts/check-built-assets.sh`, which fails it for carrying any part of the voice's bundle, as an archive for the App Store must not (`docs/testflight.md`); the Release build's derived data, `build/device`, is kept for the `Package.resolved` it was built from and made afresh for any other, since what it caches of a package's headers is wrong once a pin moves). Every xcodebuild of the project, the test actions included, resolves its packages into `build/packages` (`-clonedSourcePackagesDirPath`), kept the same way for the pins it was resolved from (compared as JSON without the `originHash` field a resolution rewrites for the path it ran at; a copy that is not JSON names no pins) and made afresh for any other before the first resolution of each suite, and so do `scripts/archive-upload.sh` (`build/packages`) and `publish-topo.sh` (each checkout's own, `docs/install.md`): Xcode 27.2 carries the set of package traits it enabled at the last resolution into the next, whatever version the pin now names, so a state that last saw one version builds another with the wrong set, or refuses the resolution when the traits are named on the package reference, on every retry. The fourth, `scripts`, is the scripts' tests alone, the same ones `others` runs: each runs against fakes of everything it touches, so the suite prepares no toolchain, builds nothing and boots no simulator, and it is what a change to the harness alone needs. The tests run at once, each in a scratch directory of its own and all in one process group of their own, and the suite takes as long as its slowest (about three and a half minutes) rather than their sum; each test's log is printed whole under its heading in `mac-suite.log` once it has ended, and a signal to the script ends every test still going and whatever it started. For the other three the script holds the toolchain to its pins (Xcode, the iOS and watchOS simulator runtimes, XcodeGen), generates the projects from `project.yml`, builds the guest's framework, and fetches the voice's compiled core at its pin (`scripts/fetch-phonon.sh`) before any suite, keeping its zip under its sha256 in the Mac's validation cache (`~/Library/Caches/topo-validate/phonon`), so a checkout made afresh takes it from there rather than from GitHub.

A commit runs only the suites its paths need, chosen the same way in both places. The `select` job reads the paths the PR changes against main and matches each against `SUITE_RULES` in the workflow (`scripts/ci-select-suites.sh`, first rule wins): documentation, root markdown, the other workflows, `.claude/`, `.gitignore`, and the TestFlight and plan-review tooling need none; the hub, watch and TV targets, the watch's widget extension and suite, Womble and `TopoLink`, which the app does not compile, need `others` alone; the harness alone needs `scripts` alone, which is each script named there one by one with its test, a script whose test fakes its whole world: the janitor, `validate-and-push.sh`, `validate-host.sh`, the two selectors and the reviewer's three scripts, and the tests alone of the simulator run, the audio lane and the suite gate (`simulator-run-test.sh`, `ci-audio-lane-test.sh`, `ci-require-tests-test.sh`), whose scripts the product suites prove; the app's sources, every package the app links, the tests, the project, the guest patches, the workflow, a script the product suites are what prove (`mac-suite.sh`, the audio lane's, the build and fetch scripts) and any path no rule names need `topo_unit`, `topo_ui` and `others`, as does a diff that cannot be read. `scripts` is never chosen beside `others`, which runs the same tests, and `--suites all` is the three. `validate-and-push.sh` reads the same list out of the commit's own workflow and runs the commit's own copy of that script, not the worktree's, over the commit's diff against its merge base with origin/main. `scripts/tests/ci-select-suites-test.sh` pins the rules and their cases. The two read different diffs once main has moved under a branch, so `test` can name a status the script's choice left out: `--suites` and `--lane` run what it names.

`validate-and-push.sh`, from the worktree whose HEAD is the commit:

```sh
scripts/validate-and-push.sh             # run the suites the commit needs, push it, post the statuses
scripts/validate-and-push.sh --no-push   # a commit origin's branch already holds: run, post, re-run `test`
scripts/validate-and-push.sh --suites all --lane full
```

- **What runs is the commit.** The suites run in one of the Mac's validation worktrees, a slot (`~/Library/Caches/topo-validate/slots/<n>/checkout`, a detached worktree of the checkout), checked out at the commit and cleaned of untracked files, so an uncommitted change or a stray file in the engineer's worktree is not in the result, and XcodeGen's regenerated projects are not written over the engineer's. A slot's path never changes, so its DerivedData, the guest's framework and `build/` stay warm between runs.
- **The toolchain is pinned.** `scripts/mac-suite.sh` holds every suite that builds to Xcode 27.2, the iOS and watchOS 27.2 simulator runtimes, and XcodeGen 2.46.0, and fails each suite asked for on a Mac without them. The Xcode is the selected one when that is the pin; otherwise the suite finds the `Xcode*.app` under `/Applications` (`TOPO_XCODE_APPS`) whose `version.plist` and `xcodebuild -version` both name the pin, and runs everything under `DEVELOPER_DIR` set to it, so a Mac keeps whichever Xcode other work has selected. The log of every suite but `scripts`, which builds nothing and asks for no Xcode, names the `DEVELOPER_DIR` it ran under; with no pinned Xcode it is refused, naming the versions it found.
- **One suite on buddybox at a time.** A slot is a suite running on buddybox, not a run: a run takes a slot's lock as it is about to run a suite here and lets it go as that suite ends, and there is one slot, so a second run's suite here waits for the first's: buddybox shares its memory with the house's voice assistant, and one suite's simulators are what it has room for (a run with the brain resident already has its swap nearly full). `TOPO_VALIDATE_SLOTS=2` in every run's environment makes two, for a Mac or an afternoon with room: two suites are then in two checkouts and a third waits for one. A run holds no slot while a suite of its runs on another Mac, while it waits for one, or while it waits here for a suite's name, so a run whose suites all go to a lent Mac never takes one; the checkout is moved to the commit at every suite, since another run's suite may have been in it since. Each suite is run under that suite's own lock (`suite-<name>.lock` beside the slots), one call of `mac-suite.sh` a suite, so one suite of a name runs on the Mac at a time (the audio lane is one per Mac, `docs/simulator.md`) and, with two slots, one run's `topo_ui` overlaps another's `topo_unit` or `others`. The cap is on validation's suites: `others` boots a phone and a watch of its own, and a simulator another session booted is not counted. A run takes the first of its remaining suites whose lock is free, in the order they were chosen (`topo_unit`, `topo_ui`, `others`) or asked for with `--suites`, so one whose `topo_unit` a sibling is running goes on with its next and comes back. It waits three hours in all (for every slot and for suites, together), saying who holds what as a wait begins and every ten minutes, then exits 2 with nothing pushed or posted; the three hours begin again whenever, waiting for a checkout or for a suite's name, it finds a run that was ahead of it gone from the line or a slot in other hands than at its last look (which of a run's suites reads free is no part of it, since every waiting run asks those locks at each look), so a run deep in a moving line keeps its place however long the line is, and gives up only on one that has stood still for three hours. The wait for a slot is in the order the runs began: a run that waits takes a ticket in `~/Library/Caches/topo-validate/queue`, named for the microsecond the run began, by the clock that counts from the Mac's start, and its pid, and only the run whose ticket is first asks for a slot, every five seconds. The wait for a suite's name here is in the same line: a ticket names the suites its run still has to run here, and counts against a later run only while one of those names is free, so a run waiting for a suite a sibling is running holds up nobody whose suite is free, and has that suite before any run that began after it. A run reads the line and takes a suite's name and a slot as one step, under the line's own lock (`queue.lock` beside the queue), so no name changes hands to a run while another reads the line. A ticket whose process has gone holds nobody, and a run is out of the line for as long as it is running a suite, here or on another Mac, or asking another Mac, and back in its own place after; one that has just let a slot go with a suite still to run is back in its place at once, so the run that began first runs its next suite here before a later run's. The wait for another Mac is in no order. A simulator run by hand that is not a validation (a mutant run, a perf run) takes the slot the same way: `scripts/validate-and-push.sh --hold -- <command>` waits in the line, runs the command with the slot held and exits as it did, running no suite and pushing and posting nothing. Each suite runs on a simulator the run created and deletes, so no worktree's simulator is shared, and `mac-suite.pids` in the logs lists the pid of the suite's script and the commands it is waiting on (CLAUDE.md, *Working here*). A signal to the script ends its suite, which stops its lane and deletes its simulators. A SIGKILL ends the script alone and frees its locks with the suite still going, so the suite's pid and name are kept in its slot, and while it lives no run of this script takes that slot or starts a suite of that name: the run that waits names the pid to end. A suite SIGKILLed itself leaves its simulators behind, named `topo-validate-<label>-<pid>`, and the next suite to make one deletes every such device whose pid is not running first. Each suite's and each slot's holder (`suite-<name>.holder`, `slots/<n>/holder` under the cache), the label a waiting run reads, is removed as what it labels is let go; the lock is what holds it.
- **Another Mac, by hand.** `scripts/validate-host.sh on thicc-boi` on buddybox, once the laptop's person has unlocked it, lends it to validation: it writes the name into `~/Library/Caches/topo-validate/hosts`, which every run reads, and starts a `caffeinate` on the laptop that keeps its display on and counts its person as present for six hours (a number after the name asks for another, twelve at most), so it neither sleeps nor locks between suites; it refuses a Mac where the session of the user it reaches is locked or is not the one on the screen, and names nothing then, and a closed lid sleeps it whatever holds it awake. `scripts/validate-host.sh off thicc-boi` takes the name out, wherever in the file it stands, and ends that `caffeinate`: the one whose pid, hours and end `on` left on record there, and only while that pid is still that command and its hours are not up, so a `caffeinate` anyone else started is never ended. One `on` or `off` runs at a time, and `status` says who is named and held, and whether each is unlocked with its lid open now, since a hold keeps neither so (`mac-suite.sh --check` reads the same two before each suite). `TOPO_VALIDATE_HOSTS="thicc-boi"` in one run's environment names a Mac for that run alone, in place of the file, and holds nothing awake. No name is there by default and nothing finds a Mac or adds one. With one named, `topo_unit`, `others` and `scripts` run there first and on buddybox only when it is busy or cannot be used. `topo_ui` goes as two parts, each a suite of `scripts/mac-suite.sh` by its own name: `topo_ui:quiet` is every UI test class but `MicrophonePressTests`, with no audio lane, no hold on the display, no models and no test that opens a microphone or speaks (the runner's environment carries `TEST_RUNNER_TOPO_QUIET_LANE=1`, and `TopoApplication` in `Tests/ClientUI/TopoLaunch.swift`, the one application the UI suites launch, then sets `TOPO_DEBUG_EAR` and `TOPO_DEBUG_VOICE` to `loading` at every `launch()` and `activate()`, whatever the suite set before it; `QuietLaneTests` launches with a stub ear and the real voice asked for and reads both back from the app as loading. Ahead of the part, `mac-suite.sh` refuses a route round that class, and runs no test, when the token `XCUIApplication` is anywhere under `Tests/ClientUI` but `TopoLaunch.swift`, or `TopoLaunch.swift` does not name `TOPO_QUIET_LANE`; it parses nothing, so the word in a comment or a string is refused too. The proof is after the part's tests, before the run deletes their simulator: the app's data container there (`xcrun simctl get_app_container <udid> zone.hexagon.topo data`) holds no file under the ear's and the voice's homes in `Library/Application Support` (the ear's `Models/parakeet-tdt-0.6b-v2`, FluidAudio's `FluidAudio/Models`, and `Models/parakeet-ctc-110m-coreml`, the id a set made before its home sits under; the voice's store, `Voice/phonon-40m-en`, and the `Voice/phonon-40m-en.partial` its copy is made in; the rest of `Models/` is the guest's, which the part fetches), and the part fails naming each file it finds; no folder, or folders with nothing in them, is nothing fetched, and a container, a folder on the way to a home or a folder in one that cannot be read fails the part, named. A transfer still in flight is staged at the device's root (`<dataPath>/Library/Caches/com.apple.nsurlsessiond/Downloads/zone.hexagon.topo`) under an anonymous name, in the one background session the guest's downloads share, so what is there is listed in the log and judges nothing), and it goes to the named Mac as the other suites do; `topo_ui:mic` is that one class behind the lane, and so `real_ear`, and never leaves buddybox, whose audio lane it is. On the full lane `topo_unit` fetches Smart Turn's model into the cache too, beside Silero's detector (`scripts/fetch-ear-models.sh`, `TEST_RUNNER_TOPO_UNIT_EAR_MODELS`), for `SmartTurnRealTests`, the real model judging the fixture, and the fast lane leaves that class out by name rather than skip it. The microphone's part is the last thing the run does. One is everything but the class and the other the class, so a new class is in the quiet part and no test is in neither; `mac-suite.sh` holds each part's results to its side of that (`ci-require-tests.sh absent`, `named`). A UI test that opens the microphone or speaks belongs in `MicrophonePressTests`. The two are one status, `local/topo_ui`, a success when both are, naming where each ran. When the Mac is busy, cannot be used or loses the quiet part, `topo_ui` runs whole on buddybox in one call, as it does with no Mac named. On buddybox either part holds `topo_ui`'s name. The commit is pushed over ssh to a repository of that Mac's own (`~/Library/Caches/topo-validate/repo.git` there, under `refs/validate/<sha>` until the attempt ends) and checked out in a validation worktree of that Mac's, under its lock. A Mac that is busy says `busy:` in the run's log, not `error:`, so the summary a red run prints, its errors and the compiler's, is the suites' own. A lent Mac runs one validation's suite at a time unless it is lent for two (`scripts/validate-host.sh on thicc-boi 12 2`; `on` without the number is one again, and `status` says which): then two validations each have a checkout there (`~/Library/Caches/topo-validate/checkout` and `slots/2/checkout`), the simulators each suite makes for itself and its own build directories, and no two suites of one name run there at once, since `topo_unit` fetches the guest's files into the cache both checkouts share, and one suite of a name is what keeps two fetches apart. A third validation, or a second suite of a name, finds the Mac busy and runs here. A suite a killed run left going there keeps its checkout and its name until it ends. Each suite is asked for its 10 GB as it starts, so two that both passed can still run short together. `off` leaves the number where `on` wrote it, and a run that names the Mac for itself (`TOPO_VALIDATE_HOSTS`) reads it too. Before anything runs, the commit's `scripts/mac-suite.sh --check <suite>` says whether the Mac can run it and names what it lacks: the pinned Xcode, selected or installed beside the selected one, and XcodeGen, jq, a simulator of each pinned runtime, meson, ninja and Homebrew's llvm and lld unless the guest's framework there is current, 10 GB of disk as Finder counts it (purgeable space included, which `df` leaves out; when Finder's figure reads 0 or nothing, `df`'s is judged instead, and the refusal names which), an open lid and, for `topo_unit` on a Mac whose disk is encrypted, the session of the user the suite runs as on the screen and unlocked (FileVault gives no file complete protection while the screen is locked, and `TopoTests` asks that of files in the simulator's home). A suite that runs the scripts' tests, `scripts` or `others`, is asked for node and for a python3 that runs, which two of those tests run under (the stub a Mac with no developer tools has at `/usr/bin` is refused without being run, since it answers with a dialog on that Mac's screen); of `scripts` alone that, jq and the lid are everything asked. The suite runs in the Mac's login session where it has a way in (`/usr/local/libexec/gui-session-run`), under `caffeinate`, its display kept on so that it does not lock for idleness mid-suite, and with none of its person's git configuration (the script tests commit in scratch repositories, and a laptop that signs its owner's commits would ask a key of them for each), its logs are copied into the run's own under the host's name (the result bundles stay there, the five newest runs'), and its status says which Mac ran it. A Mac that is not reached, refuses, stops answering for a minute, or ends a suite with no result runs nothing more of that validation and the suite runs on buddybox: only a suite that ran to a result there has one, and a pass counts only when the connection outlived it. A red result the Mac wrote is red as buddybox's would be, whatever there made it so (its network, say), since `--check` looks once at what it names and no further. A signal to the script ends the suite there too, started or not, and is heard within about a minute and a half even when the Mac has stopped answering, in which case what it was running is left to end by itself.
- **The push follows a green run, and the statuses follow the push.** GitHub takes a status only for a commit it has. A red suite pushes nothing and exits 1. The commit is pushed to its branch by sha, without force. A push that fails is tried three times, a few seconds apart, since a GitHub 500 after every suite has passed would otherwise cost the whole run again; a branch that has moved to a commit this one does not carry is a refusal and is not tried again, and a push that failed but landed counts as pushed. A push to a PR that is ready and whose newest Codex verdict read an earlier head is refused before any suite runs, since it would start a review round nobody chose out of the four the cap allows (a fix after a verdict goes to a draft, and the coordinator marks it ready when it wants the round); `--after-verdict` pushes it anyway. A PR list or a comment read that fails is said and refuses nothing.
- **The result bundles hold the tests and nothing of the simulator.** Every test action runs with `-collect-test-diagnostics never`: without it xcodebuild runs `simctl diagnose` after the last test, which copies every crash report on the Mac and a log archive into the bundle, 320 MB a run that nothing reads, and its `log collect` stalls on buddybox often enough that three UI runs in seven waited the 600 s xcodebuild allows before giving up. A test's own log and attachments are in the bundle; a crash report is in `~/Library/Logs/DiagnosticReports` on the Mac that ran the suite.
- **Port 53 is lent, not bound.** `GuestDNSTests.testLookupSurvivesForwarderStop` stands a stub on port 53, since the guest's musl names no port; while a Tart VM runs on the Mac, vmnet's DNS proxy holds `*:53` and a bind of it is EADDRINUSE. A Mac that runs VMs keeps the port from its login (dotfiles `tools/port53-holder`, bound first with `SO_REUSEPORT`, which keeps every loopback datagram after the proxy binds beside it) and lends a copy over `~/Library/Caches/port53-holder/socket`; `mac-suite.sh` hands that path to `topo_unit` as `TEST_RUNNER_TOPO_PORT53_SOCKET` when the socket is there, and `StubDNS` borrows it, closing and never shutting down its copy. With none there, or one no holder answers on, the stub binds the port itself, and a VM running then fails the test with errno 48.
- **Silero's detector is loaded for real in `topo_unit`.** `mac-suite.sh` fetches it by name (`scripts/fetch-ear-models.sh <cache>/ear-models silero-vad-coreml`, 1 MB, verified against the manifest, with `smart-turn-v3` named beside it on the full lane) and hands the directory to the tests as `TEST_RUNNER_TOPO_UNIT_EAR_MODELS`; `SileroLoadTests` lays it where the app's own store keeps it (`ModelStore.standard(support:)`) and loads it through `Endpoint.silero`, the loader the app runs, and fails without the variable. The conversation's suite hands `Endpoint` a scripted detector and so proves nothing of where the model is kept.
- **The statuses** are `local/topo_unit`, `local/topo_ui`, `local/others` and `local/scripts`, `success` or `failure`, one per suite run, and `local/real_ear` beside a `topo_ui` that passed on the full lane. A suite with a `failure` line is posted as `failure` whatever else it wrote. Each description names the lane, the minutes and the logs (the logs alone, or the end of their path, under a root too long for GitHub's 140 characters), which are `~/Library/Logs/topo-validate/<sha>/` on buddybox, one directory per run inside it named for when the run began in UTC (`mac-suite.log`, each step's log, the result bundles), so a head run again after a red keeps the red run's logs. The ten newest commits are kept, and each one's five newest runs, and beside them any run that is still going, its push and its statuses included: a run marks its logs with its pid and when that began until it is over. A commit that was already origin's head, a draft pushed plainly, is posted to whatever the suites did.
- **`test`** requires a `success` under each context `select` said the PR needs, on the PR's head commit, and `local/real_ear` when the lane is not `fast`. The script posts straight after its push, so `test` waits two minutes for a status and no longer; a head validated later, every suite green, has its `test` job re-run by the script once that run has concluded with it red (`gh run rerun --job`), which is the only job it re-runs. A run still going when the statuses land is re-run by hand.

The reviewer runs only on a PR that is ready and whose `test` is green, so a suite that did not pass spends no round. A run learns whether the PR is ready from the API as it starts (`review_cap`), never from the event that started it: marking a PR ready and pushing to it a second apart start two runs on one head, the later one cancels the other (one run per PR, `cancel-in-progress`), and whichever survives reads the PR as ready.

A PR opened from a host with no Mac passes `test` only when its paths need no suite; anything else is validated from a worktree on buddybox. Nothing runs the suites on main on a schedule: a regression in recognition from a change off the voice path shows at the next commit whose paths take the full lane, or when a branch's pushed head is run through it by hand (`scripts/validate-and-push.sh --no-push --suites topo_ui --lane full`, from that branch's worktree; the script refuses main and a detached HEAD).

## What the UI tests can and cannot see

**`.accessibilityHidden(true)` does not take a view out of the XCUITest tree.** The element stays queryable, so a control that must be absent to a UI test has to leave the layout (an `if` around the view), not be hidden in place.

**Every test case passes: none is skipped and none is an expected failure.** `scripts/ci-require-tests.sh` reads the result bundle and fails a case whose result is `Skipped` or `Expected Failure` as it fails a red one, since neither proves what it names. So `XCTSkip` and `XCTExpectFailure` are both refused: a test of a known defect lands with its fix, not ahead of it marked as expected to fail.

**A headless simulator has no hardware keyboard and no route to connect one.** CI refuses `XCTSkip`, so a path that only exists with a keyboard focused (the composer taking focus with no bar press) can have no UI-test proof. A PR that changes such a path proves it with unit tests over the form state and a device box on a phone with a hardware keyboard — this page states the rule; the proof belongs to that PR.

**A plan that promises bar room measures it first.** On a 402 pt phone the bar holds 196 pt beside its model and mute controls, so a plan written as "notices fit whole at the largest font" could not hold. Measure on the smallest supported phone at the largest Dynamic Type before writing the plan line.

## The voice's asset pack against a mock server

The Background Assets path — the pack downloaded, `PhononStore` copying it and removing the pack — can be run on a simulator against Xcode's mock server, `xcrun ba-serve`, by hand. It is not part of the PR check, and the Apple-hosted path is otherwise proven on the first TestFlight build.

1. The server needs an SSL server identity for `localhost` that the Mac trusts: one issued by a root CA trusted in the login keychain, which takes a person at the Mac's console to approve.
2. Package the pack (`scripts/phonon-bundles.sh package`, which writes `build/phonon/phonon-40m-en.aar`) and serve it: `xcrun ba-serve serve build/phonon/phonon-40m-en.aar --asset-pack-versions 1 --host localhost --choose-identity-automatically`.
3. Trust the CA in the simulator: `xcrun simctl keychain <udid> add-root-cert ca.pem`.
4. Point the simulator's Background Assets at the server. The override is the `MBAURLOverride` key of the `com.apple.backgroundassets.managed` defaults domain: set it on the Mac with `xcrun ba-serve url-override https://localhost:64496`, `defaults export com.apple.backgroundassets.managed <file>`, and clear it on the Mac at once (`xcrun ba-serve url-override --clear`); then `xcrun simctl spawn <udid> defaults import com.apple.backgroundassets.managed <file>` and reboot that simulator.
