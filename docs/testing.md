# Tests and the PR check

Every suite's own description sits with the code it holds (the guest's in `docs/guest.md`, the mascot's in `docs/mascot.md`, the packages' in `docs/cloudkit.md`). Running the app signed in, the microphone press, the audio lane and the talk lane are `docs/simulator.md`.

## The debug launch environment

A simulator is signed in from its launch environment, not by hand: `Apps/Client/DebugRun.swift` (all of it behind `#if DEBUG`) takes a Claude Code setup token from `TOPO_CLAUDE_SETUP_TOKEN` and writes it to the store as a finished sign-in, puts a turn on the harness's line from `TOPO_DEBUG_OUTBOX` (empty clears it) so a launch can be the relaunch that finds one owed, and takes one turn from `TOPO_DEBUG_SEND` through the ordinary harness, waiting first for the guest to be ready (`guest: waiting: …`, then `guest: ready`), printing each step prefixed `[topo-debug]`, each pose Topo takes from the guest's turn (`mascot: turn began for <turn>, process P, …`, `mascot: …`, `mascot: turn gone for <turn>, …`, naming the turns the guest turn answers), and the reply as `reply to <nonce> in run <run> from session <id>, process <pid>: <text>`.

A `--userland` run (`docs/simulator.md`) prints `userland: dns forwarder on 127.0.0.1:<port>` once the guest is booted; launched with `TOPO_DEBUG_DNS=stopped` (`DebugRun.dnsVariable`), it stops the forwarder instead, as iOS taking its listeners would, waits for the phone's name servers to be written to the guest's `resolv.conf`, and prints `userland: dns forwarder stopped` before the command runs.

## The PR check

The suites run on buddybox, not on a hosted runner: a macOS runner bills at ten times a Linux one, and the three suites are about 77 runner-minutes a push against the account's 2,000 free minutes a month. An engineer pushes with `scripts/validate-and-push.sh`, which runs the suites at the commit being pushed, pushes it only when they pass, and posts each suite's result to that commit as a status; `pr-validate.yaml` runs on ubuntu alone and its `test` job, the required check the merge waits on, reads those statuses. A commit pushed any other way has none, and its `test` is red until the script is run on it.

There are three suites (`scripts/mac-suite.sh`): the Topo scheme's test action split by test selection into the UI tests (`topo_ui`) and everything else (`topo_unit`), and the scripts' tests, the packages, Womble, the watch's suite (`TopoWatchTests` on a watch simulator from the pinned watchOS runtime, booted and waited on with `simctl bootstatus -b` before the run, bounded at 15 minutes) and the watch, TV, Release and hub builds (`others`; the watch build is read for its widget extension, background mode and URL scheme by `scripts/check-built-plist.sh --watch`). The script holds the toolchain to its pins (Xcode, the iOS and watchOS simulator runtimes, XcodeGen), generates the projects from `project.yml`, and builds the guest's framework before any suite.

A commit runs only the suites its paths need, chosen the same way in both places. The `select` job reads the paths the PR changes against main and matches each against `SUITE_RULES` in the workflow (`scripts/ci-select-suites.sh`, first rule wins): documentation, root markdown, the other workflows, `.claude/`, `.gitignore`, and the TestFlight and plan-review tooling need none of the three; the hub, watch and TV targets, the watch's widget extension and suite, Womble and `TopoLink`, which the app does not compile, and the janitor and `validate-and-push.sh`, whose tests run there, need `others` alone; the app's sources, every package the app links, the tests, the project, the guest patches, the workflow and its other scripts, and any path no rule names need all three, as does a diff that cannot be read. `validate-and-push.sh` reads the same list out of the commit's own workflow and runs the commit's own copy of that script, not the worktree's, over the commit's diff against its merge base with origin/main. `scripts/tests/ci-select-suites-test.sh` pins the rules and their cases. The two read different diffs once main has moved under a branch, so `test` can name a status the script's choice left out: `--suites` and `--lane` run what it names.

`validate-and-push.sh`, from the worktree whose HEAD is the commit:

```sh
scripts/validate-and-push.sh             # run the suites the commit needs, push it, post the statuses
scripts/validate-and-push.sh --no-push   # a commit origin's branch already holds: run, post, re-run `test`
scripts/validate-and-push.sh --suites all --lane full
```

- **What runs is the commit.** The suites run in one of the Mac's validation worktrees, a slot (`~/Library/Caches/topo-validate/slots/<n>/checkout`, a detached worktree of the checkout), checked out at the commit and cleaned of untracked files, so an uncommitted change or a stray file in the engineer's worktree is not in the result, and XcodeGen's regenerated projects are not written over the engineer's. A slot's path never changes, so its DerivedData, the guest's framework and `build/` stay warm between runs.
- **Two runs at once, in two different suites.** A run holds a slot's lock for the whole of it, and there are two slots (`TOPO_VALIDATE_SLOTS`), so two runs are in two checkouts and a third waits for one. Each suite is run under that suite's own lock (`suite-<name>.lock` beside the slots), one call of `mac-suite.sh` a suite, so one suite of a name runs on the Mac at a time (the audio lane is one per Mac, `docs/simulator.md`) and one run's `topo_ui` overlaps another's `topo_unit` or `others`. A run takes the first of its remaining suites whose lock is free, in the order they were chosen (`topo_unit`, `topo_ui`, `others`) or asked for with `--suites`, so one whose `topo_unit` a sibling is running goes on with its next and comes back. It waits three hours in all (for a slot, for suites, and for a run of the script as it was, together), saying who holds what as a wait begins and every ten minutes, then exits 2 with nothing pushed or posted; nothing makes the waits first come, first served. Each suite runs on a simulator the run created and deletes, so no worktree's simulator is shared, and `mac-suite.pids` in the logs lists the pid of the suite's script and the command it is waiting on (CLAUDE.md, *Working here*). A signal to the script ends its suite, which stops its lane and deletes its simulators. A SIGKILL ends the script alone and frees its locks with the suite still going, so the suite's pid and name are kept in its slot, and while it lives no run of this script takes that slot or starts a suite of that name: the run that waits names the pid to end.
- **Beside a branch that has not merged main.** Such a branch runs the script as it was: one lock (`~/Library/Caches/topo-validate/lock`) held for its whole run, in one checkout beside it. A run of this script holds that lock shared from its checkout to its last suite here, so the two kinds are never going at once, while runs of this script share it; it waits for the lock asleep on it, half a minute at a time. A run of the script as it was therefore waits for as long as any run of this one is going, and gives up after its own three hours. That script looks for a suite left running without its script in one record beside its lock, so a slot's record is kept there too, and it refuses to start beside a suite a run of this script left behind.
- **Another Mac, by hand.** `TOPO_VALIDATE_HOSTS="thicc-boi"` in the run's environment, or a line of `~/Library/Caches/topo-validate/hosts` on buddybox while that variable is not set, names ssh aliases a run may use; neither is there by default, nothing finds a Mac or adds one, and a laptop named has its lid open. With one named, `topo_unit` and `others` run there first and on buddybox only when it is busy or cannot be used; `topo_ui`, and so `real_ear`, never leave buddybox, whose audio lane it is. The commit is pushed over ssh to a repository of that Mac's own (`~/Library/Caches/topo-validate/repo.git` there) and checked out in its one validation worktree under its own lock, one suite at a time. Before anything runs, the commit's `scripts/mac-suite.sh --check <suite>` says whether the Mac can run it and names what it lacks: the pinned Xcode and XcodeGen, jq, a simulator of each pinned runtime, meson, ninja and Homebrew's llvm and lld unless the guest's framework there is current, 10 GB of disk as Finder counts it (purgeable space included, which `df` leaves out), an open lid. The suite runs in the Mac's login session where it has a way in (`/usr/local/libexec/gui-session-run`) and under `caffeinate`, its logs are copied into the run's own under the host's name (the result bundles stay there, the five newest runs'), and its status says which Mac ran it. A Mac that is not reached, refuses, or ends a suite with no result runs nothing more of that validation and the suite runs on buddybox: only a suite that ran to a result there has one.
- **The push follows a green run, and the statuses follow the push.** GitHub takes a status only for a commit it has. A red suite pushes nothing and exits 1. The commit is pushed to its branch by sha, without force.
- **The statuses** are `local/topo_unit`, `local/topo_ui` and `local/others`, `success` or `failure`, one per suite run, and `local/real_ear` beside a `topo_ui` that passed on the full lane. A suite with a `failure` line is posted as `failure` whatever else it wrote. Each description names the lane, the minutes and the logs (the logs alone, or the end of their path, under a root too long for GitHub's 140 characters), which are `~/Library/Logs/topo-validate/<sha>/` on buddybox, one directory per run inside it named for when the run began in UTC (`mac-suite.log`, each step's log, the result bundles), so a head run again after a red keeps the red run's logs. The ten newest commits are kept, and each one's five newest runs. A commit that was already origin's head, a draft pushed plainly, is posted to whatever the suites did.
- **`test`** requires a `success` under each context `select` said the PR needs, on the PR's head commit, and `local/real_ear` when the lane is not `fast`. The script posts straight after its push, so `test` waits two minutes for a status and no longer; a head validated later, every suite green, has its `test` job re-run by the script once that run has concluded with it red (`gh run rerun --job`), which is the only job it re-runs. A run still going when the statuses land is re-run by hand.

The reviewer runs only on a PR that is ready and whose `test` is green, so a suite that did not pass spends no round. A run learns whether the PR is ready from the API as it starts (`review_cap`), never from the event that started it: marking a PR ready and pushing to it a second apart start two runs on one head, the later one cancels the other (one run per PR, `cancel-in-progress`), and whichever survives reads the PR as ready.

A PR opened from a host with no Mac passes `test` only when its paths need no suite; anything else is validated from a worktree on buddybox. Nothing runs the suites on main on a schedule: a regression in recognition from a change off the voice path shows at the next commit whose paths take the full lane, or when a branch's pushed head is run through it by hand (`scripts/validate-and-push.sh --no-push --suites topo_ui --lane full`, from that branch's worktree; the script refuses main and a detached HEAD).
