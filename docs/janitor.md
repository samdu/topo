# The janitor

The mechanical upkeep of the pipeline: `scripts/janitor.py`, one pass every fifteen minutes on buddybox as `buddy`, in the GUI session so it has the login keychain the OTA build signs with. It is a script and not a session: every decision is a function of what it read, every action is a `gh`, `git`, `tmux` or shell call, and `--dry-run` prints the pass instead of running it. It reads no review, merges over no red or missing verdict, edits no code, and says nothing to Sam.

## What a pass does

1. **Merges what automerge left.** A ready PR on `main` whose newest `pull_request` validate run for its head — among the runs GitHub ties to that PR's number, since two PRs can share a head and one's green run is not the other's — is green, whose description has no unchecked box, and that carries the `automerge` label when the repository's `AUTOMERGE_REQUIRE_LABEL` variable is `true` — the conditions `automerge.yaml` merges on — still open fifteen minutes after that run last changed, is squash-merged with the branch deleted, pinned to the head the green run was read for (`--match-head-commit`), so a push between the read and the merge is refused rather than merged unvalidated. Automerge misses a PR when the event that would have fired it is dropped or arrives before the run is green; the janitor is the backstop, not a second policy. A label rule it cannot read merges nothing and is reported; a merge GitHub refuses is reported with the refusal.
2. **Reruns an infrastructure red once.** A validate run whose reds are the infrastructure's has its failed jobs rerun once per PR and head, ten minutes after the run last changed and only when it is the newest run for that head. Two shapes count, and no other: a suite job (`topo_unit`, `topo_ui`, `others`) concluded `failure` where every step that did not pass is a runner step (`SETUP_STEPS` and `SETUP_PREFIXES` in the script: booting the simulator, the audio lane, a model cache, the checkout and upload actions) or where no step of its own failed at all, which is a runner lost; and the reviewer chain (`review_cap`, `codex_wait`, `codex`, `post_feedback`, `reviewer_ran`, `review_gate`) red with `reviewer_ran` among the reds and nothing outside the chain red — Codex out of quota, a login gone stale. A red job outside the suites, the `test` gate (red whenever a suite job is) and the reviewer chain (which waits on the suites) — `select`, or a job this script does not know — is the run's own and holds the rerun even beside a runner red. A test, build or script step cancelled by its `timeout-minutes` (a setup step cancelled by its own is the runner's, as its failure is), a suite job cancelled or timed out, and any red at the prepare action, the pinned-inputs fetch, a build, a script test or the tests are the code's or the run's own, whatever the other jobs did: never rerun, and reported as idle in time. Red again after the one rerun, the run is reported with its red jobs and, for a suite job, the failing tests read off the log. A red `review_gate` with `reviewer_ran` green is a verdict, or, with `codex` skipped or `post_feedback`'s `Report Codex feedback` step skipped, the review cap: reported at once, whatever else on the run is red, and never rerun for its own sake — Codex runs beside the suites, so a blocking review and a runner red on the same run are both said, and the runner red is still rerun once.
3. **Republishes the install page** when the commit in its `version.json` is not origin/main's, by running `publish-topo.sh origin/main` from the `ota` experiment in samdu/experiments. The attempt is recorded, and the state saved, before the script starts, so a publish that gives no answer inside 45 minutes (killed, and said so), or one the pass died under, counts as tried: nothing is tried again for that commit for two hours, a success included, since the page lags the pod bounce by a minute. A failed publish is reported with the tail of its log. A page that cannot be read or is not JSON is reported and republishes nothing, since a page that did not answer is not a page that is behind.
4. **Sweeps worktrees.** A linked worktree of the main checkout is removed when its branch has no open PR, its tip is exactly the head a PR on that branch was merged at, that merge is more than a day old, and `git status` in it is clean. A reused branch name (an older PR merged at another head, a newer one open) and a tip with commits past the merged head both match nothing. The clean check comes first; only then is every tmux session with a pane in the worktree or under it killed (`kill-session -t =name`, exact), from a pane list tmux answered — no server running is no sessions, but a `list-panes` that fails for any other reason stops that worktree's sweep with the error in the report, since a session that could not be seen is not one that is not there. Then the tip is read again — every call before it took time, and a session that was not in the worktree (an engineer's pane sits at the checkout) may have committed to it meanwhile — and a tip that moved is reported and left; the branch's PRs are read again before the kills and once more right before the remove, and a PR opened meanwhile keeps its worktree (and, before the kills, its sessions). Only then is the worktree removed, and the branch ref deleted with `update-ref -d` given the merged head as its expected value, which git refuses if the ref has moved: a commit landing at any point is kept, and the report says the ref was. A worktree with uncommitted changes is reported and left with its sessions. Detached worktrees, and the checkout itself, are never touched. A branch's PR history is read with a page of 100 and refused as unwhole if it fills the page, so a worktree on such a branch is reported and left rather than swept on a list that may have left its open PR off.
5. **Reports a ready PR that needs a person**, once, and again only when the PR changes: a verdict that blocks (the review is on the PR, and the session that opened it may not carry the channel that would deliver it); the review cap reached (`review_gate` red beside a green `reviewer_ran` with no verdict posted that run: four Codex verdicts, and the PR waits on Sam's word or a replan); an open PR list that filled its page of 200 (read as unwhole: nothing is merged, rerun or reported off a list that may be missing a PR); a green PR with Proof boxes unticked; a ready PR with no validate run; a run cancelled with nothing after it; and a PR nothing has touched for forty-five minutes while no run is in progress, with the run's conclusion and its red jobs. A draft is never read or reported: it is at gate one, the coordinator's (`docs/process.md`), its suites run on every push, and the reviewer waits for it to be marked ready. What was said of a PR is kept as a fingerprint — its head, the count of unticked boxes, its labels, base and review decision, the run's status and conclusion, every job's conclusion, and which of the conditions above hold — and its lines are said again, all of them, only when that fingerprint differs from the one last said: a new commit, a box ticked, a check flipped, a verdict. No age is in it, and no updated-at, so a PR that only got older, or a comment on, says nothing; nor is the idle condition, which is age alone, so a PR already reported is not said again for having sat. The record stands until the PR leaves the open list, through a run in progress included, so a red rerun by hand into the same red is silent. That is also how a line is answered: once buddy-prime has read it, nothing arrives until the PR itself moves.
6. **Reports every untriaged issue.** A GraphQL read (`gh api graphql`, `repository.issues(states: OPEN, first: 100)`, paged on `endCursor`, at most five pages) gives each open issue's number, title, age, updated-at, labels (up to 100, with whether more stand) and comment count, and never its body, which can hold a token or a person's data. An issue with no `triaged` label and no comment, older than `GRACE`, is reported as `issue: #N <title>, opened <age> ago, untriaged.`, with ` (filed by Topo)` after the title when it carries `from-topo`; once, and again only when its labels or its updated-at change, which are its fingerprint. Triage is buddy-prime's: a comment on the issue (a plan named, a roadmap line, a question for Sam) or the `triaged` label, and either silences the line. `repository.issues` holds no pull request. A list that still has a next page after the fifth is read as unwhole: no issue is reported off it, and one line says the list was not read whole. A read that fails is said, and reports nothing; a read that answers ends that failure, so the next is said at once. A node that is not a whole issue (null, or a number, title, either date, label list or comment count missing or of the wrong type, or a label list with a further page, which may have left `triaged` off it) is skipped, and one line names the first ten and counts the rest, and the rest of the list is read as usual; one with no number drops no issue's key that pass, since it may be that issue. Issue lines are the first cut of a report, because the PR lines are the ones that carry a merge: a pass says at most `ISSUE_LINES` (60) of them, within what `PENDING_MAX` leaves after its other lines, and says how many more wait; a report the other lines already fill takes no line of this step at all, the notice included. While an earlier report is undelivered the step adds no line at all — no issue, no read failure, no page or malformed-node line — so a queue waiting on the bridge fills with PR lines. An issue line not said records nothing of its issue, so a later pass says it.

**The digest.** An item whose fingerprint has not moved is silent however old it gets. Once per `DIGEST` (24 h), while anything stands, one line names what stands and was not said that pass: `still standing, unchanged since it was said: #N (conditions), …; untriaged issues #N, …`, the first forty of each and a count of the rest. A pass with nothing new and no digest due sends nothing.

**A first run.** A state file that is missing, is not JSON, or holds no whole record of what was said (`reported`) is a first run: every PR and issue that stands is recorded and named in one digest line, `first pass with no record of what was said; standing now: …`, and none is said line by line, so a lost file is one line and not a flood. The PRs and the issues are each a first run until a pass has read them whole, so an issue read that failed on that pass is still one digest line on the pass that reads it. What the file held of things done — reruns, publishes, undelivered reports — is kept when it is readable.

The repository carries two labels for this, and they mean nothing else: `triaged` (buddy-prime has read it: planned, parked or put to Sam) and `from-topo` (the mind on the phone filed it). Every issue is filed as `samdu`, so the author tells nothing; the label is the only mark of Topo's, and an issue without it is reported all the same.

Thresholds are constants at the top of the script: `GRACE` (15 min: automerge's chance, a box's, a cancelled run's, a ready PR's with no run), `SETTLE` (10 min before a rerun), `IDLE` (45 min), `REPEAT` (24 h), `DIGEST` (24 h), `SWEEP` (24 h), `PUBLISH_RETRY` (2 h), `PUBLISH_KEEP` (7 days), `PENDING_MAX` (200 lines), `ISSUE_LINES` (60), `ISSUES_PAGES` (5). A line about the janitor's own work that stands while its condition does — a refusal, a read that failed, a worktree left — is keyed by the condition and the head (or the worktree) and said once per `REPEAT`; a read that answers ends its failure, so the next one is said at once. A merge, a rerun, a publish and a sweep are said each time they happen.

## Where the report goes

One message per pass that did something or found something new, posted to **buddy-prime**'s mesh bridge over the fleet's authenticated route — `POST /mesh/buddy-prime/deliver` on the LAN Traefik, the same call buddybox's own bridge makes when it forwards — with `from` this host's verified mesh name, `buddy-janitor`, `sender` `topo-janitor`, and this host's peer token as the bearer. It arrives in buddy-prime as a turn from `buddy-janitor/topo-janitor`, and, like every relayed message, is mirrored in full to `#agent-mesh`. No report wants an answer, and its first line says so (`No reply is read: topo-janitor is a script with no session, so do not answer this.`): the receiving bridge ends every relayed message by asking for a reply with `SendMessage`, and one sent to `topo-janitor` is addressed to no session, is refused by buddybox's bridge, and holds buddy-prime's queue to this host behind it until it expires. A report the far bridge does not take — no answer, an answer that is not whole, a 403, a 503 — is kept in the state file as the message it was, id and lines, and sent again first on the next pass, exactly as it was, before that pass's own report goes under a new id: a bridge that took the message before answering badly sees the retry as the message it already has, and never a bigger message under that id. A message the bridge does not take holds every message after it. Of more than 200 lines standing, the oldest messages go whole, then the newest is cut, and a message of its own says how many lines went, so no message already sent is re-sent with other text; a 400 is the bridge refusing that message for good, and it is dropped with a note in the log. buddy-prime is the coordinator (`docs/process.md`): what it does with a line is its judgement, and nothing here reaches Sam directly.

It does not go through the local `~/.claude/sessions/` registrations: on buddybox the bridge registers its roster peers under thread ids, which macOS does not count as live processes, so the bridge's own sweep removes them within a minute and no local `buddy-prime` socket stands.

## What it holds

The launcher reads `GH_TOKEN` out of `~/.bashenv.local` and exports that one variable, nothing else the file holds; it is Sam's classic PAT (`repo`, `workflow`): the merge, the rerun and every read are made as him, and the token is what lets `gh run rerun` touch Actions. `~/.mesh-bridge-env` holds `BRIDGE_PEER_TOKEN`, this host's own mesh identity, read by the janitor for the report and never logged. The publish runs `publish-topo.sh`, which pushes to samdu/experiments as the checkout's git credential and bounces the `ota` deployment with `~/.kube/config`, scoped to the experiments namespace, and signs with the Apple Development identity in buddy's login keychain, which is why the pass runs in the GUI session. Nothing of this reaches a log line or a report.

## State

`~/.local/state/topo-janitor/state.json`, outside every checkout: the fingerprint last said of each PR and issue (`reported`), which of the two lists a pass has read whole (`seeded`), when the last digest went (`digest_at`), which of the janitor's own conditions fired and when, which heads have had their rerun, each publish attempt by commit with its outcome (`null` while it runs, or if it never answered), and the undelivered reports, each with the id it was sent under. Written whole to a temporary file and renamed, after every action that changed the world — a merge, a rerun, a publish begun and a publish ended, a sweep — and again as the pass ends, whatever ended it: an error anywhere in the pass, or a SIGTERM (`launchctl bootout`, a reboot) under a running publish, is caught, said in the report as the pass stopping early, delivered and saved. So nothing is done twice for want of a record and nothing said is lost. A PR's record and the keys for heads no open PR carries are dropped at the end of a pass that read the PR list — never on one that could not, since an unread list is not an empty one — and an issue's record at the end of a pass that read the whole issue list and found it closed or triaged, never on one whose read failed or was not whole; publish records after a week, a sweep's once its worktree is gone. A key of the wrong shape is dropped on reading, and the record of what was said with it when it is not whole, which makes the pass a first run. `state.json.lock` is held for the pass, and a pass that finds it held exits.

## Running it

The LaunchAgent `zone.hexagon.topo-janitor` (dotfiles, installed by `setup.sh` on buddybox) runs `tools/topo-janitor` every fifteen minutes: it fetches origin and runs `scripts/janitor.py` as it is on origin/main, so the janitor is never the checkout's stale copy and never edits the checkout. By hand:

```sh
scripts/janitor.py --dry-run --verbose    # decide everything, run nothing, print the report
scripts/janitor.py                        # one pass
```

`scripts/tests/janitor-test.sh` holds the decisions over scripted readings and whole passes against a fake `gh`, `git`, `tmux` and `curl`, with buddy-prime's bridge played by a loopback server, in the PR check.
