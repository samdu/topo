# Sign in with Claude, and connections

How the phone signs in to Claude, and the services it is connected to on the person's behalf. The guest's side of the login is `docs/guest.md`.

## Sign in with Claude

The login is Claude Code's own, in the guest's unmodified `claude`: the OAuth client, the redirect, the code exchange and the stored credential are all Claude Code's, and Topo holds no Claude.ai token. `SignIn` (`Packages/TopoAuth`) drives it through a `ClaudeLogin`, which on the phone is `GuestLogin` (`Apps/Topo/GuestLogin.swift`):

1. **Ready.** The sign-in screen waits for the rootfs and Claude Code to be on the phone and the guest to boot (`SignIn.prepare`, "Getting Topo ready…" over the downloads' line), then offers *Sign in with Claude*. No sign-in happens before the guest is up.
2. **Login.** `claude auth login --claudeai` runs in the guest from the home (`/home/topo`, the app's `Library/Application Support/home`) with no resident beside it (`GuestSession.withoutResident`): the two are `claude` processes over one credentials file, and a resident reads its login once, as it starts. Its environment is the guest's and the tool service's, with `BROWSER` set to `topo-browser` (`GuestTools.browser`), which hands the URL it is given to `topo open-url`, and no `ANTHROPIC_BASE_URL`: the exchange goes to Claude's hosts directly.
3. **Approve.** `topo open-url` (`OpenURLTool`) hands the URL to the sign-in waiting for its browser (`LoginBrowser`), and only then, and only an https URL on `claude.com`, `claude.ai` or `platform.claude.com` with no user, password or port; any other call is refused, so no other guest process can put a page on the phone. The screen opens it in `WebAuth`'s sheet (not ephemeral, so the person is often already logged in). Its `redirect_uri` is `http://localhost:<port>/callback`, claude's own listener, which binds `127.0.0.1` only; guest sockets are the app's, so the sheet reaches it. claude exchanges the code itself, writes `~/.claude/.credentials.json` in the home, serves its own success page and exits 0.
4. **Signed in.** On exit 0 the app runs `claude auth status --json` and needs `loggedIn` and `authMethod == "claude.ai"` (`ClaudeLoginStatus.isClaudeAI`); exit 0 without it is a failure on the screen. The fact and the subscription, no token, are kept in the app's defaults (`LoginCache`) for the callers that ask before any guest is up: the role at launch, the memory, the sign-in screen's first frame and the resident's launcher, which refuses a launch while it says signed out. Every boot of the guest asks `auth status` again before any process starts (`GuestResident.booted`, `SignIn.refresh`), so a login that has gone puts the screen back on the sign-in; a status that cannot be read changes nothing. Claude Code refreshes its own tokens from then on.
5. **Paste fallback.** The same login prints a second URL on stdout, whose `redirect_uri` is Claude's hosted code page (`GuestLogin.pastePage`). When the loopback cannot be reached the browser stops on a connection error; the person closes the sheet, and *Open the page again* opens that page (`SignIn.openPageAgain`) and shows the field: the `code#state` it shows is written to the login's stdin (`SignIn.paste`). With no login running any more, *Open the page again* starts a fresh one. A code that cannot be written ends the login, through the queue below, before the screen offers the sign-in again; a write that fails for a login cancelled or replaced meanwhile reaches nothing.
6. **Ending.** Cancel ends the login: claude does not exit when its stdin closes, so the app ends the process (`GuestLoginAttempt.end`, every guest task, since nothing else runs beside it; a login that has already exited is not ended, since the resident may be starting again). Closing a sheet ends nothing, since closing the loopback's is how the person reaches *Open the page again* and closing the paste page's is how its code reaches the field. Every start, every login's end and every logout runs in one queue, in order (`SignIn`), so a login begins only once the end of the one before it and any logout have run: nothing that ends every guest task runs beside a live login. `Login failed: …` (exit 1, a bad state or code) is what the screen says, read once the process is reaped and both its pipes have closed, so stderr's last line is in. Only the sheet that is up reports its close (`WebAuth`), and only the sheet the sign-in has now (`SignIn.sheetClosed`); what an attempt ended, cancelled or replaced says afterwards reaches nothing (`SignIn`'s generation).

**Sign-out, takeover, demotion.** Each ends with `SignIn.signOut`, last, after the harness, the memory and the connections: the cache is cleared at once, so nothing launches on the login from that moment, and then `claude auth logout` runs in the guest with no resident beside it, when the guest is up in this process, and the credentials file is removed from the host side whether or not it ran, with any copy an earlier build left in `Documents/home` (`GuestLogin.credentialsFiles`; the sign-out is not done while either stands) (`GuestLogin.logout`). Each is removed through its folder opened with no link followed: a link the guest left at `.claude` has nothing removed through it, and the sign-out stays owed, since what stands behind it is no place the app can see. A sign-in after it waits for that logout in the queue, and a `refresh` while it is owed changes nothing. The sign-out is owed (`SignIn.signOutOwedKey`, in the app's defaults) from its first step until the credentials file is gone or a later sign-in has written a new one, so a sign-out the app died in, or whose file would not go, is finished at the next launch: the file is removed as the sign-in is made, before anything reads it, and the logout is queued again, which with no guest up yet in that process is the removal alone. The login does not outlive a delete of the app: the credential is in the app's container.

**What a feature holds under the login.** Four paths end a login: the settings sheet (`SignOut`), a takeover (`Takeover`), a viewer's arrival (`ViewerArrival`), and the phase leaving signed in with none of their steps run, which is a `refresh` finding the login gone and which the app's phase observer hands to `DefaultSurface.follow`. All four go through `LoginLife` (`Apps/Client/LoginLife.swift`), so a feature that holds work under a login registers there once and is ended on every one of them, and a guard written for it checks the epoch rather than a counter of its own. `ActivityKeeper` and `topo activity` check the epoch. `SurfaceSync` (`signOuts`) and `TurnImages` (`age`) check counters of their own that only their teardown moves, `WidgetActions` cancels its runs, and the share door, `GuestImages`' age and the generations `Connections`, `Memory` and the harness keep are outside `LoginLife` (the last three also move on a cancel, a disconnect or a superseding request, which no login's end is). Its epoch (`LoginLife.epoch`) moves at the first step of each sequence, before anything is waited on, again as the teardowns run (for work begun while the sign-out was under way), and at the phase leaving signed in: work begun under the login takes `let epoch = login.epoch` before it awaits, and checks `epoch.isCurrent` before it keeps or changes anything after, dropping itself when the login has ended since. From a login's teardowns until the next sign-in (`LoginLife.began`, which moves the epoch again and is run by `SignIn.beginning` as the login begins, before the cache says signed in and the phase moves: the resident's launch checks the cache, and the foreground launches one with no turn, so what it takes is the new login's epoch and not one the next render moves) no epoch is current at all, so work begun in that gap — after a sign-out's last step, or before a teardown's own task has started — keeps nothing either. A feature's teardown is registered with `onEnd` (or `onEnd(awaiting:)` for one that has to await, as `ActivityKeeper.endAll` does) and is run (an awaiting one started) just before the surfaces go (`runTeardowns`, the step before `forgetSurfaces`), on all four paths, a viewer's arrival with no login included. A teardown runs under the moved epoch and never checks it: one guarded by `isCurrent` would never run. The registered teardowns are the activities' end (`ActivityKeeper`), the widget runs in flight (`WidgetActions.cancelAll`), the pictures read for the bubbles (`TurnImages`), this phone's `Surface` records (`SurfaceSync.forget`) and what the login's requests uploaded (`ThreadSampler.clear`). They run once a login: a sign-out, a takeover or an arrival has run them by the time its last step moves the phase, so `DefaultSurface.follow` runs them, and clears the surfaces, only for a login whose end has not run its teardowns (`LoginLife.standing`), which the next sign-in resets (`began`). A feature's suite builds it with a `LoginLife` of its own, parks the work on a gate, and signs out with `SigningOut.midFlight(login, reached:release:)` (`Tests/Client/SigningOut.swift`), which fails when the work never reached its gate, then moves the epoch, runs the teardowns, releases the work and waits for every teardown to finish; `LoginLifeTests` holds the rules themselves and the refresh path's effects.

**Where the credential rests.** `.credentials.json` is in the guest's home inside the app container, which `GuestResident.makeHome` excludes from backup and makes, with `.claude` beside it, under `completeUntilFirstUserAuthentication`, so the file claude writes there takes that class; anything but a folder at `.claude`, a link the guest made there included, is refused by name and not followed. Any guest process can read it: a full-scope, refreshable Claude.ai credential (CLAUDE.md, *The holes in the guest*).

**The update from the earlier login.** A build before this one kept Claude.ai tokens in two keychain items (service `zone.hexagon.topo.claude`, accounts `claude` and `claude-guest`). Every launch deletes both (`LoginMigration`, on the phone and on the hub), each whether or not it can be read, so a delete the keychain refused (one not yet unlocked since boot) is logged and tried again at the next launch. Once one has been deleted the phone asks for one more sign-in, its screen saying why ("Sign in again: Topo now signs in through Claude Code, which brings your claude.ai connectors.") until that sign-in lands. The conversation and the memory are CloudKit's and are untouched.

**Debug runs and CI.** A debug build launched with `TOPO_CLAUDE_SETUP_TOKEN`, or with `TOPO_DEBUG_TOKEN_PORT` and `TOPO_DEBUG_TOKEN_NONCE` naming a listener on the host's loopback that serves it the token once (`DebugRun.servedToken`, read at launch within one 10 s deadline and kept in memory, and a launch that names the port and gets none is signed out; `scripts/simulator-run.sh`'s, since the simulator's log and a UI test's result bundle record the launch environment) (`DebugRun.developerToken`), is marked signed in at launch (`DebugRun.signIn`, as `oauth_token`, which `DebugRun.accepts` counts) and every `claude` it starts gets the token as `CLAUDE_CODE_OAUTH_TOKEN` (`GuestResident.developerEnvironment`); a release build has neither. That token reaches no connector: a connector needs Claude Code's own login.

The hub runs no Claude Code yet, so it has no sign-in; the TV and the watch never sign in.

Diagnostics' *Claude login* row is `auth status`'s method and subscription from the cache, never a token.

## Connections

Settings › Connections (`Apps/Topo/ConnectionsView.swift`, over `Connections`) connects GitHub and 1Password: connect, who or what it is connected to, and disconnect. The tokens are `ConnectionStore` (`Packages/TopoAuth/Connections.swift`), one keychain item a service in service `zone.hexagon.topo.connections`, `AfterFirstUnlockThisDeviceOnly`, through `KeychainItem`, holding the token and the account the screen names.

GitHub is Topo's OAuth App (client ID `Ov23liOQVQHli5vrchlv`) through the OAuth device flow (`GitHubDeviceFlow`): the app asks `github.com/login/device/code` for a code with the client ID and the scopes `repo`, `read:org` and `workflow`, shows the code in the GitHub row and polls. Topo stands at the foot of the Connections page (`GitHubCodeSign`, drawn by the chat's engine through `MascotDriver`, a still under Reduce Motion, and drawing no frame while the browser's sheet is over him, `Connections.browserShowing`) with nothing in his hands. Nothing is copied and no page opened until the person taps *Copy code and open GitHub* in the row (`Connections.copyCodeAndOpenGitHub`): the code goes on the pasteboard and GitHub's page opens in `WebAuth`'s sheet at once. From the first copy (`Connections.codeCopied`) he holds the code up on a sign, which is a button: a tap copies again, jumps the sign, and opens the page after `look.settings.copiedPause`, only if the same connect is still waiting on the same code, so a Cancel, a second Connect, a sign-out or the flow ending meanwhile opens nothing. Each copy while the sign is up (`Connections.copies`) is said on the board itself, Copied for `copiedPause` and then the code again, so a code lost from the pasteboard is still there to read and copy. While the sheet opened for that code is up (`Connections.codeOverPage`: from the moment the system has taken the sheet, `WebAuth`'s `onShown`, until it goes, another page opens in its place, or the connect stops waiting) — which is from the system's prompt to use github.com, before the page shows, and over GitHub's login page when Safari has no GitHub session — he is drawn over the page too (`GitHubSignOverPage`), in a window one level above the app's and the scene's size (`AboveSheets`), since nothing in the app's own window draws over a sheet the system presents and that sheet takes no accessory. He swims up from the foot of the screen at `look.mascot.swimSpeed`, the animation SwiftUI's at the display's rate, to his place: the top of his sign's board (`GitHubCodeSign.boardTop`, art row 79) `look.settings.signOverPageTop` points under the safe area's top, centred, at `signOverPageScale` points an art pixel, which on an iPhone is below the browser's bar, so its close button and the address stay in sight. Only there does he take the sign up, saying Copied first. Under Reduce Motion he is put there. The window takes a touch only on a pixel of the picture he last drew, once he is in his place (`SignSeen`), and its `hitTest` answers nil for every other point, so the page has every other touch, the parts of the window round him included; a tap on him copies the code and opens nothing (`Connections.copyCode`). It is under the keyboard. Password AutoFill fills the GitHub login in the sheet. The flow polls `login/oauth/access_token` at the interval GitHub gave — from each `slow_down`, the interval GitHub names or five seconds more, whichever is longer — polling again after a network failure, until a token, a refusal, or the code's expiry by the flow's clock, and names the user from `api.github.com/user`. No client secret and no redirect are used anywhere. The token (`gho_`) does not expire, so nothing refreshes, and it reaches every repository the person can, with their organizations' membership and the right to change workflow files. It lasts until the person revokes it at github.com/settings/applications, which *Revoke on GitHub* opens in the same sheet. What the guest writes with it is signed: its commits are committed and authored by `Topo <topo@topo.invalid>`, linked to no person's account, and a body given to `issue create`, `issue comment`, `pr create` or `pr comment` carries `<!-- topo -->`, while a call with no body (`--fill`, an editor) goes out unmarked (`docs/guest.md`).

Each flow runs under a generation that Cancel, Disconnect, a second Connect and `forget()` move; the flow checks it after the poll and after `/user` and just before the save, so a flow walked away from saves nothing. Disconnect forgets the token on this phone; revoking it at GitHub takes the client secret, so the screen says where the person revokes it. A failed row keeps Disconnect beside Try again (`ConnectionsView.githubActions`), since the failure may be a clear the keychain refused with the token still on the phone: Disconnect tries the clear again, every connection's while a refused sign-out clear stands. A save whose generation is stale is refused. Signing out (`SignOut.forgetConnections`, before the login), a takeover by another phone (`Takeover`, in `ChatView`) and a demotion to viewer (`RootView`) all call `forget()`, which clears every service and says a keychain that refused rather than showing it disconnected — on the row, and after a sign-out, takeover or demotion on the sign-in screen (`SignIn.signOut(unfinished:)`, from `Connections.unforgotten`) — so a phone with no login keeps none of its person's tokens. `forget()` clears the controls' secrets too (`docs/widgets.md`, *Controls*), whose refused clear is kept and said beside the connections' and tried again alone. A clear the keychain refused is kept past it (`ConnectionsLeftBehind`, in the app's defaults): until a clear of every connection succeeds — tried at each launch, by Disconnect and before a connect — `topo github` hands out nothing and a connect is refused, so whoever signs in next is never handed a token an earlier login connected. The first launch of an install clears every connection too (`ConnectionsLeftBehind.installed`): the keychain outlives an uninstall and the defaults do not, so a token found then is an earlier install's. A token GitHub grants without every scope asked for (`repo`, `read:org`, `workflow`, read from the token response's `scope`) is refused with what it does carry, never saved as connected.

A debug launch with `TOPO_DEBUG_CONNECT_GITHUB=1` (`DebugRun.connectGitHub`) connects GitHub at launch as *Connect* does, against github.com itself, leaving the code on the sign for a tap, and prints each state the row takes as `[topo-debug] github: …` — the user code and its page, never the token or the device code — so a simulator shows a real code on the sign; tapping it and approving on GitHub are a person's.

1Password is a service account the person makes in 1Password (*Create a service account* opens 1Password's page for it in the sheet), scoped to the vaults they choose and read-only if they make it so, and whose token they paste (*Paste token*, the system's paste button, so reading the pasteboard asks nothing). `connectOnePassword` takes one `ops_` token and nothing else — `ops_` and then only `[A-Za-z0-9_]`, the alphabet service-account tokens are written in (`Connections.isServiceAccountToken`) —, checks it by running `op vault list` in the guest (`GuestOnePassword`, below), and saves it with the names of the vaults it reaches only when that answers with at least one; 1Password's refusal is said in its own `[ERROR]` lines. The check runs under a generation of its own that Cancel, Disconnect and `forget()` move, so a check walked away from saves nothing. Disconnect forgets the token on this phone, and its dialog tells the person to revoke the service account in 1Password too, since a copy taken while connected keeps working until they do. A failed row keeps Disconnect beside the paste (`ConnectionsView.onePasswordActions`), since the failure may be a clear the keychain refused with the token still on the phone: Disconnect tries the clear again, every connection's while a refused sign-out clear stands. A debug launch with `TOPO_DEBUG_ONEPASSWORD_TOKEN=<ops_…>` (`DebugRun.connectOnePassword`) connects at launch as a paste does and prints each state, the vaults' names and never the token.
