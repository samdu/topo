# Sign in with Claude

How the phone gets and keeps a Claude login, and the long-lived token the guest runs on. The guest's side of that token is `docs/guest.md`.

Sign in with Claude is `Packages/TopoAuth`: the Claude Code CLI's OAuth client (authorization code with PKCE against `claude.com/cai/oauth/authorize`, exchange and refresh at `platform.claude.com/v1/oauth/token`, the CLI's client id and scopes). The browser redirects to a loopback listener in the app; if that cannot bind, to the hosted callback page, whose `code#state` the user pastes.

Tokens live in the device keychain, never synced; only the primary and the hub ever hold one. The ordinary tokens are read and refreshed through one `StoredTokenProvider`, made in `TopoApp` and handed to the harness and to the guest's hand-over (`DebugRun.handOver`): a refresh token is single-use, a second grant on a spent one is refused, so the provider has one refresh in flight at most, held as a `Task` every caller of an expired set (or of `refresh()`) awaits for its tokens or its error, and cleared as it ends so a failed refresh is not kept.

The phone's sign-in (`SignIn(guestStore:)`, given `KeychainTokenStore.guest`) is two authorizations, as `claude login` and `claude setup-token` are two, so the person approves twice: the ordinary login, then the guest's token (`ClaudeOAuth.Grant.longLived`), asked for as `setup-token` asks — its own code and verifier, `user:inference` alone on the authorize URL and `expires_in: 31536000` on the code exchange — of which only the access token is kept, as its own keychain item beside the ordinary tokens. The second never touches the ordinary tokens: they are their own exchange's, refresh token included, because a refresh grant asking for `user:inference` rotates the refresh token it spends into one that will not refresh the ordinary scopes. With a loopback listener the login's callback answers with a redirect to the second authorization (`LoopbackCallback.redirectOnSuccess`), so one browser sheet carries both; without one the sign-in screen opens the second (`SignIn.Phase.approvingGuest(opening:)`) and its code is pasted like the first. A second authorization declined (Skip, or the sheet closed) or refused still signs in, with no guest token kept. Sign-out clears both.

`GuestCredential` hands the guest the long-lived token while it is unexpired and otherwise the ordinary access token, refreshed first when it is about to expire. The debug userland launch prints the guest token's scope and days left as `userland: mint scope:` (or that none is held) and refreshes the ordinary tokens once, asking for their own scopes, printing what that refresh granted as `userland: ordinary refresh scope:` or its refusal, never a value.
