# Sign in with Claude, and connections

How the phone signs in to Claude, and the services it is connected to on the person's behalf. The guest's side of the login is `docs/guest.md`.

## Sign in with Claude

The login is Claude Code's own, in the guest's unmodified `claude`: the OAuth client, the redirect, the code exchange and the stored credential are all Claude Code's, and Topo holds no Claude.ai token. `SignIn` (`Packages/TopoAuth`) drives it through a `ClaudeLogin`, which on the phone is `GuestLogin` (`Apps/Topo/GuestLogin.swift`):

1. **Ready.** The sign-in screen waits for the rootfs and Claude Code to be on the phone and the guest to boot (`SignIn.prepare`, "Getting Topo ready…" over the downloads' line), then offers *Sign in with Claude*. No sign-in happens before the guest is up.
2. **Login.** `claude auth login --claudeai` runs in the guest from the home (`/home/topo`, the app's `Documents/home`) with no resident beside it (`GuestSession.withoutResident`): the two are `claude` processes over one credentials file, and a resident reads its login once, as it starts. Its environment is the guest's and the tool service's, with `BROWSER` set to `topo-browser` (`GuestTools.browser`), which hands the URL it is given to `topo open-url`, and no `ANTHROPIC_BASE_URL`: the exchange goes to Claude's hosts directly.
3. **Approve.** `topo open-url` (`OpenURLTool`) hands the URL to the sign-in waiting for its browser (`LoginBrowser`), and only then, and only an https URL on `claude.com`, `claude.ai` or `platform.claude.com` with no user, password or port; any other call is refused, so no other guest process can put a page on the phone. The screen opens it in `WebAuth`'s sheet (not ephemeral, so the person is often already logged in). Its `redirect_uri` is `http://localhost:<port>/callback`, claude's own listener, which binds `127.0.0.1` only; guest sockets are the app's, so the sheet reaches it. claude exchanges the code itself, writes `~/.claude/.credentials.json` in the home, serves its own success page and exits 0.
4. **Signed in.** On exit 0 the app runs `claude auth status --json` and needs `loggedIn` and `authMethod == "claude.ai"` (`ClaudeLoginStatus.isClaudeAI`); exit 0 without it is a failure on the screen. The fact and the subscription, no token, are kept in the app's defaults (`LoginCache`) for the callers that ask before any guest is up: the role at launch, the memory, the sign-in screen's first frame and the resident's launcher, which refuses a launch while it says signed out. Every boot of the guest asks `auth status` again before any process starts (`GuestResident.booted`, `SignIn.refresh`), so a login that has gone puts the screen back on the sign-in; a status that cannot be read changes nothing. Claude Code refreshes its own tokens from then on.
5. **Paste fallback.** The same login prints a second URL on stdout, whose `redirect_uri` is Claude's hosted code page (`GuestLogin.pastePage`). When the loopback cannot be reached the browser stops on a connection error, so *Open the page again* opens that page (`SignIn.openPageAgain`) and shows the field: the `code#state` it shows is written to the login's stdin (`SignIn.paste`). With no login running any more, *Open the page again* starts a fresh one.
6. **Ending.** The person closing the loopback's sheet, or Cancel, ends the login: claude does not exit when its stdin closes, so the app ends the process (`GuestLoginAttempt.end`, every guest task, since nothing else runs beside it; a login that has already exited is not ended, since the resident may be starting again). Closing the paste page's sheet does not end it, since copying the code and closing the sheet is how the code reaches the field. `Login failed: …` (exit 1, a bad state or code) is what the screen says. Only the sheet that is up reports its close (`WebAuth`), and only the sheet the sign-in has now (`SignIn.sheetClosed`); what an attempt ended, cancelled or replaced says afterwards reaches nothing (`SignIn`'s generation).

**Sign-out, takeover, demotion.** Each ends with `SignIn.signOut`, last, after the harness, the memory and the connections: the cache is cleared at once, so nothing launches on the login from that moment, and then `claude auth logout` runs in the guest with no resident beside it, when the guest is up in this process, and the credentials file is removed from the host side whether or not it ran (`GuestLogin.logout`). A sign-in after it waits for that logout, and so does a `refresh`. The login does not outlive a delete of the app: the credential is in the app's container.

**Where the credential rests.** `.credentials.json` is in the guest's home inside the app container, which `GuestResident.makeHome` excludes from backup and makes, with `.claude` beside it, under `completeUntilFirstUserAuthentication`, so the file claude writes there takes that class. Any guest process can read it: a full-scope, refreshable Claude.ai credential (CLAUDE.md, *The holes in the guest*).

**The update from the earlier login.** A build before this one kept Claude.ai tokens in two keychain items (service `zone.hexagon.topo.claude`, accounts `claude` and `claude-guest`). The first launch of this build deletes both (`LoginMigration`, on the phone and on the hub) and the phone asks for one more sign-in, its screen saying why ("Sign in again: Topo now signs in through Claude Code, which brings your claude.ai connectors.") until that sign-in lands. The conversation and the memory are CloudKit's and are untouched.

**Debug runs and CI.** A debug build launched with `TOPO_CLAUDE_SETUP_TOKEN` (`DebugRun.developerToken`) is marked signed in at launch (`DebugRun.signIn`, as `oauth_token`, which `DebugRun.accepts` counts) and every `claude` it starts gets the token as `CLAUDE_CODE_OAUTH_TOKEN` (`GuestResident.developerEnvironment`); a release build has neither. That token reaches no connector: a connector needs Claude Code's own login.

The hub runs no Claude Code yet, so it has no sign-in; the TV and the watch never sign in.

Diagnostics' *Claude login* row is `auth status`'s method and subscription from the cache, never a token.

## Connections

Settings › Connections (`Apps/Topo/ConnectionsView.swift`, over `Connections`) connects GitHub and 1Password: connect, who or what it is connected to, and disconnect. The tokens are `ConnectionStore` (`Packages/TopoAuth/Connections.swift`), one keychain item a service in service `zone.hexagon.topo.connections`, `AfterFirstUnlockThisDeviceOnly`, through `KeychainItem`, holding the token and the account the screen names.

GitHub is Topo's OAuth App (client ID `Ov23liOQVQHli5vrchlv`) through the OAuth device flow (`GitHubDeviceFlow`): the app asks `github.com/login/device/code` for a code with the client ID and the scopes `repo`, `read:org` and `workflow`, shows the code on a sign Topo holds up at the foot of the Connections page (`GitHubCodeSign`, drawn by the chat's engine through `MascotDriver`, a still under Reduce Motion, and drawing no frame while the browser's sheet is over him, `Connections.browserShowing`) and polls. Nothing is copied and no page opened until the person taps the sign (`Connections.copyCodeAndOpenGitHub`): the code goes on the pasteboard at once, the sign jumps and the line under it says Copied in `highlight`, and GitHub's page opens in `WebAuth`'s sheet when that confirmation has stood `look.settings.copiedPause` — only if the same connect is still waiting on the same code, so a Cancel, a second Connect, a sign-out or the flow ending meanwhile opens nothing. *Copy code and open GitHub* in the row is the same tap with no pause, which is also how the page is opened again after the person closed it; the footer says the code is copied only once it is. Password AutoFill fills the GitHub login in the sheet. The flow polls `login/oauth/access_token` at the interval GitHub gave — from each `slow_down`, the interval GitHub names or five seconds more, whichever is longer — polling again after a network failure, until a token, a refusal, or the code's expiry by the flow's clock, and names the user from `api.github.com/user`. No client secret and no redirect are used anywhere. The token (`gho_`) does not expire, so nothing refreshes, and it reaches every repository the person can, with their organizations' membership and the right to change workflow files. It lasts until the person revokes it at github.com/settings/applications, which *Revoke on GitHub* opens in the same sheet.

Each flow runs under a generation that Cancel, Disconnect, a second Connect and `forget()` move; the flow checks it after the poll and after `/user` and just before the save, so a flow walked away from saves nothing. Disconnect forgets the token on this phone; revoking it at GitHub takes the client secret, so the screen says where the person revokes it. A failed row keeps Disconnect beside Try again (`ConnectionsView.githubActions`), since the failure may be a clear the keychain refused with the token still on the phone: Disconnect tries the clear again, every connection's while a refused sign-out clear stands. A save whose generation is stale is refused. Signing out (`SignOut.forgetConnections`, before the login), a takeover by another phone (`Takeover`, in `ChatView`) and a demotion to viewer (`RootView`) all call `forget()`, which clears every service and says a keychain that refused rather than showing it disconnected — on the row, and after a sign-out, takeover or demotion on the sign-in screen (`SignIn.signOut(unfinished:)`, from `Connections.unforgotten`) — so a phone with no login keeps none of its person's tokens. `forget()` clears the controls' secrets too (`docs/widgets.md`, *Controls*), whose refused clear is kept and said beside the connections' and tried again alone. A clear the keychain refused is kept past it (`ConnectionsLeftBehind`, in the app's defaults): until a clear of every connection succeeds — tried at each launch, by Disconnect and before a connect — `topo github` hands out nothing and a connect is refused, so whoever signs in next is never handed a token an earlier login connected. The first launch of an install clears every connection too (`ConnectionsLeftBehind.installed`): the keychain outlives an uninstall and the defaults do not, so a token found then is an earlier install's. A token GitHub grants without every scope asked for (`repo`, `read:org`, `workflow`, read from the token response's `scope`) is refused with what it does carry, never saved as connected.

A debug launch with `TOPO_DEBUG_CONNECT_GITHUB=1` (`DebugRun.connectGitHub`) connects GitHub at launch as *Connect* does, against github.com itself, leaving the code on the sign for a tap, and prints each state the row takes as `[topo-debug] github: …` — the user code and its page, never the token or the device code — so a simulator shows a real code on the sign; tapping it and approving on GitHub are a person's.

1Password is a service account the person makes in 1Password (*Create a service account* opens 1Password's page for it in the sheet), scoped to the vaults they choose and read-only if they make it so, and whose token they paste (*Paste token*, the system's paste button, so reading the pasteboard asks nothing). `connectOnePassword` takes one `ops_` token and nothing else — `ops_` and then only `[A-Za-z0-9_]`, the alphabet service-account tokens are written in (`Connections.isServiceAccountToken`) —, checks it by running `op vault list` in the guest (`GuestOnePassword`, below), and saves it with the names of the vaults it reaches only when that answers with at least one; 1Password's refusal is said in its own `[ERROR]` lines. The check runs under a generation of its own that Cancel, Disconnect and `forget()` move, so a check walked away from saves nothing. Disconnect forgets the token on this phone, and its dialog tells the person to revoke the service account in 1Password too, since a copy taken while connected keeps working until they do. A failed row keeps Disconnect beside the paste (`ConnectionsView.onePasswordActions`), since the failure may be a clear the keychain refused with the token still on the phone: Disconnect tries the clear again, every connection's while a refused sign-out clear stands. A debug launch with `TOPO_DEBUG_ONEPASSWORD_TOKEN=<ops_…>` (`DebugRun.connectOnePassword`) connects at launch as a paste does and prints each state, the vaults' names and never the token.
