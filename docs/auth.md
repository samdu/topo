# Sign in with Claude, and connections

How the phone gets and keeps a Claude login, the long-lived token the guest runs on, and the services it is connected to on the person's behalf. The guest's side of those tokens is `docs/guest.md`.

Sign in with Claude is `Packages/TopoAuth`: the Claude Code CLI's OAuth client (authorization code with PKCE against `claude.com/cai/oauth/authorize`, exchange and refresh at `platform.claude.com/v1/oauth/token`, the CLI's client id and scopes). The browser redirects to a loopback listener in the app; if that cannot bind, to the hosted callback page, whose `code#state` the user pastes.

Tokens live in the device keychain, never synced; only the primary and the hub ever hold one. The ordinary tokens are read and refreshed through one `StoredTokenProvider`, made in `TopoApp` and handed to the harness and to the guest's hand-over (`DebugRun.handOver`): a refresh token is single-use, a second grant on a spent one is refused, so the provider has one refresh in flight at most, held as a `Task` every caller of an expired set (or of `refresh()`) awaits for its tokens or its error, and cleared as it ends so a failed refresh is not kept.

The phone's sign-in (`SignIn(guestStore:)`, given `KeychainTokenStore.guest`) is two authorizations, as `claude login` and `claude setup-token` are two, so the person approves twice: the ordinary login, then the guest's token (`ClaudeOAuth.Grant.longLived`), asked for as `setup-token` asks — its own code and verifier, `user:inference` alone on the authorize URL and `expires_in: 31536000` on the code exchange — of which only the access token is kept, as its own keychain item beside the ordinary tokens. The second never touches the ordinary tokens: they are their own exchange's, refresh token included, because a refresh grant asking for `user:inference` rotates the refresh token it spends into one that will not refresh the ordinary scopes. With a loopback listener the login's callback answers with a redirect to the second authorization (`LoopbackCallback.redirectOnSuccess`), so one browser sheet carries both; without one the sign-in screen opens the second (`SignIn.Phase.approvingGuest(opening:)`) and its code is pasted like the first. A second authorization declined (Skip, or the sheet closed) or refused still signs in, with no guest token kept. Sign-out clears both.

`GuestCredential` hands the guest the long-lived token while it is unexpired and otherwise the ordinary access token, refreshed first when it is about to expire. The debug userland launch prints the guest token's scope and days left as `userland: mint scope:` (or that none is held) and refreshes the ordinary tokens once, asking for their own scopes, printing what that refresh granted as `userland: ordinary refresh scope:` or its refusal, never a value.

## Connections

Settings › Connections (`Apps/Topo/ConnectionsView.swift`, over `Connections`) connects GitHub: connect, who it is connected as, and disconnect. The tokens are `ConnectionStore` (`Packages/TopoAuth/Connections.swift`), one keychain item a service in service `zone.hexagon.topo.connections`, `AfterFirstUnlockThisDeviceOnly` as the Claude tokens are (both through `KeychainItem`), holding the token and the account the screen names.

GitHub is Topo's OAuth App (client ID `Ov23liOQVQHli5vrchlv`) through the OAuth device flow (`GitHubDeviceFlow`): the app asks `github.com/login/device/code` for a code with the client ID and the scopes `repo`, `read:org` and `workflow`, copies the code to the pasteboard, shows it and opens GitHub's page for it in `WebAuth`'s sheet, where Password AutoFill fills the GitHub login; it then polls `login/oauth/access_token` at the interval GitHub gave — from each `slow_down`, the interval GitHub names or five seconds more, whichever is longer — polling again after a network failure, until a token, a refusal, or the code's expiry by the flow's clock, and names the user from `api.github.com/user`. No client secret and no redirect are used anywhere. The token (`gho_`) does not expire, so nothing refreshes, and it reaches every repository the person can, with their organizations' membership and the right to change workflow files. It lasts until the person revokes it at github.com/settings/applications, which *Revoke on GitHub* opens in the same sheet.

Each flow runs under a generation that Cancel, Disconnect, a second Connect and `forget()` move; the flow checks it after the poll and after `/user` and just before the save, so a flow walked away from saves nothing. Disconnect forgets the token on this phone; revoking it at GitHub takes the client secret, so the screen says where the person revokes it. A save whose generation is stale is refused. Signing out (`SignOut.forgetConnections`, before the login), a takeover by another phone (`Takeover`, in `ChatView`) and a demotion to viewer (`RootView`) all call `forget()`, which clears every service and says a keychain that refused rather than showing it disconnected — on the row, and after a sign-out, takeover or demotion on the sign-in screen (`SignIn.signOut(unfinished:)`, from `Connections.unforgotten`) — so a phone with no login keeps none of its person's tokens.

A debug launch with `TOPO_DEBUG_CONNECT_GITHUB=1` (`DebugRun.connectGitHub`) connects GitHub at launch as *Connect* does, against github.com itself, and prints each state the row takes as `[topo-debug] github: …` — the user code and its page, never the token or the device code — so a simulator shows a real code and GitHub's page in the sheet; approving it is a person's.
